The `cocoindex.resources` package provides common data models and abstractions shared across connectors and built-in operations. Connectors provide concrete implementations — for example, `localfs.File` implements `FileLike`, and `localfs.FilePath` extends `FilePath`. See individual [connector docs](../connectors/localfs) for connector-specific details.

The Rust SDK has the same modules under `cocoindex::resources` (`file`, `fs`, `chunk`, `embedder`, `id`, `live_map`, `rate_limit`, `schema`). The types this page names are re-exported from `cocoindex::prelude`. The local file system lives in `cocoindex::resources::fs`: its `FileEntry` implements `FileLike`, and `walk_dir` builds a `FilePath` for each file.

## File

The file module (`cocoindex.resources.file`) defines base classes and utilities for working with file-like objects.

### FileLike

`FileLike` is a base class for file objects with async read methods. Each connector provides its own subclass (e.g., `localfs.File`, `amazon_s3.S3Object`).

{/* Rust: rust/sdk/cocoindex/tests/pipeline.rs (read_file), examples/rust/azure_blob_embedding/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
from cocoindex.resources.file import FileLike

async def process_file(file: FileLike) -> str:
    text = await file.read_text()
    ...
    return text
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::prelude::*;

#[cocoindex::function(memo)]
async fn read_file(ctx: &Ctx, file: &FileEntry) -> Result<String> {
    file.read_text().await
}
```

In Rust, `FileLike` is a trait (`cocoindex::resources::file::FileLike`). Each connector has a type that implements it: `FileEntry` for the local file system, `AzureBlobFile` for Azure Blob Storage, and so on. A function takes the concrete type, as above, or a `&dyn FileLike`.

</Fragment>
</LangTabs>

**Properties:**

- `file_path` — A `FilePath` object representing the file's path. Access the relative path via `file_path.path` (`PurePath`).

**Methods:**

- `async size()` — Return the file size in bytes.
- `async read(size=-1)` — Read file content as bytes. Pass `size` to limit bytes read.
- `async read_text(encoding=None, errors="replace")` — Read as text. Auto-detects encoding via BOM if not specified.

The Rust trait has the same surface with Rust names:

| Python | Rust (`FileLike`) |
|---|---|
| `file.file_path` | `file.file_path()` returns a `FilePath` |
| `await file.size()` | `file.metadata().await?.size`; `FileMetadata` also holds `modified` and an optional `content_fingerprint` |
| `await file.read()` | `file.read().await?` returns `bytes::Bytes` (the cached content, shared, not copied) |
| `await file.read(size)` | `file.read_size(size).await?` |
| `await file.read_text()` | `file.read_text().await?` detects a BOM and decodes with replacement characters |
| `await file.read_text(encoding="latin1", errors="strict")` | `file.read_text_with(Some("latin1"), DecodeErrors::Strict).await?` |
| — | `file.content_fingerprint().await?` returns the `Fingerprint` the memo validation uses |

`read_text_with(encoding, errors)` is Python's `read_text(encoding=, errors=)`: `encoding` is a WHATWG label such as `"latin1"` or `"utf-16le"` (or `"utf-32le"` / `"utf-32be"`), `None` detects by BOM and falls back to UTF-8; `DecodeErrors::Replace` (the default), `Ignore` and `Strict` are Python's `"replace"`, `"ignore"` and `"strict"`. `decode_bytes_with` does the same on bytes you already hold. `FileEntry` adds the sync helpers `content()` and `content_str()`, plus `key()`, `stem()` and `relative_path()`.

**Memoization:**

`FileLike` objects provide a memoization key based on `file_path` (file identity). When used as arguments to a [memoized function](../programming_guide/function#memoization), CocoIndex uses a two-level validation: it checks the modification time first (cheap), then computes a content fingerprint only if the modification time has changed. This means touching a file or moving it won't cause unnecessary recomputation if the content is unchanged. When the backend reports a fingerprint at no cost (for example an S3 ETag), CocoIndex compares it even when the modification time is unchanged. This catches an overwrite within the resolution of the modification time (S3 reports whole seconds).

The Rust types do the same: a `FileLike` is a `MemoInput` whose key is `file_path().memo_key()`, and whose state is the modification time, validated by the content fingerprint when the time changed. A `FileEntry` can therefore be an argument of a `#[cocoindex::function(memo)]` directly, or inside a `Vec`.

### FilePath

`FilePath` is a base class that combines a **base directory** (with a stable key) and a **relative path**. This enables stable memoization even when the entire directory tree is moved to a different location.

{/* Rust: rust/sdk/cocoindex/tests/pipeline.rs (with_base_dir), rust/sdk/cocoindex/tests/fs_target.rs (under_context_dir) */}
<LangTabs>
<Fragment slot="python">

```python
from cocoindex.resources.file import FilePath
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::prelude::*;

// A path with no base key: memoization follows the path itself.
let path = FilePath::new("docs/guide.md");

// A base directory under a stable key: the tree can move between runs.
let files = walk_dir(FilePath::with_base_dir("docs", root.to_path_buf(), PathBuf::new()))
    .recursive(true)
    .walk()?;

// The base directory comes from a `ContextKey<PathBuf>` provided in the lifespan.
let root = FilePath::under_context_dir(&ctx, &OUT_DIR, "out")?;
```

In Rust there is one `FilePath` struct for every connector. `with_base_dir(base_key, base_dir, path)` is Python's `FilePath(path, base_dir=...)`; `under_context_dir(&ctx, &KEY, path)` reads the base directory from the context and uses the key's name as the base key.

</Fragment>
</LangTabs>

Each connector provides its own `FilePath` subclass (e.g., `localfs.FilePath`). The base class defines the common interface.

**Properties:**

- `base_dir` — An object that holds the base directory. Its key is used for stable memoization.
- `path` — The path relative to the base directory (`PurePath`).

**Methods:**

- `resolve()` — Resolve to the full path (type depends on the connector, e.g., `pathlib.Path` for local filesystem).

In Rust, `path()` returns the relative `&Path`, `base_key()` the optional base key, and `resolve()` a `PathBuf` (the base directory joined with the path).

**Path Operations:**

`FilePath` supports most `pathlib.PurePath` operations:

```python
# Join paths with /
config_path = source_dir / "config" / "settings.json"

# Access path properties
config_path.name      # "settings.json"
config_path.stem      # "settings"
config_path.suffix    # ".json"
config_path.parts     # ("config", "settings.json")
config_path.parent    # FilePath pointing to "config/"

# Modify path components
config_path.with_name("other.json")
config_path.with_suffix(".yaml")
config_path.with_stem("config")

# Pattern matching
config_path.match("*.json")  # True

# Convert to POSIX string
config_path.as_posix()  # "config/settings.json"
```

The Rust `FilePath` has the same operations as methods: `join(child)`, `name()`, `stem()`, `suffix()`, `suffixes()`, `parts()`, `parent()`, `with_name(..)`, `with_stem(..)`, `with_suffix(..)`, `parents()`, `relative_to(base)`, `is_relative_to(base)`, `matches(pattern)` and `as_posix()`. `matches` follows `PurePath.match`: a relative pattern is matched from the right, one component at a time, and an absolute pattern must match the whole path.

**Memoization:**

`FilePath` provides a memoization key based on `(base_dir.key, path)`. This means:

- Two `FilePath` objects with the same base directory key and relative path have the same memo key
- Moving the entire project directory doesn't invalidate memoization, as long as the same base directory key is used

For connector-specific usage (e.g., `register_base_dir`), see the individual connector documentation like [Local File System](../connectors/localfs).

In Rust, `memo_key()` returns that same `(base_key, path)` pair, and it falls back to the path alone when the `FilePath` has no base key.

### FilePathMatcher

`FilePathMatcher` is a protocol for filtering files and directories during traversal.

```python
from cocoindex.resources.file import FilePathMatcher

class MyMatcher(FilePathMatcher):
    def is_dir_included(self, path: PurePath) -> bool:
        """Return True to traverse this directory."""
        return not path.name.startswith(".")

    def is_file_included(self, path: PurePath) -> bool:
        """Return True to include this file."""
        return path.suffix in (".py", ".md")
```

In Rust, `FilePathMatcher` is a trait with the same two methods, `is_dir_included(&self, path: &Path) -> bool` (default: `true`) and `is_file_included(&self, path: &Path) -> bool`. Pass an implementation to `walk_dir(..).path_matcher(..)`. `MatchAllFilePathMatcher` includes everything.

#### PatternFilePathMatcher

A built-in `FilePathMatcher` implementation using [globset](https://docs.rs/globset/#syntax) patterns:

{/* Rust: examples/rust/text_embedding/src/main.rs; PatternFilePathMatcher::include from rust/sdk/cocoindex/src/resources/file.rs */}
<LangTabs>
<Fragment slot="python">

```python
from cocoindex.resources.file import PatternFilePathMatcher

# Include only Python and Markdown files, exclude tests and hidden dirs
matcher = PatternFilePathMatcher(
    included_patterns=["**/*.py", "**/*.md"],
    excluded_patterns=["**/test_*", "**/.*"],
)
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::prelude::*;

// Include only Markdown files; no exclusions.
let files = walk_dir(sourcedir)
    .recursive(true)
    .path_matcher(PatternFilePathMatcher::new(
        ["**/*.md"],
        std::iter::empty::<&str>(),
    )?);
```

`PatternFilePathMatcher::new(included, excluded)` takes two iterables of patterns and returns a `Result`: an invalid glob is an error at construction. `PatternFilePathMatcher::include(patterns)` is the form with no exclusions.

</Fragment>
</LangTabs>

**Parameters:**

- `included_patterns` — Glob patterns ([globset](https://docs.rs/globset) syntax) for files to include. Use `**/*.ext` to match at any depth. If `None`, all files are included.
- `excluded_patterns` — Glob patterns ([globset](https://docs.rs/globset) syntax) for files/directories to exclude. Excluded directories are not traversed. A pattern prefixed with `!` negates the exclusion for matching paths (see below).

:::note
Patterns use [globset](https://docs.rs/globset) semantics: `*.py` matches only in the root directory; use `**/*.py` to match at any depth.
:::

**Gitignore-style negation.** Within `excluded_patterns`, a pattern beginning with `!` *un-excludes* paths that would otherwise be excluded by a preceding pattern. This lets you exclude broadly and then carve out exceptions, instead of enumerating every directory to exclude:

```python
# Exclude all dot-entries, but keep .github through
matcher = PatternFilePathMatcher(
    excluded_patterns=[
        "**/.*",           # exclude all dot-files and dot-directories
        "!**/.github/**",  # …except anything under .github
    ]
)
```

Directory traversal honors negations correctly: a directory excluded by a normal pattern is still traversed when a `!` pattern could match its contents, so the kept paths inside it are reachable.

The Rust matcher reads the same `!` negations from its `excluded` patterns, and traverses directories the same way.

## Chunk

The chunk module (`cocoindex.resources.chunk`) defines types for representing text chunks produced by [text splitters](../ops/text).

### Chunk
A `Chunk` is a frozen dataclass representing a piece of text with its position information in the original document.

```python
from cocoindex.resources.chunk import Chunk
```

**Fields:**

- `text` (`str`) — The text content of the chunk.
- `start` (`TextPosition`) — Start position in the original text.
- `end` (`TextPosition`) — End position in the original text.

The Rust `Chunk` (`cocoindex::resources::chunk::Chunk`, in the prelude) has the public fields `start` and `end`, but it does not own its text. It keeps the byte range: `chunk.range()` returns it, and `chunk.text(&source)` returns the slice of the original string. Chunking a large document therefore does not copy its contents.

### TextPosition

A frozen dataclass representing a position in text.

**Fields:**

- `byte_offset` (`int`) — Byte offset from the start of the text.
- `char_offset` (`int`) — Character offset from the start of the text.
- `line` (`int`) — 1-based line number.
- `column` (`int`) — 1-based column number.

In Rust, `TextPosition` has the same four fields: `byte_offset` and `char_offset` are `usize`, `line` and `column` are `u32`.

**Example:**

{/* Rust: examples/rust/text_embedding/src/main.rs (split_with and chunk.text) */}
<LangTabs>
<Fragment slot="python">

```python
from cocoindex.ops.text import RecursiveSplitter

splitter = RecursiveSplitter()
chunks = splitter.split(text, chunk_size=2000, chunk_overlap=500, language="markdown")

for chunk in chunks:
    print(f"[{chunk.start.line}:{chunk.start.column}] {chunk.text[:50]}...")
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::ops::text::{RecursiveChunkConfig, RecursiveSplitter};

let splitter = RecursiveSplitter::new()?;
let chunks = splitter.split_with(
    &text,
    RecursiveChunkConfig {
        chunk_size: 2000,
        min_chunk_size: None,
        chunk_overlap: Some(500),
        language: Some("markdown".to_string()),
    },
);

for chunk in &chunks {
    println!("[{}:{}] {}", chunk.start.line, chunk.start.column, chunk.text(&text));
}
```

</Fragment>
</LangTabs>

## Embedder

The embedder module (`cocoindex.resources.embedder`) defines a protocol for single-text async embedding.

### Embedder Protocol

{/* Rust: rust/sdk/cocoindex/src/resources/embedder.rs (trait definition) */}
<LangTabs>
<Fragment slot="python">

```python
from cocoindex.resources.embedder import Embedder

class Embedder(Protocol):
    async def embed(self, text: str) -> NDArray[np.float32]: ...
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::prelude::*;

#[async_trait]
pub trait Embedder: Send + Sync {
    async fn embed(&self, ctx: &Ctx, text: &str) -> Result<Vec<f32>>;
}
```

The Rust trait takes the `Ctx` explicitly, so an implementation can memoize each text and batch concurrent calls through the engine. The two built-in embedders, [`SentenceTransformerEmbedder`](../ops/sentence_transformers) and [`ApiEmbedder`](../ops/litellm), do both.

</Fragment>
</LangTabs>

This is the call-site contract that consumers like [`resolve_entities`](../ops/entity_resolution) rely on. Both [`LiteLLMEmbedder`](../ops/litellm) and [`SentenceTransformerEmbedder`](../ops/sentence_transformers) satisfy this protocol — `await embedder.embed("some text")` returns a single `NDArray[np.float32]`.

The protocol is deliberately narrow: it does not include `dimension()` or `__coco_vector_schema__()`, which are concerns of connectors and table-schema creation, not of embedding consumers.

{/* Rust: examples/rust/conversation_to_knowledge/src/pipeline.rs (resolve_entities) */}
<LangTabs>
<Fragment slot="python">

```python
# Any embedder works with resolve_entities:
from cocoindex.ops.entity_resolution import resolve_entities

result = await resolve_entities(
    entities={"Apple Inc.", "Apple"},
    embedder=my_embedder,  # LiteLLMEmbedder, SentenceTransformerEmbedder, or your own
    resolve_pair=my_resolver,
)
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::entity_resolution;

// Any `Embedder` works with resolve_entities.
let embedder = ctx.get_key(&EMBEDDER)?;
let resolved = entity_resolution::resolve_entities(
    ctx,
    names,
    embedder,
    &resolver,
    None,
    entity_resolution::ResolveOptions::default(),
)
.await?;
```

`resolve_entities` takes an `EntityEmbedder`. Every `Embedder` is one through a blanket implementation, so a `SentenceTransformerEmbedder`, an `ApiEmbedder` or your own type works as is.

</Fragment>
</LangTabs>
