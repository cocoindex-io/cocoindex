a pipeline makes to an external service — so it stays within that service's rate

## RateLimiter

A token-bucket limiter. Acquire tokens with <Lang only="python">`await limiter.acquire(n)`</Lang><Lang only="rust">`limiter.acquire(n).await?`</Lang>; the call
returns once `n` tokens are available, otherwise it waits.

{/* Rust: rust/sdk/cocoindex/src/resources/rate_limit.rs (signatures) */}
<LangTabs>
<Fragment slot="python">

```python
class RateLimiter:
    def __init__(
        self,
        max_rows_per_second: float,
        burst_window_secs: float = 1.0,
    ) -> None: ...

    async def acquire(self, n: int = 1) -> None: ...
```

</Fragment>
<Fragment slot="rust">

```rust
impl RateLimiter {
    pub fn new(max_rows_per_second: f64, burst_window: Duration) -> Result<Self>;
    pub async fn acquire(&self, n: u32) -> Result<()>;
}
```

</Fragment>
</LangTabs>

<RustNote>
The constructor and `acquire` have no default arguments: pass `Duration::from_secs(1)` for a one-second burst window, and `acquire(1)` for one token. An invalid rate (zero or negative) is an error from `new`, not a panic.
</RustNote>

**Constructor parameters:**

- `max_rows_per_second` — the **sustained** rate, in tokens (think: units of
  work) per second. Fractional rates are supported (e.g. `2.5` → one token every
  0.4s). Must be positive.

<Lang only="python">

- `burst_window_secs` — the **burst** allowance, in seconds. Up to
  `max_rows_per_second * burst_window_secs` tokens may accumulate while the
  limiter is idle, letting a sudden fan-out proceed immediately before settling
  to the sustained rate. Defaults to `1.0` (a one-second burst). Set to `0.0` for
  no burst (strict spacing between tokens).

</Lang>

<Lang only="rust">

- `burst_window` — the **burst** allowance, as a `Duration`. Up to
  `max_rows_per_second` × `burst_window` (in seconds) tokens may accumulate while the
  limiter is idle, letting a sudden fan-out proceed immediately before settling
  to the sustained rate. `Duration::from_secs(1)` gives a one-second burst;
  `Duration::ZERO` gives no burst (strict spacing between tokens).

</Lang>

**<Lang only="python">`acquire(n=1)`</Lang><Lang only="rust">`acquire(n)`</Lang>** — wait until `n` tokens are available, then consume them. A
single `RateLimiter` is safe to share across concurrent callers; they are served
in **FIFO order**, so no caller can be starved.

{/* Rust: rust/sdk/cocoindex/src/resources/rate_limit.rs (signatures) */}
<LangTabs>
<Fragment slot="python">

```python
limiter = RateLimiter(max_rows_per_second=20.0)

# Pace outbound calls at ~20/s (with a 1s burst).
async def fetch(item: Item) -> Data:
    await limiter.acquire()          # one token
    return await call_external_api(item)
```

</Fragment>
<Fragment slot="rust">

```rust
let limiter = RateLimiter::new(20.0, Duration::from_secs(1))?;

// Pace outbound calls at ~20/s (with a 1s burst).
limiter.acquire(1).await?; // one token
```

</Fragment>
</LangTabs>

## One budget per instance

The budget lives in the `RateLimiter` **object**, not in its settings. So the unit
of sharing is the instance: functions and components handed the *same*
`RateLimiter` draw from one shared budget, while two separately-constructed
limiters are two independent budgets — even with identical `max_rows_per_second`.

<Lang only="rust">

`RateLimiter` is `Clone`, and every clone shares the one bucket. Cloning
is the way to hand a limiter to several closures; it does not create a second budget.

</Lang>

The idiomatic way to share one budget is to bind a `RateLimiter` to a
[context](../programming_guide/context) key and retrieve it with <Lang only="python">`coco.use_context`</Lang><Lang only="rust">`ctx.get_key`</Lang>
wherever you make outbound calls. Every component then draws from the same budget,
with no limiter to thread through each signature:

{/* Rust: context_key! / provide_key / get_key from examples/rust/text_embedding/src/main.rs; RateLimiter from rust/sdk/cocoindex/src/resources/rate_limit.rs (signatures) */}
<LangTabs>
<Fragment slot="python">

```python
import cocoindex as coco
from cocoindex.resources.rate_limit import RateLimiter

RATE_LIMIT = coco.ContextKey[RateLimiter]("rate_limiter")


@coco.lifespan
async def lifespan(builder: coco.EnvironmentBuilder):
    builder.provide(RATE_LIMIT, RateLimiter(max_rows_per_second=50.0))
    yield


@coco.fn
async def fetch_one(item: Item) -> Data:
    await coco.use_context(RATE_LIMIT).acquire()
    return await call_external_api(item)
```

</Fragment>
<Fragment slot="rust">

```rust
use std::time::Duration;

use cocoindex::prelude::*;

cocoindex::context_key!(static RATE_LIMIT: RateLimiter);

#[cocoindex::lifespan]
async fn lifespan(builder: EnvironmentBuilder) -> Result<EnvironmentBuilder> {
    Ok(builder.provide_key(&RATE_LIMIT, RateLimiter::new(50.0, Duration::from_secs(1))?))
}

#[cocoindex::function]
async fn fetch_one(ctx: &Ctx, item: Item) -> Result<Data> {
    ctx.get_key(&RATE_LIMIT)?.acquire(1).await?;
    call_external_api(item).await
}
```

</Fragment>
</LangTabs>

Because the key resolves to one shared instance, every `acquire` call across the app
draws from the same 50/s budget.

## Pacing a batched function

<Lang only="python">

A [batched function](../programming_guide/function#batching) whose every batch is one request can take its tokens from the limiter itself: pass it as `rate_limiter`, and each batch takes one token before it runs. A token then pays for one batch rather than one call, and calls that arrive while the batcher waits for a token ride the next batch, so a scarce quota is spent on full batches. See [Pacing batches with a rate limiter](../programming_guide/function#pacing-batches-with-a-rate-limiter).

```python
limiter = RateLimiter(max_rows_per_second=1.0)


@coco.fn.as_async(batching=True, max_batch_size=100, rate_limiter=limiter)
async def fetch_many(ids: list[str]) -> list[Item]:
    return await call_external_api(ids)  # one request per batch, one token each
```

</Lang>

<Lang only="rust">

A [batched function](../programming_guide/function#batching) whose every batch is one request can pace itself on the limiter: call `acquire(1)` at the start of the batched body. The body runs once per batch, so a token pays for one batch rather than one call, and a scarce quota is spent on batches rather than on single items.

</Lang>

<RustNote>
`#[cocoindex::function(batching, ..)]` has no `rate_limiter` option, so the batcher does not wait for a token before it forms a batch. Call `acquire(1)` in the body instead.
</RustNote>

## When to use it

Reach for a `RateLimiter` whenever a pipeline makes outbound calls to a
rate-limited service — an API you query from a <Lang only="python">`@coco.fn`</Lang><Lang only="rust">`#[cocoindex::function]`</Lang>, an embedding or LLM
endpoint, a bucket or database with a request cap — and you want the whole
pipeline to stay within one budget rather than each call site guessing at its own
`sleep`. Because a fan-out (e.g. one component per source item) can otherwise
issue requests as fast as the engine schedules them, a shared limiter is the
simplest way to keep concurrent components cooperatively under quota.
