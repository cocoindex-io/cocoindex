By default, an update (<Lang only="python">`app.update()`</Lang><Lang only="rust">`app.update(body)`</Lang>) runs in **catch-up mode**: it scans all sources, processes what changed since the last run (memoized components are skipped, so unchanged work is not redone), syncs target states, and returns. Targets are caught up to the moment the run started, and that's it — to pick up further changes, you run an update again.

**Live mode** keeps the app running after catch-up finishes and lets components stream changes continuously from their sources (e.g. a file system watcher or a database change feed), applying them to target states with low latency. This is useful when:

- You want near-real-time reactions to source changes, instead of waiting for the next update
- Your sources can push changes more efficiently than a full rescan can discover them

Two things are needed for live mode to work: the app must be **enabled** to stay running, and somewhere in the component tree a component must **react** to changes.

## Reacting to changes

Enabling live mode keeps the app running, but something in the component tree needs to actually watch for changes. That something is a [**LiveComponent**](../advanced_topics/live_component) — a component with a long-running `process_live()` method that delivers incremental updates.

You rarely need to write a `LiveComponent` manually. The two most common patterns are:

<Lang only="python">

### Sources with `LiveMapView` or `LiveMapFeed`

Source connectors can provide live capabilities via two [protocols](../advanced_topics/live_component#livemapfeed-and-livemapview):

- **`LiveMapView`** — the source has scannable current state (e.g., a directory or database table). It does a full scan first, then watches for changes. Example: [`localfs.walk_dir(live=True).items()`](../connectors/localfs#live-file-watching).
- **`LiveMapFeed`** — the source only streams changes, with no snapshot to scan (e.g., a Kafka consumer). All data arrives via the change stream. Example: [`kafka.topic_as_map()`](../connectors/kafka#as-source).

When `mount_each()` receives either, it automatically creates a `LiveComponent` internally that:

</Lang>

<Lang only="rust">

### Sources with `LiveMapView`

Source connectors provide live capabilities through two [traits](../advanced_topics/live_component#livemapfeed-and-livemapview):

- **`LiveMapFeed`** — `watch` streams changes to a subscriber. A feed with no snapshot to scan works only in live mode.
- **`LiveMapView`** — a `LiveMapFeed` that also has a `scan` of its current state, so it works in both catch-up and live modes. Examples: [`walk_dir(..).live()`](../connectors/localfs#live-file-watching) and [`kafka::topic_as_map`](../connectors/kafka#as-source).

`ctx.mount_each_live(&key, feed, f)` takes a `LiveMapView` and mounts one child component per key. It creates a `LiveComponent` internally that:

</Lang>

1. **Scans current state** (if available) — iterates all items and mounts a processing component for each
2. **Signals readiness** — the initial scan is complete (or the stream has caught up), target states are synced
3. **Watches for changes** — the source delivers incremental updates:
   - New or modified items → re-mount the affected component
   - Deleted items → remove the component and its target states

CocoIndex handles change detection, memoization, and target state reconciliation the same way as in catch-up mode.

<Lang only="python">

Without live support on the source, `mount_each()` falls back to catch-up behavior — a one-time iteration over items and that's it.

</Lang>

<Lang only="rust">

In catch-up mode, `mount_each_live` scans the feed once and returns. `mount_each!` and `ctx.mount_each` take a plain iterator instead, and always do a one-time iteration over the items. A `LiveComponent` of your own implements the `LiveComponent` trait (`process`, and `process_live` for the reactive body) and is mounted with `ctx.mount_live(&key, component)`.

</Lang>

<Lang only="python">

### Periodic refresh with `ctx.auto_refresh`

When the source isn't change-aware but you still want fresh data (say, polling a REST endpoint or re-reading a database table that doesn't emit change events) mount your processing body with [`ctx.auto_refresh`](../advanced_topics/live_component#example-periodic-refresh-with-cocoauto_refresh). It runs the body once, signals readiness, then re-runs it on a fixed delay:

</Lang>

{/* Rust: rust/sdk/cocoindex/tests/live_component.rs (`ctx.auto_refresh`), verified against rust/sdk/cocoindex/src/ctx.rs */}
<LangTabs>
<Fragment slot="python">

```python
import datetime
import cocoindex as coco

async def sync_users(db, target) -> None:
    rows = await db.fetch_all_users()
    for row in rows:
        target.declare_row(row=UserRow(...))

@coco.fn
async def app_main(db, target) -> None:
    await coco.mount(
        coco.auto_refresh(sync_users, interval=datetime.timedelta(minutes=5)),
        db, target,
    )

app = coco.App(coco.AppConfig(name="UserSync"), app_main, db=..., target=...)
app.update_blocking(live=True)
```

</Fragment>
<Fragment slot="rust">

```rust
ctx.auto_refresh(&"poller", Duration::from_secs(60), |ctx| async move {
    // declare the rows that exist now ...
    Ok(())
})
.await?;
```

`ctx.auto_refresh(&key, interval, f)` mounts the refresh component under `key`. In catch-up mode it runs `f` once and returns. In live mode it runs once, marks the component ready, then runs again after each `interval`.

</Fragment>
</LangTabs>

<Lang only="python">

**Catch-up compatibility:** in catch-up mode (the default), `auto_refresh` runs `sync_users` once and exits — observationally identical to mounting `sync_users` directly. The interval is ignored. Same pipeline, choose catch-up or live at run time.

**Handling deletes:** each cycle's declarations are reconciled against the previous run. If a row disappears from the source table between polls, `sync_users` simply doesn't declare it that cycle — CocoIndex automatically deletes the corresponding target. You don't need to track deletions yourself.

</Lang>

### Decoupling stages with an in-memory `LiveMap`

When one part of your pipeline produces keyed data and another consumes it (without going through an external system) put an in-memory [`LiveMap`](../common_resources/live_map) between them. Producers declare `(key, value)` entries; the consumer reads it as a `LiveMapView` via <Lang only="python">`mount_each`</Lang><Lang only="rust">`ctx.mount_each_live`</Lang>, reacting to adds, updates, and deletes just like a live source.

<Lang only="rust">

`LiveMap<K, V>` takes any `LiveMapKey` as `K` (`String`, `i64`, `u64` or a `StableKey`):

{/* Rust: rust/sdk/SHOWCASE.md "In-memory `LiveMap`", verified against rust/sdk/cocoindex/tests/live_map.rs */}
```rust
let lm: LiveMap<i64, String> = LiveMap::create(&ctx).await?;
lm.declare_entry(&ctx, 7, "seven".to_string())?;           // producer side
ctx.mount_each_live(&"entries", lm.clone(), process_entry).await?; // consumer side
```

</Lang>

## Examples

### `localfs` — file watching with `LiveMapView`

The [`localfs`](../connectors/localfs) connector supports live mode via <Lang only="python">`walk_dir(..., live=True)`, which watches for file system changes using `watchfiles`</Lang><Lang only="rust">`walk_dir(..).live()`, which watches for file system changes</Lang>:

{/* Rust: examples/rust/text_embedding/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
@coco.fn
async def app_main(sourcedir: pathlib.Path, outdir: pathlib.Path) -> None:
    files = localfs.walk_dir(
        sourcedir, recursive=True,
        path_matcher=PatternFilePathMatcher(included_patterns=["**/*.md"]),
        live=True,  # items() returns a LiveMapView
    )
    await coco.mount_each(process_file, files.items(), outdir)

app = coco.App(coco.AppConfig(name="FilesTransform"), app_main, sourcedir=..., outdir=...)
app.update_blocking(live=True)
```

</Fragment>
<Fragment slot="rust">

```rust
async fn index(ctx: Ctx, sourcedir: PathBuf) -> Result<()> {
    // ...
    // The source supports live watch; pass `-L` to `cocoindex update` to run live.
    let files = walk_dir(sourcedir)
        .recursive(true)
        .path_matcher(PatternFilePathMatcher::include(["**/*.md"])?)
        .live()
        .poll_interval(Duration::from_secs(1));
    ctx.mount_each_live(&"process_file", files, move |ctx, file: FileEntry| {
        let target_table = target_table.clone();
        async move { process_file(&ctx, &file, &target_table).await }
    })
    .await
}
```

`walk_dir(..).live()` needs the `fs_live` feature. It follows the directory with the platform's native file events (each event updates or removes one file's component), polls at `poll_interval` where those are unavailable, and walks the whole directory every `rescan_interval` (an hour by default) as a safety net.

</Fragment>
</LangTabs>

**Catch-up compatibility:** `LiveMapView` sources also work in catch-up mode — they do the initial full scan and exit cleanly. You can write your pipeline once and choose catch-up or live at run time.

### `kafka` — consuming a topic with `LiveMapView`

The [`kafka`](../connectors/kafka) connector treats a topic as a live keyed map — each message is an upsert or delete for a key. `kafka::topic_as_map` returns a `LiveMapView`: its scan reads every partition up to its high-watermark, keeping the latest message per key, and its watch tails new records from there. With a consumer group, a live run resumes from the committed offsets instead of scanning:

</Lang>

{/* Rust: examples/rust/kafka_consume/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
from confluent_kafka.aio import AIOConsumer
from cocoindex.connectors import kafka

@coco.fn
async def app_main() -> None:
    consumer = AIOConsumer({
        "bootstrap.servers": "localhost:9092",
        "group.id": "my-group",
        "enable.auto.commit": "false",
    })
    items = kafka.topic_as_map(consumer, "my-topic")
    await coco.mount_each(process_message, items)

app = coco.App(coco.AppConfig(name="KafkaConsumer"), app_main)
app.update_blocking(live=True)
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::connectors::kafka::{self, KafkaMessage};

let consumer = kafka::KafkaConsumer::connect_with_options(
    &broker_refs,

    },

.await?;

        Ok(())
    }
})
.await
```

## Going deeper

The abstractions behind live mode, from most general to most specific:

<Lang only="python">

- **[LiveComponent](../advanced_topics/live_component)** — the underlying protocol for components that react to changes incrementally. Most flexible — full control over the lifecycle.
- **[LiveMapFeed / LiveMapView](../advanced_topics/live_component#livemapfeed-and-livemapview)** — represents a changing collection of keyed items. `mount_each()` uses it to construct a `LiveComponent` automatically. Connector authors implement this to add live support.
- **[`coco.auto_refresh`](../advanced_topics/live_component#example-periodic-refresh-with-cocoauto_refresh)** — wraps a regular processor function as a `LiveComponent` that re-runs on a fixed interval. Use when there's no change-event source.
- **Source connectors** — provide `LiveMapView` (e.g., [`localfs`](../connectors/localfs)) or `LiveMapFeed` (e.g., [`kafka`](../connectors/kafka)) from their source APIs. Users just pass the result to `mount_each()`.

</Lang>

<Lang only="rust">

- **[LiveComponent](../advanced_topics/live_component)** — the trait for components that react to changes incrementally, mounted with `ctx.mount_live`. Most flexible — full control over the lifecycle.
- **[LiveMapFeed / LiveMapView](../advanced_topics/live_component#livemapfeed-and-livemapview)** — traits for a changing collection of keyed items. `ctx.mount_each_live` uses a `LiveMapView` to construct a `LiveComponent` automatically. Connector authors implement them to add live support.
- **[`ctx.auto_refresh`](../advanced_topics/live_component#example-periodic-refresh-with-cocoauto_refresh)** — mounts a regular processing body as a `LiveComponent` that re-runs on a fixed interval. Use when there's no change-event source.
- **Source connectors** — provide a `LiveMapView` from their source APIs (e.g., `walk_dir(..).live()` in [`localfs`](../connectors/localfs), `kafka::topic_as_map` in [`kafka`](../connectors/kafka), `iggy::topic_as_map` in [`iggy`](../connectors/iggy)). Users just pass the result to `ctx.mount_each_live()`.

</Lang>

For custom change feeds, fine-grained lifecycle control, or implementing live map <Lang only="python">protocols</Lang><Lang only="rust">traits</Lang> on your own connector, see [Live Components](../advanced_topics/live_component).
