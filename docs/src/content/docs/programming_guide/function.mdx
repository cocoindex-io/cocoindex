It's common to factor work into helper functions (for parsing, chunking, embedding, formatting, etc.). In CocoIndex, you can mark any function with <Lang only="python">`@coco.fn`</Lang><Lang only="rust">`#[cocoindex::function]`</Lang> when you want to add incremental capabilities to it. The marked function is still a normal function: its signature stays the same, and you can call it normally.

<LangTabs>
<Fragment slot="python">

```python
@coco.fn
async def process_file(file: FileLike) -> str:
    return await file.read_text()

# Can be called like any normal function
result = await process_file(file)
```

</Fragment>
<Fragment slot="rust">

```rust
#[cocoindex::function]
async fn process_file(_ctx: &Ctx, file: FileEntry) -> Result<String> {
    Ok(file.content_str()?.to_string())
}

// Called like any other function, with the component's `Ctx`.
let text = process_file(&ctx, file).await?;
```

</Fragment>
</LangTabs>

<Lang only="python">

`@coco.fn` preserves the sync/async nature of the underlying function. Decorating a sync function yields a sync function; decorating an async function yields an async function.

</Lang>

<RustNote>
The Rust SDK has no sync/async adapter (`as_async`, `as_sync`): a `#[cocoindex::function]` body is an `async fn` and runs on the Tokio runtime. Rust has no ambient component context: every function takes the component's `&Ctx` as its first argument, and the macro substitutes a scoped `Ctx` for the call.

## How to think about `#[cocoindex::function]`

</Lang>

<Lang only="python">Decorating</Lang><Lang only="rust">Marking</Lang> a function tells CocoIndex that calls to it are part of the incremental update engine. You still write normal <Lang only="python">Python</Lang><Lang only="rust">Rust</Lang>, but CocoIndex can now:

- Detect when inputs or code have changed (change detection)
- Skip work when nothing has changed (memoization)

This is what lets CocoIndex avoid rerunning expensive steps on every `app.update()`. See [Processing Component](./processing_component) for how <Lang only="python">decorated</Lang><Lang only="rust">marked</Lang> functions are mounted at component paths.

If you don't need any of the above for a helper, keep it as a plain <Lang only="python">Python</Lang><Lang only="rust">Rust</Lang> function.

## Change detection and memoization

Every <Lang only="python">`@coco.fn`</Lang><Lang only="rust">`#[cocoindex::function]`</Lang> function participates in CocoIndex's change detection system. With <Lang only="python">`memo=True`</Lang><Lang only="rust">`memo`</Lang>, the function's results are cached and reused when nothing has changed. These two mechanisms (detecting changes and acting on them) work together to enable incremental updates. For the big-picture view (how memoization skips unchanged work across both input and code changes) see the [Function memoization section in Core Concepts](./core_concepts#function-memoization-skip-unchanged-computations).

:::tip[Mental model]
A function's behavior is determined by its **logic** (source code, [`deps`](#deps), [`version`](#version)), its **inputs** (arguments), and the **context values** it reads via <Lang only="python">[`use_context()`](./context#retrieving-values)</Lang><Lang only="rust">[`ctx.get_key()`](./context#retrieving-values)</Lang>. If none of those have changed, a memoized function returns its cached result without re-executing.
:::

### Change detection

CocoIndex detects three kinds of changes:

<Lang only="python">

**Logic changes** — a function's *logic* is its own source code (or, when you set [`version`](#version), that integer **instead of** the source), plus any [`deps`](#deps) values. Tracked by `@coco.fn`. Logic fingerprints **propagate transitively** up the call chain, following *runtime invocations* rather than the static call graph: every `@coco.fn` function reached during a memoized call — directly, or through plain undecorated helpers — contributes its logic to that call. So if `foo` (memoized) calls `bar` (also `@coco.fn`-decorated, with or without `memo=True`) and `bar`'s logic changes, `foo`'s memo is invalidated; undecorated helpers in between don't break the chain. What the decorator buys is having a function's *own* logic tracked: an undecorated helper is invisible to change detection, so editing it invalidates nothing. This is why `@coco.fn` matters for **any** function in the call chain, not just memoized ones — see [Common patterns](#common-patterns) and the [FAQ](../faq#how-does-logic-change-propagation-work). To stop propagation deliberately, set [`logic_tracking`](#logic_tracking) to `"self"` or `None`.

**Input changes** — the function's arguments. Tracked by `@coco.fn`. When you call a function with different arguments, the fingerprints change. Input fingerprints do not propagate transitively.

**Context changes** — [context values](./context) with [`detect_change=True`](./context#change-detection). Tracked by [`use_context()`](./context#retrieving-values) at the call site — independent of `@coco.fn`. Context reads propagate transitively: if a memoized `foo` calls `bar` and `bar` reads a change-detected context value, then changing that value invalidates `foo`'s memo too — even though `foo` itself never called `use_context()`. What matters is whether the key was read *anywhere* during the memoized call, not where in the call chain.

</Lang>

<Lang only="rust">

**Logic changes** — a function's *logic* is its own body (or, when you set [`version`](#version), that integer **instead of** the body), plus any [`deps`](#deps) value. Tracked by `#[cocoindex::function]`. Logic fingerprints **propagate transitively** up the call chain, following *runtime invocations* rather than the static call graph: every `#[cocoindex::function]` reached during a memoized call — directly, or through plain unmarked helpers that pass the `Ctx` on — contributes its logic to that call. So if `foo` (memoized) calls `bar` (also `#[cocoindex::function]`, with or without `memo`) and `bar`'s logic changes, `foo`'s memo is invalidated; unmarked helpers in between don't break the chain. What the attribute buys is having a function's *own* logic tracked: an unmarked helper is invisible to change detection, so editing it invalidates nothing. This is why `#[cocoindex::function]` matters for **any** function in the call chain, not just memoized ones — see [Common patterns](#common-patterns) and the [FAQ](../faq#how-does-logic-change-propagation-work). To stop propagation deliberately, set [`logic_tracking`](#logic_tracking) to `"self"` or `"none"`.

**Input changes** — the function's arguments. Tracked by `#[cocoindex::function]`. When you call a function with different arguments, the fingerprints change. Input fingerprints do not propagate transitively.

**Context changes** — [context values](./context) whose key is declared with [`detect_change`](./context#change-detection). Tracked by [`ctx.get_key()`](./context#retrieving-values) at the call site — independent of `#[cocoindex::function]`. Context reads propagate transitively: if a memoized `foo` calls `bar` and `bar` reads a change-detected context value, then changing that value invalidates `foo`'s memo too — even though `foo` itself never called `get_key()`. What matters is whether the key was read *anywhere* during the memoized call, not where in the call chain.

</Lang>

### Memoization

With <Lang only="python">`memo=True`</Lang><Lang only="rust">`memo`</Lang>, the function's result is cached. On subsequent calls, if no logic, input, or read context values have changed, the cached result is reused without executing the function body — it carries over [target states](./target_state) declared during the function's previous invocation and returns its previous return value.

{/* Rust: rust/sdk/SHOWCASE.md "Define functions", verified against rust/sdk/cocoindex/tests/memo_deps.rs */}

```python
@coco.fn(memo=True)
def process_chunk(chunk: Chunk) -> list[float]:
    # This computation is skipped if chunk, logic, and context are unchanged
    return embed(chunk.text)
```

Without a type annotation, cached values may deserialize as basic Python types (`dict`, `list`, etc.) instead of their original types. See [Serialization](./serialization) for details on supported types.

:::caution[`memo=True` constraints]
A memoized function:

- **Must run inside a [processing component](./processing_component)** for memoization to take effect. Outside a component context (e.g., invoked from a script or a test), the function still executes correctly but the cache is bypassed silently — every call runs the body.
- **Cannot mount child components when called directly** (`coco.mount(...)` / `coco.use_mount(...)` inside the body of a memoized function invoked as a plain call). Mounting is a side effect the call's cache cannot replay; CocoIndex raises an error if a directly-called memoized function attempts it. The restriction applies to the call, not the function — the fix, which the error message itself suggests, is to **mount the memoized function as a component**: a [memoized component](./processing_component#memoized-components) may mount children freely (a cache hit carries its child mounts over along with its target states). Alternatively, drop `memo=True`, or restructure so the mount happens in a non-memoized caller.
:::

</Lang>

- **Cannot mount child components when called directly** (`mount!`, `use_mount!` or `ctx.scope(..)` inside the body of a memoized function invoked as a plain call). #### Cache-hit semantics

When a memoized function's cache hits, its **body does not run** — and neither do any nested <Lang only="python">`@coco.fn`</Lang><Lang only="rust">`#[cocoindex::function]`</Lang> calls inside it. The cached output is replayed directly: the previous return value is returned, and any target states the function declared on its previous run are carried over.

{/* Rust: rust/sdk/cocoindex/tests/pipeline.rs (`read_version`, `outer_read_version`) */}

<Fragment slot="python">

The fragment below omits the enclosing `App` and processing component. Treat the calls as invocations of the same processing component across successive application updates.

```python
@coco.fn(memo=True)
async def inner(text: str) -> str:
    print("inner ran")
    return await call_llm(text)

@coco.fn(memo=True)
async def outer(text: str) -> str:
    print("outer ran")
    return await inner(text) + "!"

# First component update: both print, both bodies execute.
result = await outer("hello")

# Later component update with the same input: nothing prints. The cached value
# from outer is returned directly, and inner is not invoked at all.
result = await outer("hello")
```

</Fragment>
<Fragment slot="rust">

```rust
static OUTER_CALLS: AtomicUsize = AtomicUsize::new(0);
static INNER_CALLS: AtomicUsize = AtomicUsize::new(0);

#[cocoindex::function(memo)]
async fn read_version(ctx: &Ctx) -> Result<String> {
    INNER_CALLS.fetch_add(1, Ordering::SeqCst);
    Ok(ctx.get_key(version_key())?.clone())
}

#[cocoindex::function(memo)]
async fn outer_read_version(ctx: &Ctx) -> Result<String> {
    OUTER_CALLS.fetch_add(1, Ordering::SeqCst);
    read_version(ctx).await
}

// First update: both bodies run (OUTER_CALLS == 1, INNER_CALLS == 1).
// Second update with the same context value: neither counter moves —
// outer's cached value is returned directly, and read_version is not invoked.
```

</Fragment>
</LangTabs>

Propagation (logic, `deps`, context) is recorded during the **previous** invocation and replayed on cache lookup. You don't need to model the internals — change anything that affects behavior and the cache invalidates correctly.

<Lang only="python">

:::note[Exceptions and the cache]
If a memoized function raises, no cache entry is written for that call. The next invocation with the same inputs sees a cache miss and re-executes the body — exceptions never poison the cache, so you don't need to wrap calls defensively.
:::

</Lang>

If a memoized function returns an `Err`, no cache entry is written for that call. The next invocation with the same inputs sees a cache miss and re-executes the body — errors never poison the cache, so you don't need to wrap calls defensively.

#### When to memoize

**Cost:** A directly-called memoized function's cache entry must store everything needed to serve a hit — the return value, plus the *path* of every [target state](./target_state) it declared during the call (the state values themselves stay in the enclosing component's tracking; the recorded paths are what keep those states alive on a hit). Large return values, or a call that declares many target states, mean large entries. (A function *mounted* as a component avoids the per-state paths entirely: a [memoized component](./processing_component#memoized-components)'s entry holds fingerprints plus its return value — <Lang only="python">`None`</Lang><Lang only="rust">`()`</Lang> for a typical mounted declarer.)

**Benefit:** Memoization saves more when:

- The computation is expensive
- The function's caller is reprocessed frequently (due to logic or input changes)

**Placement:** memoize at a boundary only if its key can hit while every *enclosing* memo boundary misses. Stacked levels pay off exactly when the outer boundary is keyed more coarsely than the inner one's inputs. A per-file component plus a per-chunk embedding memo composes well: an edited file re-runs its component while its unchanged chunks still skip embedding.

If an enclosing *memoized* component's identity already commits to this function's inputs (for example, the component path is keyed by a hash of the content the function transforms), the inner memo can never hit on a *content-driven* rerun. The component memo already covers those cases. The inner memo can still help when the enclosing component re-runs because its code changed or its `version` was bumped. Each entry permanently stores a value, often one the target also stores, for those reruns.

A 1536-dim float32 vector is ~6 KB. An embedding memo under content-hash-keyed components therefore stores ~600 MB per 100k chunks to cover those rare reruns. Consider that storage cost when deciding whether to keep the inner memo.

**Examples:**

- ✅ **Embedding functions** — good to memoize when callers can re-run with the same text (e.g., per-file components re-running on edits). Computation is heavy; return value is fixed-size and not too large.
- ❌ **Splitting text into fixed-size chunks** — usually not worth memoizing. Computation is light; return value can be large.
- ✅ **Processing component for files that are mostly stable between runs** — memoization skips unchanged files, saving the cost of reading and processing their contents.
- 🤔 **Chunk embedding when file-level memoization is already enabled** — still beneficial, but less so for stable files. The benefit increases for files that change frequently, or when your code evolves (e.g., adding more features per file triggers file-level reprocessing, but unchanged chunks can still skip embedding).
- ❌ **Chunk embedding inside a *memoized* component keyed by the chunk's content hash** — usually redundant by the placement rule: the component memo already commits to the text, so the inner memo serves only reruns caused by the component's own code or `version` changes — at the cost of storing every vector twice.

### Controlling change detection scope

Three <Lang only="python">parameters on `@coco.fn`</Lang><Lang only="rust">arguments of `#[cocoindex::function]`</Lang> let you customize how logic changes are detected:

- **`logic_tracking`** — controls the *scope* of automatic logic change detection
- **`version`** — provides explicit manual control over when dependent memos are invalidated
- **`deps`** — declares external values (e.g. a <Lang only="python">module-level prompt string</Lang><Lang only="rust">prompt `const`</Lang>) as part of the function's logic, so changing them invalidates dependent memos

These <Lang only="python">parameters</Lang><Lang only="rust">arguments</Lang> control logic fingerprinting. Data fingerprinting (for arguments, `deps` values, and context values) is controlled by the objects themselves (see [Memoization Keys & States](../advanced_topics/memoization_keys)). Three more tools cover what <Lang only="python">a decorator parameter</Lang><Lang only="rust">an attribute argument</Lang> cannot: <Lang only="python">[`coco.LogicDep` / `coco.use_logic_dep`](#per-call-dependencies-logicdep-and-use_logic_dep)</Lang><Lang only="rust">[`LogicDep` / `ctx.use_logic_dep`](#per-call-dependencies-logicdep-and-use_logic_dep)</Lang> for a dependency decided per call, <Lang only="python">[`coco.DataDep` / `coco.use_data_dep`](#data-dependencies-datadep-and-use_data_dep)</Lang><Lang only="rust">[`DataDep` / `ctx.use_data_dep`](#data-dependencies-datadep-and-use_data_dep)</Lang> for data a body reads that is not among its arguments, and <Lang only="python">[`coco.logic_propagated_to_callers`](#callbacks-logic_propagated_to_callers)</Lang><Lang only="rust">[`ctx.logic_propagated_to_callers`](#callbacks-logic_propagated_to_callers)</Lang> for callbacks that cross a `"self"` boundary.

#### `logic_tracking`

The `logic_tracking` <Lang only="python">parameter</Lang><Lang only="rust">argument</Lang> controls whether and how logic changes are detected:

- **`"full"` (default):** Track this function's logic AND all transitively called <Lang only="python">`@coco.fn`</Lang><Lang only="rust">`#[cocoindex::function]`</Lang> functions' logic. A change anywhere in the call chain invalidates dependent memos.
- **`"self"`:** Track only this function's own logic — its fingerprint still propagates to its callers, but the logic of functions it calls does not propagate through it.
- **<Lang only="python">`None`</Lang><Lang only="rust">`"none"`</Lang>:** Don't track logic through this function at all — neither its own logic nor its callees' reaches its callers.

These settings govern nested *function calls*. A [mounted child component](./processing_component) is tracked through the component tree instead, so its logic reaches the parent regardless of the parent's `logic_tracking`.

:::caution[Adopting tracking later does not re-store existing memo entries]
A memo entry records only the logic fingerprints its writer offered when it was stored. <Lang only="python">Decorating a function with `@coco.fn`</Lang><Lang only="rust">Marking a function with `#[cocoindex::function]`</Lang> after memoized callers have stored entries that ran it, or raising its `logic_tracking` from <Lang only="python">`None`</Lang><Lang only="rust">`"none"`</Lang>, leaves those entries valid: nothing in them can fail. Ship such a change together with a [`version`](#version) bump or a memoization-key change on the memoized callers, so their entries are stored again with the new fingerprints.
:::

#### `deps`

A recorded dependency travels exactly like the function's own fingerprint: into the entry of a memoized caller, onward through `"full"` callers, hidden by a `"self"` caller above unless the call is carried by [`logic_propagated_to_callers`](#callbacks-logic_propagated_to_callers), and from a [mounted component](./processing_component) into every ancestor component's entry. When a later release constructs the `LogicDep` with a new value, only the entries that recorded the old one are invalidated: in the example, a parser's new version re-runs its files and the directories above them, and every other subtree is reused. It is recorded whatever the function's own `logic_tracking` is: it describes the call, not the function's code.

The rules for an entry that recorded data dependencies:

- The entry is reused only when its arguments, logic and context match **and** every record validates. A record whose kind is no longer registered, or whose stored key or state no longer deserializes, is a logged miss; a validator's <Lang only="python">exception propagates</Lang><Lang only="rust">error propagates</Lang>. A changed-but-valid state is refreshed without a run. On a miss the body's new records replace the stored set.
- A record rides up through every enclosing function frame regardless of `logic_tracking`, into every enclosing memoized function's entry and the component's entry, where it stops. Records are **not** copied into ancestor components' entries. A component reports one bit upward instead, and its parent's entry lists the children that reported it: **a component is skipped only if its own entry validates and every descendant that recorded data dependencies validates too**, which the parent's probe checks from those descendants' own stored entries, by path, without mounting them. A changed-but-valid descendant record is refreshed in place. The probe stops, and the body re-runs, at a listed descendant with no entry (a non-memoized one, whose records are dropped, or one whose last run observed a key in two states), a record that no longer decodes, a kind no longer registered, or a validator answering invalid. Closed descendants are carried over by the reuse unvalidated, as they always were. A component that records nothing is unaffected.
- Because a parent's probe may validate a record while the component that recorded it is not mounted, a validator runs with no component context and must depend on its key and stored state alone.
- <Lang only="python">`use_data_dep` raises outside a component context, and when the current frame has already closed. #### Callbacks: `logic_propagated_to_callers`

<Lang only="python">

`logic_tracking` is per function, so `"self"` hides the logic of *everything* a function calls — including callbacks it received as arguments. A library whose `accept` is `logic_tracking="self"` therefore hides the user's `visit_file`: an edit to `visit_file` invalidates nothing, even though it is the user's input, not the library's implementation detail.

`coco.logic_propagated_to_callers(fn)` closes this gap. It is library-side; the user only puts `@coco.fn` on the callback. It does not make `fn` tracked: `fn`'s own `@coco.fn` and `logic_tracking` decide what it offers, exactly as for any function. The wrapper only carries that up to the frame that called it, through layers that would otherwise drop it. (`coco.logic_tracked` is the former name; it still works and emits a `DeprecationWarning`.)

</Lang>

### Debugging unexpected re-runs

If a memoized function is re-running when you expect a cache hit, walk through the inputs in order:

1. **Logic** — did the function's source code change? Did any <Lang only="python">`@coco.fn`</Lang><Lang only="rust">`#[cocoindex::function]`</Lang> it transitively calls change? Was a `version` bumped? Was a `deps` value edited?
2. **Inputs** — are the arguments byte-identical to the previous call (after canonicalization)? Custom types with unstable equality are a common source of spurious invalidation — see [Memoization Keys & States](../advanced_topics/memoization_keys).
3. **Context** — did any <Lang only="python">[`detect_change=True`](./context#change-detection)</Lang><Lang only="rust">[`detect_change`](./context#change-detection)</Lang> context value read during the previous invocation change? Remember this propagates transitively through nested <Lang only="python">`@coco.fn`</Lang><Lang only="rust">`#[cocoindex::function]`</Lang> calls.

If none of those changed and the function still re-runs, the most common cause is a non-stable fingerprint on a custom-typed argument or context value — <Lang only="python">define `__coco_memo_key__` to make it deterministic</Lang><Lang only="rust">derive `MemoInput`, or implement it by hand over the fields that identify the value, to make it deterministic</Lang>.

Conversely, if a memo is hitting when you expect invalidation, common causes are:

<Lang only="python">

- A logic change in a helper that is **not** decorated with `@coco.fn`. Add `@coco.fn` to it (no `memo=` needed) so its logic participates in propagation — see [Common patterns](#common-patterns).
- A `deps` value that you changed at runtime: `deps` is [snapshotted at decoration time](#deps), so per-instance or per-request values must be passed as regular arguments instead.
- The function uses [`logic_tracking=None`](#logic_tracking), which opts it out of code-change detection entirely.
- The change is in a callback that passes through a `logic_tracking="self"` function and nobody wrapped it with [`coco.logic_propagated_to_callers`](#callbacks-logic_propagated_to_callers).

</Lang>

<Lang only="rust">

- A logic change in a helper that is **not** marked with `#[cocoindex::function]`. Add the attribute to it (no `memo` needed) so its logic participates in propagation — see [Common patterns](#common-patterns).
- A `deps` value that you changed at runtime: `deps` is [fingerprinted once per process](#deps), so per-request values must be passed as regular arguments instead.
- The function uses [`logic_tracking = "none"`](#logic_tracking), which opts it out of code-change detection entirely.
- The change is in a callback that passes through a `logic_tracking = "self"` function and nobody wrapped it with [`ctx.logic_propagated_to_callers`](#callbacks-logic_propagated_to_callers).

### Customizing data fingerprinting

<Lang only="python">

By default, CocoIndex fingerprints function arguments, `deps` values, and context values automatically for most types — primitives, containers, dataclasses, Pydantic models, and picklable objects. For custom types, or when you need multi-level validation (e.g., check mtime first, then content hash), see [Memoization Keys & States](../advanced_topics/memoization_keys).

For per-function overrides (excluding an argument from the memo key, or transforming it just for this function) pass `memo_key={...}` on `@coco.fn` / `@coco.fn.as_async`; see [Override at the call site with `memo_key=`](../advanced_topics/memoization_keys#override-at-the-call-site-with-memo_key).

</Lang>

### Async adapter

Use `@coco.fn.as_async` when you need an **async** interface for a function that has a sync underlying implementation. This is useful for compute-intensive leaf functions. The decorator also accepts an `async def` body as-is, and [batching](#batching) and [runner](#runner) (which need an async interface) are always enabled through it.

```python
@coco.fn.as_async
def embed(text: str) -> list[float]:
    return model.encode([text])[0]

# External usage: always async, even though the function body is sync
embedding = await embed("hello world")
```

`@coco.fn.as_async` is equivalent to wrapping the function in `asyncio.to_thread()` — the sync function runs on a thread pool and doesn't block the event loop.

You can also call any `@coco.fn`-decorated function asynchronously via the `.as_async()` method, without changing its primary signature:

```python
@coco.fn
def expensive_fn(data: bytes) -> bytes:
    return process(data)

# Primary call is sync:
result = expensive_fn(data)

# Async call via .as_async():
result = await expensive_fn.as_async(data)
```

</Lang>

### Batching

With <Lang only="python">`batching=True`</Lang><Lang only="rust">`batching`</Lang>, multiple concurrent calls to the function are automatically batched together. This is useful for operations that are more efficient when processing multiple inputs at once, such as embedding models.

<Lang only="python">

Batching requires an async interface, so it is always enabled with `@coco.fn.as_async(batching=True)`, whether the body is a plain `def` or an `async def`. `@coco.fn(batching=True)` is not supported: it raises `ValueError` when the decorator is applied, whichever kind of body it is given.

When batching is enabled:

- The function implementation receives a `list[T]` and returns a `list[R]`
- The external signature becomes `async T -> R` (single input, single output)
- Concurrent calls are collected and processed together
- The implementation runs outside the calling components — see [Context values in a batched body](#context-values-in-a-batched-body)

</Lang>

<Lang only="rust">

When batching is enabled:

- The function body receives a `Vec<T>` and returns a `Vec<R>`
- The generated function takes one `T` and returns one `R` (single input, single output)
- Concurrent calls are collected and processed together
- With `memo`, a cache hit is served per item and only misses enter a batch

</Lang>

{/* Rust: rust/sdk/SHOWCASE.md "Batch item-shaped calls", verified against rust/sdk/cocoindex_macros/src/lib.rs and rust/sdk/cocoindex/tests/batching_runner.rs */}
<LangTabs>
<Fragment slot="python">

```python
@coco.fn.as_async(batching=True, max_batch_size=32)
def embed(texts: list[str]) -> list[list[float]]:
    # Called with a batch of texts, returns a batch of embeddings
    return model.encode(texts)

# External usage: async, single input, single output
embedding = await embed("hello world")  # Returns list[float]

# Concurrent calls are automatically batched using asyncio.gather
embeddings = await asyncio.gather(
    embed("text1"),
    embed("text2"),
    embed("text3"),
)
```

</Fragment>
<Fragment slot="rust">

```rust
#[cocoindex::function(memo, batching, max_batch_size = 64)]
async fn embed_batch(
    ctx: &Ctx,
    texts: Vec<String>,
    model: String,
) -> Result<Vec<Vec<f32>>> {
    ctx.get_key(&EMBEDDING_CLIENT)?.embed(texts, &model).await
}

// External usage: one input, one output.
let embedding: Vec<f32> = embed_batch(&ctx, text, model).await?;

// Concurrent calls are batched: `ctx.map` runs one call per item.
let embeddings = ctx
    .map(texts, {
        let ctx = ctx.clone();
        move |text| {
            let ctx = ctx.clone();
            let model = model.clone();
            async move { embed_batch(&ctx, text, model).await }
        }
    })
    .await?;
```

The `max_batch_size` <Lang only="python">parameter</Lang><Lang only="rust">argument</Lang> limits how many inputs can be processed in a single batch.

<Lang only="rust">

A batching function must not call itself from its own body: that waits on the batcher which is already running the body.

</Lang>

<RustNote>
The attribute has no `max_in_flight` or `rate_limiter` argument. Its batching arguments are `batching`, `max_batch_size` and `runner`.
</RustNote>

<Lang only="python">

The `max_in_flight` parameter bounds how many batches run at once. By default (`None`), a full batch starts as soon as it fills, and the next partial batch starts only once every running batch has finished. With `max_in_flight=n`, at most `n` batches run concurrently, and whenever one finishes the next pending batch (full or partial) starts, so a slow batch no longer holds back the rest:

```python
@coco.fn.as_async(batching=True, max_batch_size=32, max_in_flight=4)
async def embed(texts: list[str]) -> list[list[float]]:
    return await client.embed(texts)
```

</Lang>

#### Pacing batches with a rate limiter

<Lang only="rust">

When each batch is one request against a quota, take a token from a shared [`RateLimiter`](../common_resources/rate_limiting) at the top of the batching body, with `limiter.acquire(1).await?`. One token then pays for one batch rather than one call.

</Lang>

<Lang only="python">

When each batch is one request against a quota, pass the quota's [`RateLimiter`](../common_resources/rate_limiting) as `rate_limiter`. Every batch takes one token before it runs, so a token pays for one batch rather than one call, and the batch boundary becomes the moment a request can be sent:

- No call runs on its own: calls join the open batch, and a pump runs the oldest pending batch once a `max_in_flight` slot and a token are available. Under a scarce quota, every call that arrives while the pump waits for the token rides the next batch.
- With tokens to spare, a batch goes out at once and the next one fills during its round trip (under `max_in_flight`, when set). The burst allowance of the limiter is how many requests may go out unbatched after an idle stretch.
- Requests the body makes beyond the batch's own — a retry, a per-item fallback — take their own tokens from the same limiter.

For a method whose limiter lives on the instance, pass a callable that receives `self` and returns the limiter (or `None` for no pacing); it is resolved once per batcher, which is already keyed by `self`:

```python
class Client:
    def __init__(self, limiter: RateLimiter) -> None:
        self._limiter = limiter

    @coco.fn.as_async(
        batching=True, max_batch_size=100, rate_limiter=lambda self: self._limiter
    )
    async def fetch(self, ids: list[str]) -> list[Item]:
        return await self._api.fetch_many(ids)  # one request, one token
```

</Lang>

<Lang only="python">

#### Context values in a batched body

One batch merges calls from many components, so the body runs outside any of them: `coco.use_context(...)` inside a `batching=True` body raises `RuntimeError: No ComponentContext available`. Resolve context values in the caller — a `@coco.fn` function or method running inside the component — and pass them to the batched function as extra arguments:

```python
EMBED_CLIENT = coco.ContextKey[EmbedClient]("embed_client")

@coco.fn.as_async(batching=True, max_batch_size=64)
async def _embed_batch(texts: list[str], client: EmbedClient) -> list[list[float]]:
    return await client.embed(texts)

@coco.fn
async def embed(text: str) -> list[float]:
    client = coco.use_context(EMBED_CLIENT)  # inside the component
    return await _embed_batch(text, client)
```

Only the first parameter is batched. Every other argument is passed through to the body unchanged and is part of the key that selects the batcher (so is `self`, for methods): calls share a batcher only when these arguments compare equal, which also means they must be hashable. Pass them the same way on every call. An explicit value and the default, or the same value given positionally and by keyword, select different batchers, and the calls are never batched together.

</Lang>

<Lang only="rust">

#### Context values and extra parameters in a batched body

A batching body receives a `Ctx`, so `ctx.get_key(&KEY)?` works inside it, as in the `embed_batch` example above. The engine joins the dependencies the body reads into every caller's memo entry.

The parameter after the `&Ctx` is the batched one. Every other parameter is passed through to the body unchanged and must implement `Serialize`: its serialized value selects the batcher, so calls share a batch only when these values are equal. With `memo`, each must also implement `MemoInput`, unless `memo_key(..)` transforms or skips it.

</Lang>

#### Retrying a failed batch as smaller batches

Some batch failures depend on the batch's composition rather than any single input — e.g. a provider's per-request token or payload limit, or one input the provider rejects. No fixed `max_batch_size` can rule these out. <Lang only="python">When the function body hits such a failure, raise `coco.RetryWithSmallerBatch` from it: CocoIndex halves the batch and retries each half, recursing down to single items. At size 1, the wrapped original error is raised as that item's own failure — so one bad input fails only its own caller, while the rest of the batch still succeeds. There is no need to check the batch size before raising: at size 1 the engine simply unwraps the signal and raises the original error.</Lang><Lang only="rust">When the function body hits such a failure, return `Error::retry_with_smaller_batch(cause)` from it: CocoIndex halves the batch and retries each half, recursing down to single items. At size 1, `cause` becomes that item's own failure — so one bad input fails only its own caller, while the rest of the batch still succeeds. There is no need to check the batch size before returning it: at size 1 the engine simply unwraps the signal and fails that caller with `cause`.</Lang>

{/* Rust: rust/sdk/SHOWCASE.md "Batch item-shaped calls", verified against rust/sdk/cocoindex/tests/batching_runner.rs (`Error::retry_with_smaller_batch`) */}

```python
@coco.fn.as_async(batching=True, max_batch_size=64)
async def embed(texts: list[str]) -> list[list[float]]:
    try:
        return await provider.embed(texts)
    except ProviderError as e:
        if is_transient(e) or is_auth_error(e):
            raise  # retrying smaller can't help these
        raise coco.RetryWithSmallerBatch() from e
```

```rust

async fn embed_batch(ctx: &Ctx, texts: Vec<String>) -> Result<Vec<Vec<f32>>> {
    let client = ctx.get_key(&EMBEDDING_CLIENT)?;
    client
        .embed(&texts)
        .await
        .map_err(|err| Error::retry_with_smaller_batch(Error::user(err)))

```

</Fragment>

<Lang only="python">Raising it</Lang><Lang only="rust">Returning it</Lang> is safe for *any* deterministic batch failure, even when you can't tell whether the batch size was the cause: if the error was actually global (it would fail at any size), the recursion terminates at single items and every caller receives the underlying error, at the bounded cost of extra attempts. Only propagate directly for errors where splitting provably can't help — global errors like invalid credentials, and transient errors (rate limits, network blips) that haven't yet been retried at the same size. Once same-size retries are exhausted, splitting is a reasonable last resort: a smaller request may pass where the large one timed out.

:::tip[When to use batching]

Batching is beneficial when:

- The underlying operation has significant per-call overhead (e.g., GPU kernel launch)
- The operation can process multiple inputs more efficiently than one at a time
- You have concurrent calls from multiple <Lang only="python">coroutines</Lang><Lang only="rust">tasks</Lang>

Common use cases:

- **Embedding models** — most embedding APIs and models are optimized for batch processing
- **LLM inference** — batch multiple prompts together for better GPU utilization
- **Database operations** — batch inserts or lookups

:::

### Runner

The `runner` <Lang only="python">parameter</Lang><Lang only="rust">argument</Lang> allows functions to execute in a specific context, such as a dedicated GPU runner that serializes GPU workloads.

<Lang only="python">

Like batching, a runner requires an async interface, so it is always set with `@coco.fn.as_async(runner=...)`, on a plain `def` or an `async def` body. `@coco.fn(runner=...)` raises `ValueError` when applied.

</Lang>

{/* Rust: rust/sdk/cocoindex/tests/batching_runner.rs (`runner = GPU`, `GPURunner::fraction`) */}
<LangTabs>
<Fragment slot="python">

```python
@coco.fn.as_async(runner=coco.GPU)
def gpu_inference(data: bytes) -> bytes:
    # Runs with GPU serialization
    return model.predict(data)

# External usage: async
result = await gpu_inference(data)
```

</Fragment>
<Fragment slot="rust">

```rust
#[cocoindex::function(runner = cocoindex::GPU)]
async fn whole_gpu(_ctx: &Ctx, item: i64) -> Result<i64> {
    // Runs while holding one whole GPU; `current_gpu()` names it.
    let device = cocoindex::current_gpu();
    // ...
}

#[cocoindex::function(memo, runner = GPURunner::fraction(0.5))]
async fn half_gpu(_ctx: &Ctx, item: i64) -> Result<i64> {
    // Two calls share one GPU.
    // ...
}

// External usage: async
let result = whole_gpu(&ctx, item).await?;
```

</Fragment>
</LangTabs>

<Lang only="python">

The `coco.GPU` runner:

- By default, runs in-process with all functions sharing a queue for serial execution
- Sync functions run on a dedicated GPU thread to avoid blocking the event loop
- Set the environment variable `COCOINDEX_RUN_GPU_IN_SUBPROCESS=1` to run in a subprocess for GPU memory isolation

</Lang>

<Lang only="rust">

`runner = <expr>` takes a value of any type that implements `cocoindex::Runner`; it is built on the function's first call and shared by every call. The GPU runners draw from a process-wide GPU pool:

- `cocoindex::GPU` takes a whole GPU per call (or per physical batch, with `batching`), so bodies on one GPU run one at a time
- `GPURunner::fraction(f)` takes a share, so several calls run at once on one GPU
- Inside the body, `current_gpu()`, `current_gpus()` and `current_gpu_fraction()` report the assignment
- The pool size comes from `COCOINDEX_NUM_GPUS`, `CUDA_VISIBLE_DEVICES` or `nvidia-smi` (one GPU by default); `configure_gpu_pool(n)` overrides it before the first GPU function runs

A runner of your own implements `cocoindex::Runner`: it receives each body as a future and decides when to run it.

{/* Rust: rust/sdk/SHOWCASE.md "Run on a GPU" (`AtMostTwo`), verified against rust/sdk/cocoindex/src/runner.rs */}
```rust
struct AtMostTwo(tokio::sync::Semaphore);

#[async_trait::async_trait]
impl cocoindex::Runner for AtMostTwo {
    async fn run(&self, body: cocoindex::RunnerBody<'_>) -> Result<cocoindex::RunnerOutput> {
        let _permit = self.0.acquire().await.map_err(|e| Error::engine(e.to_string()))?;
        body.await
    }
}

#[cocoindex::function(memo, runner = AtMostTwo(tokio::sync::Semaphore::new(2)))]
async fn summarize(_ctx: &Ctx, text: String) -> Result<String> { /* ... */ }
```

</Lang>

Python's GPU subprocess mode (`COCOINDEX_RUN_GPU_IN_SUBPROCESS`) and its dedicated GPU thread exist for the GIL and CUDA's fork rules. A Rust body runs on the Tokio runtime and has neither problem, so there is no equivalent.
</RustNote>
