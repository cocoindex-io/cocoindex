An **App** is the top-level runnable unit in CocoIndex.
<Lang only="python">It names your pipeline and binds a main function with its parameters. When you call `app.update()`, CocoIndex runs that main function as the root [processing component](./processing_component) which can mount child processing components to do work and declare target states.</Lang><Lang only="rust">It names your pipeline and owns its state. When you call `app.run(app_main)` or `app.update(app_main)`, CocoIndex runs the main function as the root [processing component](./processing_component) which can mount child processing components to do work and declare target states.</Lang>

## Creating an app

<Lang only="python">

To create an App, provide:

1. **An `AppConfig`** (or just a name string) — identifies the pipeline
2. **A main function** — the entry point for your pipeline
3. **Arguments** — any additional arguments to pass to the main function

</Lang>

<Lang only="rust">

To create an App, provide:

1. **A main function** marked `#[cocoindex::app]` — the entry point for your pipeline
2. **A name** — identifies the pipeline; the function name unless you pass `name = "..."`

</Lang>

{/* Rust: examples/rust/text_embedding/src/main.rs, rust/sdk/SHOWCASE.md "Run apps with the `cocoindex` CLI" */}
<LangTabs>
<Fragment slot="python">

```python
import cocoindex as coco

@coco.fn
async def app_main(sourcedir: pathlib.Path) -> None:
    # ... your pipeline logic ...

app = coco.App(
    coco.AppConfig(name="MyPipeline"),
    app_main,
    sourcedir=pathlib.Path("./data"),
)
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::prelude::*;

#[cocoindex::app(name = "MyPipeline")]
async fn app_main(ctx: Ctx) -> Result<()> {
    index(ctx, source_dir()).await
}

async fn index(ctx: Ctx, sourcedir: PathBuf) -> Result<()> {
    // ... your pipeline logic ...
    Ok(())
}
```

The main function takes the root component's `Ctx` by value and returns a `Result`. `#[cocoindex::app]` registers it under its name, so `Environment::from_registered` and the [`cocoindex` CLI](#managing-apps-with-cli) find it.

</Fragment>
</LangTabs>

<Lang only="python">You can also pass just a name string instead of `AppConfig`:</Lang><Lang only="rust">Your own code opens the app by name, with the path of its state database:</Lang>

## Updating an app

<Lang only="python">Call `update()` to execute the pipeline. It returns an `UpdateHandle` that is also `Awaitable`, so the simplest usage stays the same:</Lang><Lang only="rust">Call `run()` or `update()` with the main function to execute the pipeline:</Lang>

{/* Rust: rust/sdk/SHOWCASE.md "Run apps with the `cocoindex` CLI", examples/rust/text_embedding/src/main.rs, rust/sdk/cocoindex/tests/pipeline.rs */}
<LangTabs>
<Fragment slot="python">

```python
# Async — await the result directly (backward-compatible)
result = await app.update()
```

```python
# Sync (blocking) API
result = app.update_blocking()
```

</Fragment>
<Fragment slot="rust">

```rust
// `run` returns the run's statistics.
let stats = app.run(app_main).await?;
println!("{stats}");

// `update` returns the main function's value.
let result = app.update(app_main).await?;

// Arguments travel in a closure.
let stats = app.run(move |ctx| index(ctx, dir)).await?;
```

```rust
// Sync (blocking) API, outside a Tokio runtime
let result = app.update_blocking(app_main)?;
```

</Fragment>
</LangTabs>

<Lang only="python">

**Parameters:**

- `live` option keeps the app running after the initial scan so live components can continue watching for changes. See [Live Mode](./live_mode).
- `report_to_stdout` option prints periodic progress updates during execution. Pass `True` for the default refresh interval, or a `timedelta` to set it.
- `full_reprocess` option reprocesses everything, bypassing all memoization: every component **and** every memoized function re-executes, and all target states are re-applied even if unchanged. Mind the cost — this includes every paid external call (embedding and LLM APIs re-run for all content). To force re-running just one function's work, bump its [`version`](./function#version) instead.

</Lang>

<Lang only="rust">

**Options** are the fields of `UpdateOptions`. Pass them to `app.update_with_options`, or to `app.start_update_with_options` for a handle:

- `live` keeps the app running after the initial scan so live components can continue watching for changes. See [Live Mode](./live_mode).
- `report_to_stdout` prints periodic progress updates during execution. `progress_refresh_interval` sets the refresh interval.
- `full_reprocess` reprocesses everything, bypassing all memoization: every component **and** every memoized function re-executes, and all target states are re-applied even if unchanged. Mind the cost — this includes every paid external call (embedding and LLM APIs re-run for all content). To force re-running just one function's work, bump its [`version`](./function#version) instead.
- `preview` computes the target actions without applying them.
- `timeout` bounds how long the update may run.

</Lang>

{/* Rust: rust/sdk/cocoindex/tests/fs_live.rs */}
<LangTabs>
<Fragment slot="python">

```python
handle = app.update(live=True)
await handle.result()
```

</Fragment>
<Fragment slot="rust">

```rust
let handle = app.start_update_with_options(
    UpdateOptions {
        full_reprocess: false,
        live: true,
        ..UpdateOptions::default()
    },
    app_main,
)?;
handle.result().await?;
```

`app.preview(app_main).await?` runs with `preview: true` and returns the planned `Vec<PreviewAction>` instead of applying them.

</Fragment>
</LangTabs>

When you update an App, CocoIndex:

1. <Lang only="python">Runs the lifespan setup (if not already done)</Lang><Lang only="rust">Uses the environment the lifespans configured (`Environment::from_registered` runs them before it opens the state database)</Lang>
2. Executes the main function (the root processing component), which mounts child processing components
3. Compares the declared target states with the previous run and applies only the necessary changes to external systems

Given the same logic and inputs, updates are repeatable. When logic or inputs change, only the affected parts re-execute.

<Lang only="python">To watch progress beyond the `report_to_stdout` flag, the `UpdateHandle` returned by `app.update()` also exposes stats programmatically — poll with `handle.stats()` or stream with `handle.watch()`. For those structured APIs, and for splitting a run into separately-reported scopes with `coco.stats_group()`, see [Progress monitoring](../advanced_topics/progress_monitoring).</Lang><Lang only="rust">To watch progress beyond the `report_to_stdout` option, `app.start_update(app_main)` returns an `UpdateHandle` that exposes stats programmatically: poll with `handle.stats_snapshot()`, wait for a change with `handle.changed().await`, and take the value with `handle.result().await`. See [Progress monitoring](../advanced_topics/progress_monitoring).</Lang>

## How an app runs

An App is the top-level runner and entry point. A **processing component** is the unit of incremental execution *within* an app.

- Your app's main function runs as the **root processing component** at the root path.
- <Lang only="python">Each call to `mount()` or `use_mount()` declares a **child processing component** at a child path. Sugar APIs like `mount_each()` and `mount_target()` also create child components.</Lang><Lang only="rust">Each `mount!` or `use_mount!` (or `ctx.mount`, `ctx.scope`) declares a **child processing component** at a child path. `mount_each!` and the connectors' `mount_*_target` functions also create child components.</Lang>
- Each processing component declares a set of target states, and CocoIndex syncs them as a unit when that component finishes — all writes happen after processing completes, and each target backend applies its batch atomically when supported.

This is why <Lang only="python">`app.update()`</Lang><Lang only="rust">an update</Lang> does not "run everything from scratch": CocoIndex uses the component path tree to decide what can be reused and what must re-run.

For example, an app that processes files might mount one component per file — the per-file fan-out from [Core Concepts](./core_concepts#processing-component), shown here as a path tree:

```text
(root)                         ← app_main component
└── process_file
    ├── "hello.md"             ← process_file component
    └── "world.md"             ← process_file component
```

See [Processing Component](./processing_component) for how mounting and component paths define these boundaries.

## Database path

CocoIndex needs a database path (`db_path`) to store its internal state. This database tracks target states and memoized results from previous runs, enabling CocoIndex to compute what changed and apply only the necessary updates.

The simplest way to configure the database path is via the `COCOINDEX_DB` environment variable:

```bash
export COCOINDEX_DB=./cocoindex.db
```

With `COCOINDEX_DB` set, you can create and run apps without any additional configuration<Lang only="rust"> when the environment comes from `Environment::from_registered()` or the `cocoindex` CLI</Lang>:

{/* Rust: examples/rust/text_embedding/src/main.rs; `COCOINDEX_DB` fallback verified in rust/sdk/cocoindex/src/app.rs `Environment::from_registered` */}
<LangTabs>
<Fragment slot="python">

```python
import cocoindex as coco

@coco.fn
def app_main() -> None:
    # ... your pipeline logic ...

app = coco.App("MyPipeline", app_main)
app.update_blocking()  # Uses COCOINDEX_DB for storage
```

</Fragment>
<Fragment slot="rust">

```rust
let env = Environment::from_registered().await?;  // Uses COCOINDEX_DB when no lifespan sets db_path
let app = env.app("MyPipeline").await?;
let stats = app.run(app_main).await?;
env.shutdown().await;
```

A plain `Environment::builder().build()` or `App::builder(name).build()` reads no environment variables: give it the path with `.db_path(..)`.

</Fragment>
</LangTabs>

For details on what the internal database stores and how to tune its LMDB settings (the database grows automatically; `map_size` only sets where it starts), see [Internal Storage](../advanced_topics/internal_storage).

## Lifespan (optional)

A **lifespan function** defines the CocoIndex runtime lifecycle: its setup runs when the runtime starts (<Lang only="python">automatically before the first `app.update()`</Lang><Lang only="rust">in `Environment::from_registered()`, before the state database opens</Lang>), and its cleanup runs when the runtime stops. Use it to configure CocoIndex settings programmatically or to initialize shared resources that processing components can reuse.

:::tip
If you only need to set the database path, using the `COCOINDEX_DB` environment variable is simpler than defining a lifespan function.
:::

### Defining a lifespan

<Lang only="python">Use the `@lifespan` decorator to register a lifespan function. By default, all apps share the same lifespan (unless you explicitly specify an app in a different [*Environment*](../advanced_topics/multiple_environments)). The function receives an `EnvironmentBuilder` for configuration and uses `yield` to separate setup from cleanup:</Lang><Lang only="rust">Mark an `async fn` with `#[cocoindex::lifespan]` to register a lifespan function. Every app opened from `Environment::from_registered()` shares the registered lifespans; an app opened from an `Environment` you build yourself is in a different [*Environment*](../advanced_topics/multiple_environments). The function receives an `EnvironmentBuilder`, configures it, and returns it:</Lang>

{/* Rust: examples/rust/text_embedding/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
import pathlib
from typing import AsyncIterator
import cocoindex as coco

@coco.lifespan
async def coco_lifespan(builder: coco.EnvironmentBuilder) -> AsyncIterator[None]:
    # Configure CocoIndex's internal database location (overrides COCOINDEX_DB if set)
    builder.settings.db_path = pathlib.Path("./cocoindex.db")
    # Setup: initialize resources here
    yield
    # Cleanup happens automatically when the context exits
```

</Fragment>
<Fragment slot="rust">

```rust
#[cocoindex::lifespan]
async fn lifespan(builder: EnvironmentBuilder) -> Result<EnvironmentBuilder> {
    let db = postgres::Database::connect(&database_url()).await?;
    let pool = db.pool().clone();
    Ok(builder
        .db_path(PathBuf::from(env!("CARGO_MANIFEST_DIR")).join(".cocoindex_db"))
        .provide_key(&DB, db)
        .on_shutdown(move || async move { pool.close().await }))
}
```

Register cleanup with `builder.on_shutdown(..)`. The hooks run in reverse order of registration when the environment shuts down. `Environment::from_registered()` and the `cocoindex` CLI run every registered lifespan before they open the state database.

</Fragment>
</LangTabs>

Setting `db_path` in the lifespan takes precedence over the `COCOINDEX_DB` environment variable. If neither is provided, CocoIndex <Lang only="python">will raise an error</Lang><Lang only="rust">returns an error</Lang>.

<Lang only="python">

The lifespan function can be sync or async:

```python
import cocoindex as coco

@coco.lifespan
def coco_lifespan(builder: coco.EnvironmentBuilder) -> Iterator[None]:
    builder.settings.db_path = pathlib.Path("./cocoindex.db")
    yield
```

</Lang>

<RustNote>
A lifespan is always an `async fn`, and no `yield` splits setup from cleanup: the function returns the builder, and `on_shutdown` hooks do the cleanup.
</RustNote>

You can also use the lifespan to provide resources (like database connections) that processing components can access. See [Context](./context) for details on sharing resources across your pipeline.

### Explicit lifecycle control (optional)

<Lang only="python">

The lifespan runs automatically the first time any App updates — most users don't need to do anything beyond defining the lifespan and calling `app.update()`.

If you need more explicit control (for example, to know when startup completes for health checks, or to explicitly trigger shutdown) you can manage the lifecycle directly:

</Lang>

<Lang only="rust">

The lifecycle is always explicit: `Environment::from_registered().await?` runs the registered lifespans, and `env.shutdown().await` runs the `on_shutdown` hooks and closes the state database. `#[cocoindex::main]` builds the Tokio runtime and answers `cocoindex ...` CLI invocations before the body runs:

</Lang>

{/* Rust: rust/sdk/SHOWCASE.md "Run apps with the `cocoindex` CLI", verified against rust/sdk/cocoindex/tests/registered.rs */}
<LangTabs>
<Fragment slot="python">

```python
# Async API
await coco.start()   # Run lifespan setup
# ... run apps or other operations ...
await coco.stop()    # Run lifespan cleanup
```

```python
# Sync (blocking) API
coco.start_blocking()   # Run lifespan setup
# ... run apps or other operations ...
coco.stop_blocking()    # Run lifespan cleanup
```

</Fragment>
<Fragment slot="rust">

```rust
#[cocoindex::main]
async fn main() -> Result<()> {
    // `cocoindex ...` invocations are handled before this body runs.
    let env = Environment::from_registered().await?;
    let stats = env.app("MyApp").await?.run(app_main).await?;
    println!("{stats}");
    env.shutdown().await;
    Ok(())
}
```

The hooks run once: a second `shutdown` only closes the database. Await every running update or drop before you call `shutdown`.

</Fragment>
</LangTabs>

<Lang only="python">

Or use the `runtime()` context manager, which supports both sync and async usage:

```python
# Async
async with coco.runtime():
    await app.update()
```

```python
# Sync (blocking)
with coco.runtime():
    app.update_blocking()
```

The same App can be retained and reused across sequential runtime lifecycles. After
`stop()` returns (or a `runtime()` block exits), its next update or drop starts a new
lifespan and uses freshly initialized resources. Persisted memoization and target-state
tracking in the internal database remain available across these cycles.

This restart guarantee applies to Apps using the default lazy environment (the default
when `AppConfig.environment` is omitted). An App explicitly bound to the concrete
Environment returned by `await coco.default_env()` stays bound to it, and `stop()` closes
that Environment, so the App's later updates and drops fail, even after a restart. Apps
using a separate explicit Environment are unaffected by starting or stopping the default
runtime.

Finish update and drop operations before stopping the runtime. Shutdown concurrent with
in-flight operations is not supported.

</Lang>

<RustNote>
An `Environment` does not restart after `shutdown`: its state database is closed. To run again, build a new environment with `Environment::from_registered()`. Persisted memoization and target-state tracking in the state database carry over to it.
</RustNote>

## Managing apps with CLI

CocoIndex provides a CLI for managing your apps without writing additional code.

<Lang only="rust">

The `cocoindex` binary from `rust/cli` builds your crate and drives its binary. The crate's `main` must carry `#[cocoindex::main]`, and each app must carry `#[cocoindex::app]`. The CLI's app target is `[path][:app_name]`: a crate directory (default `.`), a `Cargo.toml`, or a built binary, with the app's name after a colon when the crate registers more than one app.

</Lang>

### Update an app

Run your app once to sync all target states:

{/* Rust: rust/cli/src/main.rs (`Command::Update`, the `[path][:app_name]` target) */}
<LangTabs>
<Fragment slot="python">

```bash
cocoindex update main.py
```

</Fragment>
<Fragment slot="rust">

```bash
cocoindex update            # the crate in the current directory
cocoindex update :MyApp     # one app of a crate that registers several
```

</Fragment>
</LangTabs>

This executes your pipeline and applies all declared target states to external systems. Add `--live` (or `-L`) to keep the app running and react to source changes continuously — see [Live Mode](./live_mode).

### Drop an app

Remove an app and revert all its target states:

{/* Rust: rust/cli/src/main.rs (`Command::Drop`); `App::drop_state` in rust/sdk/cocoindex/tests/registered.rs */}
<LangTabs>
<Fragment slot="python">

```bash
cocoindex drop main.py
```

</Fragment>
<Fragment slot="rust">

```bash
cocoindex drop
```

From code, `app.drop_state().await?` does the same for one `App`.

</Fragment>
</LangTabs>

This will delete all target states created by the app (e.g., drop tables, delete rows) and clear its internal state.

`drop` is an explicit, foreground operation — any failure during the recursive delete (root or any descendant) <Lang only="python">raises</Lang><Lang only="rust">returns an error</Lang> rather than being silently logged. The internal tracking record for a component whose delete failed is preserved so the next `drop` (with the underlying problem fixed) can complete the cleanup. See [Error Handling](../advanced_topics/exception_handlers) for the general principle.

See <Lang only="python">[CLI Reference](../cli)</Lang><Lang only="rust">[CLI Reference](/docs/rust/cli/)</Lang> for more commands and options.
