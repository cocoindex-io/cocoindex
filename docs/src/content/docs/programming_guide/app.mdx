An **App** is the top-level runnable unit in CocoIndex.
It names your pipeline and binds a main function with its parameters. When you call `app.update()`, CocoIndex runs that main function as the root [processing component](./processing_component) which can mount child processing components to do work and declare target states.

## Creating an app

To create an App, provide:

1. **An `AppConfig`** (or just a name string) — identifies the pipeline
2. **A main function** — the entry point for your pipeline
3. **Arguments** — any additional arguments to pass to the main function

{/* Rust: examples/rust/text_embedding/src/main.rs, rust/sdk/SHOWCASE.md "Run apps with the `cocoindex` CLI" */}
<LangTabs>
<Fragment slot="python">

```python
import cocoindex as coco

@coco.fn
async def app_main(sourcedir: pathlib.Path) -> None:
    # ... your pipeline logic ...

app = coco.App(
    coco.AppConfig(name="MyPipeline"),
    app_main,
    sourcedir=pathlib.Path("./data"),
)
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::prelude::*;

#[cocoindex::app(name = "MyPipeline")]
async fn app_main(ctx: Ctx) -> Result<()> {
    index(ctx, source_dir()).await
}

async fn index(ctx: Ctx, sourcedir: PathBuf) -> Result<()> {
    // ... your pipeline logic ...
    Ok(())
}
```

In Rust, the main function takes the root component's `Ctx` by value and returns a `Result`. `#[cocoindex::app]` registers it under a name, so `Environment::from_registered` and the Rust CLI find it. The name is the function name unless you pass `name = "..."`. Arguments are not bound to the app: the registered function reads its inputs itself, and a closure passes them when your own code runs the app (see below).

</Fragment>
</LangTabs>

You can also pass just a name string instead of `AppConfig`:

{/* Rust: rust/sdk/SHOWCASE.md "Open and run an app" (verified against rust/sdk/cocoindex/src/app.rs) */}
<LangTabs>
<Fragment slot="python">

```python
app = coco.App("MyPipeline", app_main, sourcedir=pathlib.Path("./data"))
```

</Fragment>
<Fragment slot="rust">

```rust
let app = App::open("MyPipeline", ".cocoindex_db").await?;
```

`App::open(name, db_path)` is short for `App::builder(name).db_path(db_path).build().await`. When the app needs shared resources, build an `Environment` and open the app from it:

```rust
let app = Environment::builder()
    .db_path(".cocoindex_db")
    .provide_key(&DB, database)
    .build()
    .await?
    .app("MyPipeline")
    .await?;
```

</Fragment>
</LangTabs>

:::tip
The main function is usually async. See [How Sync and Async Work Together](./sdk_overview#how-sync-and-async-work-together) for details.
:::

## Updating an app

Call `update()` to execute the pipeline. It returns an `UpdateHandle` that is also `Awaitable`, so the simplest usage stays the same:

{/* Rust: rust/sdk/SHOWCASE.md "Run apps with the `cocoindex` CLI", examples/rust/text_embedding/src/main.rs, rust/sdk/cocoindex/tests/pipeline.rs */}
<LangTabs>
<Fragment slot="python">

```python
# Async — await the result directly (backward-compatible)
result = await app.update()
```

```python
# Sync (blocking) API
result = app.update_blocking()
```

</Fragment>
<Fragment slot="rust">

```rust
// `run` returns the run's statistics.
let stats = app.run(app_main).await?;
println!("{stats}");

// `update` returns the main function's value.
let result = app.update(app_main).await?;

// Arguments travel in a closure.
let stats = app.run(move |ctx| index(ctx, dir)).await?;
```

```rust
// Sync (blocking) API, outside a Tokio runtime
let result = app.update_blocking(app_main)?;
```

</Fragment>
</LangTabs>

**Parameters:**

- `live` option keeps the app running after the initial scan so live components can continue watching for changes. See [Live Mode](./live_mode).
- `report_to_stdout` option prints periodic progress updates during execution. Pass `True` for the default refresh interval, or a `timedelta` to set it.
- `full_reprocess` option reprocesses everything, bypassing all memoization: every component **and** every memoized function re-executes, and all target states are re-applied even if unchanged. Mind the cost — this includes every paid external call (embedding and LLM APIs re-run for all content). To force re-running just one function's work, bump its [`version`](./function#version) instead.
- `component_selector` option runs only the components you name. See [Updating part of an app](#updating-part-of-an-app).

In Rust, these options are the fields of `UpdateOptions`: `live`, `report_to_stdout` (with `progress_refresh_interval`), `full_reprocess`, `preview`, `timeout` and `component_selector`. Pass them to `app.update_with_options`, or to `app.start_update_with_options` for a handle:

{/* Rust: rust/sdk/cocoindex/tests/fs_live.rs */}
<LangTabs>
<Fragment slot="python">

```python
handle = app.update(live=True)
await handle.result()
```

</Fragment>
<Fragment slot="rust">

```rust
let handle = app.start_update_with_options(
    UpdateOptions {
        full_reprocess: false,
        live: true,
        ..UpdateOptions::default()
    },
    app_main,
)?;
handle.result().await?;
```

`app.preview(app_main).await?` runs with `preview: true` and returns the planned `Vec<PreviewAction>` instead of applying them.

</Fragment>
</LangTabs>

When you update an App, CocoIndex:

1. Runs the lifespan setup (if not already done)
2. Executes the main function (the root processing component), which mounts child processing components
3. Compares the declared target states with the previous run and applies only the necessary changes to external systems

Given the same logic and inputs, updates are repeatable. When logic or inputs change, only the affected parts re-execute.

To watch progress beyond the `report_to_stdout` flag, the `UpdateHandle` returned by `app.update()` also exposes stats programmatically — poll with `handle.stats()` or stream with `handle.watch()`. For those structured APIs, and for splitting a run into separately-reported scopes with `coco.stats_group()`, see [Progress monitoring](../advanced_topics/progress_monitoring). In Rust, `app.start_update(f)` returns the `UpdateHandle`: poll with `handle.stats_snapshot()`, wait for a change with `handle.changed().await`, and take the value with `handle.result().await`.

### Updating part of an app

Pass `component_selector` to run a slice of the app: the components at the given paths and what it takes to reach them. Every other component stays exactly as it is. This is what you want to inspect or debug a few components without processing the rest, for example the rows on one page of an observability UI.

{/* Rust: rust/sdk/cocoindex/tests/pipeline.rs */}
<LangTabs>
<Fragment slot="python">

```python
paths = [coco.ROOT_PATH / coco.Symbol("process_file") / name for name in page_of_files]
await app.update(component_selector=paths)

# Preview what they would declare, without applying it.
actions = await app.update(component_selector=paths, preview=True)
```

</Fragment>
<Fragment slot="rust">

```rust
let selector = ComponentSelector::new([
    StablePath::root().concat_part(StableKey::Str("a.md".into())),
]);
app.update_with_options(
    UpdateOptions {
        component_selector: Some(selector),
        ..UpdateOptions::default()
    },
    app_main,
)
.await?;
```

</Fragment>
</LangTabs>

A selector is a set of component paths, each a `StablePath` built from the keys of the mount calls: a mount without a subpath adds the `Symbol` of the function's name, `coco.component_subpath("process", key)` adds its keys, and a key keeps its type (`1` is not `"1"`). A path names one component and everything below it, so `coco.ROOT_PATH / "process"` selects everything mounted under it. [`cocoindex show`](#managing-apps-with-cli) lists the paths of an app. Selecting a path that does not exist is not an error: it selects nothing.

What each component does in such an update:

| Component | What happens |
|---|---|
| Selected, or under a selected path | Runs as in a plain update: memoization applies, its target states sync, and if its source item is gone, it is deleted. |
| An ancestor of a selected path | Runs, to reach the selected path. Its own target states sync. |
| The root, and a `use_mount` child | Always run, since a value they return may be needed. What they `mount` is filtered in turn. |
| Anything else | Not run, and not treated as gone: no target state changes and nothing about it changes in CocoIndex's records, even if its source item changed or was deleted. A live component does not start. |

Details to rely on:

- **The next plain update catches up.** An unselected component is processed by the next update that covers it, including its deletion if its source item is still gone. To make that possible, a component that ran with a filter on what it mounts (an ancestor of a selected path, or an unselected `use_mount` child) stores no [memo](./function#memoization) and drops the one it had, so it runs again next time. What it mounted hits its own memo as usual.
- **A memo hit stands in for the subtree.** As in a plain update, a memoized ancestor whose inputs did not change is not run, and neither is anything below it. Add `full_reprocess=True` to force the selected components to run: it applies only to them and to the ancestors that reach them.
- **An ancestor that is no longer mounted stays whole.** If an ancestor of a selected path is gone from the source, nothing below it is deleted, selected or not, because deleting it would delete unselected components too. The next update that covers it does.
- **Live mode:** the selector holds for the whole update, including `operator.update` and `operator.delete` calls from later live events. A live component already running in another update is left alone if unselected. If it is selected or an ancestor of a selected path, this update replaces it, as any second mount of a live component does, so don't run a slice over the live components of a running live update.
- **Preview** returns the actions of the components that ran: the selected ones, plus any changes to the own target states of the ancestors and `use_mount` children that ran. As in any preview, the deletion of a component that is no longer mounted is not previewed.
- **Taking over a target state.** A selected component that declares a target state another component owns takes it over, as it would in a plain update. The rest of the other component is left alone.
- **Empty selector.** `component_selector=[]` selects nothing: the root and its `use_mount` children run, and no other component does. `None`, the default, is a plain update.
- A source is still listed in full, since `mount_each()` filters item by item. Reading only the selected keys from a source that supports point reads is not implemented yet. Duplicate keys in a `mount_each()` are not detected among the items it skips.
- In Rust, the selector filters `ctx.mount`, `ctx.mount_each` and live components. `ctx.scope`, `use_mount!` and `use_mount_each!` return values, so they always run.

## How an app runs

An App is the top-level runner and entry point. A **processing component** is the unit of incremental execution *within* an app.

- Your app's main function runs as the **root processing component** at the root path.
- Each call to `mount()` or `use_mount()` declares a **child processing component** at a child path. Sugar APIs like `mount_each()` and `mount_target()` also create child components.
- Each processing component declares a set of target states, and CocoIndex syncs them as a unit when that component finishes — all writes happen after processing completes, and each target backend applies its batch atomically when supported.

This is why `app.update()` does not "run everything from scratch": CocoIndex uses the component path tree to decide what can be reused and what must re-run.

For example, an app that processes files might mount one component per file — the per-file fan-out from [Core Concepts](./core_concepts#processing-component), shown here as a path tree:

```text
(root)                         ← app_main component
└── process_file
    ├── "hello.md"             ← process_file component
    └── "world.md"             ← process_file component
```

See [Processing Component](./processing_component) for how mounting and component paths define these boundaries.

## Database path

CocoIndex needs a database path (`db_path`) to store its internal state. This database tracks target states and memoized results from previous runs, enabling CocoIndex to compute what changed and apply only the necessary updates.

The simplest way to configure the database path is via the `COCOINDEX_DB` environment variable:

```bash
export COCOINDEX_DB=./cocoindex.db
```

With `COCOINDEX_DB` set, you can create and run apps without any additional configuration:

{/* Rust: examples/rust/text_embedding/src/main.rs; `COCOINDEX_DB` fallback verified in rust/sdk/cocoindex/src/app.rs `Environment::from_registered` */}
<LangTabs>
<Fragment slot="python">

```python
import cocoindex as coco

@coco.fn
def app_main() -> None:
    # ... your pipeline logic ...

app = coco.App("MyPipeline", app_main)
app.update_blocking()  # Uses COCOINDEX_DB for storage
```

</Fragment>
<Fragment slot="rust">

```rust
let env = Environment::from_registered().await?;  // Uses COCOINDEX_DB when no lifespan sets db_path
let app = env.app("MyPipeline").await?;
let stats = app.run(app_main).await?;
env.shutdown().await;
```

In Rust, `COCOINDEX_DB` applies to `Environment::from_registered()` and the Rust CLI. A plain `Environment::builder().build()` or `App::builder(name).build()` reads no environment variables: give it the path with `.db_path(..)`.

</Fragment>
</LangTabs>

For details on what the internal database stores and how to tune its LMDB settings (the database grows automatically; `map_size` only sets where it starts), see [Internal Storage](../advanced_topics/internal_storage).

## Lifespan (optional)

A **lifespan function** defines the CocoIndex runtime lifecycle: its setup runs when the runtime starts (automatically before the first `app.update()`), and its cleanup runs when the runtime stops. Use it to configure CocoIndex settings programmatically or to initialize shared resources that processing components can reuse.

:::tip
If you only need to set the database path, using the `COCOINDEX_DB` environment variable is simpler than defining a lifespan function.
:::

### Defining a lifespan

Use the `@lifespan` decorator to register a lifespan function. By default, all apps share the same lifespan (unless you explicitly specify an app in a different [*Environment*](../advanced_topics/multiple_environments)). The function receives an `EnvironmentBuilder` for configuration and uses `yield` to separate setup from cleanup:

{/* Rust: examples/rust/text_embedding/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
import pathlib
from typing import AsyncIterator
import cocoindex as coco

@coco.lifespan
async def coco_lifespan(builder: coco.EnvironmentBuilder) -> AsyncIterator[None]:
    # Configure CocoIndex's internal database location (overrides COCOINDEX_DB if set)
    builder.settings.db_path = pathlib.Path("./cocoindex.db")
    # Setup: initialize resources here
    yield
    # Cleanup happens automatically when the context exits
```

</Fragment>
<Fragment slot="rust">

```rust
#[cocoindex::lifespan]
async fn lifespan(builder: EnvironmentBuilder) -> Result<EnvironmentBuilder> {
    let db = postgres::Database::connect(&database_url()).await?;
    let pool = db.pool().clone();
    Ok(builder
        .db_path(PathBuf::from(env!("CARGO_MANIFEST_DIR")).join(".cocoindex_db"))
        .provide_key(&DB, db)
        .on_shutdown(move || async move { pool.close().await }))
}
```

In Rust, the lifespan is an `async fn` that takes the `EnvironmentBuilder` and returns it. There is no `yield`: register cleanup with `builder.on_shutdown(..)`. Hooks run in reverse order when the environment shuts down. `Environment::from_registered()` and the Rust CLI run every registered lifespan before they open the state database.

</Fragment>
</LangTabs>

Setting `db_path` in the lifespan takes precedence over the `COCOINDEX_DB` environment variable. If neither is provided, CocoIndex will raise an error.

The lifespan function can be sync or async:

```python
import cocoindex as coco

@coco.lifespan
def coco_lifespan(builder: coco.EnvironmentBuilder) -> Iterator[None]:
    builder.settings.db_path = pathlib.Path("./cocoindex.db")
    yield
```

A Rust lifespan is always an `async fn`.

You can also use the lifespan to provide resources (like database connections) that processing components can access. See [Context](./context) for details on sharing resources across your pipeline.

### Explicit lifecycle control (optional)

The lifespan runs automatically the first time any App updates — most users don't need to do anything beyond defining the lifespan and calling `app.update()`.

If you need more explicit control (for example, to know when startup completes for health checks, or to explicitly trigger shutdown) you can manage the lifecycle directly:

{/* Rust: rust/sdk/SHOWCASE.md "Run apps with the `cocoindex` CLI", verified against rust/sdk/cocoindex/tests/registered.rs */}
<LangTabs>
<Fragment slot="python">

```python
# Async API
await coco.start()   # Run lifespan setup
# ... run apps or other operations ...
await coco.stop()    # Run lifespan cleanup
```

```python
# Sync (blocking) API
coco.start_blocking()   # Run lifespan setup
# ... run apps or other operations ...
coco.stop_blocking()    # Run lifespan cleanup
```

</Fragment>
<Fragment slot="rust">

```rust
#[cocoindex::main]
async fn main() -> Result<()> {
    // `cocoindex ...` invocations are handled before this body runs.
    let env = Environment::from_registered().await?;
    let stats = env.app("MyApp").await?.run(app_main).await?;
    println!("{stats}");
    env.shutdown().await;
    Ok(())
}
```

In Rust, the lifecycle is always explicit: `Environment::from_registered().await?` runs the registered lifespans, and `env.shutdown().await` runs the `on_shutdown` hooks. `#[cocoindex::main]` builds the Tokio runtime and answers the Rust CLI before the body runs. A second `shutdown` is a no-op.

</Fragment>
</LangTabs>

Or use the `runtime()` context manager, which supports both sync and async usage:

```python
# Async
async with coco.runtime():
    await app.update()
```

```python
# Sync (blocking)
with coco.runtime():
    app.update_blocking()
```

The Rust SDK has no `runtime()` context manager: call `env.shutdown().await` when the work is done.

The same App can be retained and reused across sequential runtime lifecycles. After
`stop()` returns (or a `runtime()` block exits), its next update or drop starts a new
lifespan and uses freshly initialized resources. Persisted memoization and target-state
tracking in the internal database remain available across these cycles.

This restart guarantee applies to Apps using the default lazy environment (the default
when `AppConfig.environment` is omitted). An App explicitly bound to the concrete
Environment returned by `await coco.default_env()` stays bound to it, and `stop()` closes
that Environment, so the App's later updates and drops fail, even after a restart. Apps
using a separate explicit Environment are unaffected by starting or stopping the default
runtime.

Finish update and drop operations before stopping the runtime. Shutdown concurrent with
in-flight operations is not supported.

## Managing apps with CLI

CocoIndex provides a CLI for managing your apps without writing additional code.

For a Rust project, the `cocoindex` binary from `rust/cli` builds the crate and drives its binary. The crate's `main` must carry `#[cocoindex::main]`, and each app must carry `#[cocoindex::app]`. The CLI's app target is `[path][:app_name]`: a crate directory (default `.`), a `Cargo.toml`, or a built binary, with the app's name after a colon when the crate registers more than one app.

### Update an app

Run your app once to sync all target states:

{/* Rust: /tmp/coco-land-rust-cli-help.txt (`cocoindex update --help`) */}
<LangTabs>
<Fragment slot="python">

```bash
cocoindex update main.py
```

</Fragment>
<Fragment slot="rust">

```bash
cocoindex update            # the crate in the current directory
cocoindex update :MyApp     # one app of a crate that registers several
```

</Fragment>
</LangTabs>

This executes your pipeline and applies all declared target states to external systems. Add `--live` (or `-L`) to keep the app running and react to source changes continuously — see [Live Mode](./live_mode).

### Drop an app

Remove an app and revert all its target states:

{/* Rust: /tmp/coco-land-rust-cli-help.txt (`cocoindex drop --help`); `App::drop_state` in rust/sdk/cocoindex/tests/registered.rs */}
<LangTabs>
<Fragment slot="python">

```bash
cocoindex drop main.py
```

</Fragment>
<Fragment slot="rust">

```bash
cocoindex drop
```

From code, `app.drop_state().await?` does the same for one `App`.

</Fragment>
</LangTabs>

This will delete all target states created by the app (e.g., drop tables, delete rows) and clear its internal state.

`drop` is an explicit, foreground operation — any failure during the recursive delete (root or any descendant) raises rather than being silently logged. The internal tracking record for a component whose delete failed is preserved so the next `drop` (with the underlying problem fixed) can complete the cleanup. See [Error Handling](../advanced_topics/exception_handlers) for the general principle.

See [CLI Reference](../cli) for more commands and options.
