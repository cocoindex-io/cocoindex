## Incremental processing

Data and code change over time. Incremental processing reruns affected work and updates targets, such as a search database.

Manual implementations must track changes and preserve intermediate results.
They must also manage inserts, updates, deletes, schema changes, and backfills.

## State-driven programming

Declare the target state you want from the current source data.
CocoIndex computes and applies the changes needed to match it.

**TargetState = Transform(SourceState)**

The target state is a pure function of the source state, with no other side effects.
Transformations read sources and produce target data, such as database rows or files.

<details>
<summary>Compare familiar programming models</summary>

- **React:** Declare UI from state. React updates the UI when state changes.
- **Spreadsheets:** Declare formulas. Upstream changes recompute dependent cells.
- **Materialized views:** Declare a query. Source changes refresh the view.

</details>

## App

An **app** is CocoIndex's top-level executable. It reads sources, transforms data, and declares target states.
CocoIndex synchronizes those target states with external systems, such as Postgres or a vector database.

## Processing component

A **processing component** owns the work and target states for one source item.
It runs independently. When it finishes, CocoIndex applies its target states without waiting for other components.

For example, if you have many files in a drive and want to process them file by file, your processing component would operate at the file level:

<ComponentPerFile />

One file can produce several target states, such as one embedding vector per text chunk.
CocoIndex batches the inserts, updates, and deletes for each file after processing completes.
Each target backend applies its batch atomically when supported, such as within a database transaction:

## Function memoization: skip unchanged computations

A **memoized function** reuses its previous result when its inputs and code remain unchanged.
Both processing components and transforms are functions, so you can memoize either level:

- **Processing component:** Skip the whole file when its content and processing logic remain unchanged.
- **Transform:** Reuse an embedding when its text and embedding logic, including the model, remain unchanged.

See [Function Memoization](./function#memoization) for more details.

<ComponentWithChunks memoized={true} />

Here's how memoization behaves in different scenarios:

<Tabs labels={["Change input", "Change code"]}>
  <Fragment slot="tab-0">
    <ComponentWithChunks memoized={true} scenario={{ rows: [
      { file: 'a.md', pcStatus: 'cache-ready', chunks: [
        { label: 'chunk1', vectorLabel: 'vector1', embedStatus: 'cache-ready' },
        { label: 'chunk2', vectorLabel: 'vector2', embedStatus: 'cache-ready' },
      ] },
      { file: 'b.md', fileState: 'updated', pcStatus: 'refreshing', pcState: 'updated', splitState: 'updated', chunks: [
        { label: 'chunk3', vectorLabel: 'vector3', embedStatus: 'cache-ready' },
        { label: 'chunk4', vectorLabel: 'vector4', state: 'removed' },
        { label: 'chunk5', vectorLabel: 'vector5', state: 'new' },
      ] },
    ]}} />

    When `b.md` changes:

    - `a.md` and its processing component remain cached.
    - `b.md` runs again and produces `chunk3` and `chunk5`.
    - `Embed(chunk3)` reuses its cached result. `Embed(chunk5)` requires a new computation.
  </Fragment>
  <Fragment slot="tab-1">
    <ComponentWithChunks memoized={true} scenario={{ rows: [
      { file: 'a.md', pcStatus: 'refreshing', pcState: 'updated', splitState: 'updated', chunks: [
        { label: 'chunk1', vectorLabel: 'vector1', embedStatus: 'cache-ready' },
        { label: 'chunk2', vectorLabel: 'vector2', embedStatus: 'cache-ready' },
      ] },
      { file: 'b.md', pcStatus: 'refreshing', pcState: 'updated', splitState: 'updated', chunks: [
        { label: 'chunk3', vectorLabel: 'vector3', state: 'removed' },
        { label: 'chunk4', vectorLabel: 'vector4', state: 'removed' },
        { label: 'chunk5', vectorLabel: 'vector5', state: 'new' },
        { label: 'chunk6', vectorLabel: 'vector6', state: 'new' },
      ] },
    ]}} />

    When the "Split into chunks" logic changes:

    - Both processing components run again.
    - `a.md` produces the same chunks, so its `Embed` results are reused.
    - `b.md` produces `chunk5` and `chunk6`, which require new `Embed` computations.

    A code change can still reuse downstream results when their inputs and function logic remain unchanged.
  </Fragment>
</Tabs>
