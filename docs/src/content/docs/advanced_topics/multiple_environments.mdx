<Lang only="python">By default, all CocoIndex apps share the same environment, which manages a shared database and context. For most use cases, this default behavior is sufficient. However, you can create multiple isolated environments when you need:</Lang><Lang only="rust">An environment manages a database and the context values shared by its apps. Most programs build one environment, through `Environment::from_registered()` or a builder. You can create multiple isolated environments when you need:</Lang>

- **Library development**: Libraries that depend on CocoIndex can use their own environment to avoid sharing state with other libraries or the application
- **Database isolation**: Different apps using separate databases
- **Multi-tenant deployments**: Isolated data per tenant
- **Testing**: Isolated test environments that don't interfere with production

## Creating an Environment

Create an explicit environment <Lang only="python">by providing `Settings` with a `db_path`</Lang><Lang only="rust">with `Environment::builder()` and a `db_path`</Lang>:

{/* Rust: rust/sdk/cocoindex/tests/pipeline.rs (Environment::builder), rust/sdk/cocoindex/src/app.rs */}
<LangTabs>
<Fragment slot="python">

```python
import cocoindex as coco
import pathlib

env = coco.Environment(coco.Settings.from_env(db_path=pathlib.Path("./my_db.db")))
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::Environment;

let env = Environment::builder()
    .db_path("./my_db.db")
    .build()
    .await?;
```

An `Environment` built this way reads no environment variables. `Environment::from_registered()` is the path that runs the `#[cocoindex::lifespan]` functions and falls back to `COCOINDEX_DB`; it is what the `cocoindex` CLI uses.

</Fragment>
</LangTabs>

<Lang only="python">

You can optionally name the environment for easier identification:

```python
env = coco.Environment(
    coco.Settings.from_env(db_path=pathlib.Path("./my_db.db")),
    name="production"
)
```

`Settings` also accepts `db_settings` (a `coco.LmdbSettings` instance) for tuning the internal LMDB database. See [Internal Storage](./internal_storage#lmdb-tuning) for details.

</Lang>

<Lang only="rust">

The builder also has `lmdb_max_dbs(..)` and `lmdb_map_size(..)` for tuning the internal LMDB database. See [Internal Storage](./internal_storage#lmdb-tuning) for details.

</Lang>

<RustNote>
An `Environment` has no name of its own: the name a handler sees in `ExceptionContext::env_name` is the app's name.
</RustNote>

## Associating Apps with an Environment

<Lang only="python">Pass the environment to `AppConfig` when creating an app</Lang><Lang only="rust">Create the app from the environment</Lang>:

{/* Rust: rust/sdk/cocoindex/src/app.rs (Environment::app), rust/sdk/SHOWCASE.md (verified) */}
<LangTabs>
<Fragment slot="python">

```python
app = coco.App(
    coco.AppConfig(name="MyApp", environment=env),
    main_fn,
)
```

</Fragment>
<Fragment slot="rust">

```rust
let app = env.app("MyApp").await?;
```

Several apps can share one environment: each name is its own LMDB namespace, and they share the environment's provided resources. `App::open(name, db_path)` and `App::builder(name)` build a single-app environment for you.

</Fragment>
</LangTabs>

<Lang only="python">

Apps that don't specify an environment use the default environment (configured via `@coco.lifespan` or the `COCOINDEX_DB` environment variable).

</Lang>

<RustNote>
There is no implicit default environment: an `App` always comes from an `Environment` you built, or from `Environment::from_registered()`, which runs the `#[cocoindex::lifespan]` functions and reads `COCOINDEX_DB` when no lifespan set a db path.
</RustNote>

## Closing an Environment

<Lang only="python">

An environment holds its database open, and LMDB allows one environment per `db_path` per process. An explicit environment's store is released when the last reference to it is gone: the environment itself, the Apps and `AppConfig`s bound to it, its `ContextProvider`, and any operations still finishing. Until then, opening the same `db_path` again fails:

```text
RuntimeError: the database at 'my_db.db' is already open in this process; close that Environment with Environment.close(), or drop it along with every App, AppConfig and ContextProvider bound to it (and let in-flight operations finish), before opening it again
```

Call `env.close()` once you're done with it to release the database without waiting for those references:

</Lang>

<Lang only="rust">

An environment holds its database open, and LMDB allows one environment per `db_path` per process: while one is open, building another on the same `db_path` fails with an error that says the database "is already open in this process".

Call `env.shutdown().await` once you're done with it to close the database:

</Lang>

{/* Rust: rust/sdk/cocoindex/tests/registered_nodb.rs (env.shutdown), rust/sdk/cocoindex/src/app.rs (Environment::shutdown) */}
<LangTabs>
<Fragment slot="python">

```python
env.close()
env = coco.Environment(coco.Settings.from_env(db_path=pathlib.Path("./my_db.db")))
```

</Fragment>
<Fragment slot="rust">

```rust
env.shutdown().await;
let env = Environment::builder().db_path("./my_db.db").build().await?;
```

`shutdown()` runs the `on_shutdown` hooks registered on the builder, most recently registered first, then closes the state db. Await every running update or drop before calling it.

</Fragment>
</LangTabs>

<Lang only="python">

`close()` waits for in-flight writes to finish. After that, using the environment raises an error, and so does updating the apps that use it. Context values provided to the environment stay open: whoever provided them closes them. Stopping the default environment (leaving `coco.runtime()`, or calling `coco.stop()`) closes it for you.

Garbage collection only helps when the last reference sits in a cycle: `gc.collect()` breaks the cycle and releases the store. Don't count on it otherwise. An environment created while an event loop is running (for example, inside a function run by `asyncio.run()`) runs its apps on that loop. On free-threaded Python 3.14+, that loop's worker threads, which connectors use for file I/O, then keep the environment alive, and its database open, for as long as the loop runs — even after you drop every reference to it. So do threads you start from your own functions while an app updates.

</Lang>

## Example: Multiple Environments

This example creates two apps in different environments, each with its own database:

{/* Rust: rust/sdk/cocoindex/src/app.rs (Environment::builder, Environment::app, App::run) */}
<LangTabs>
<Fragment slot="python">

```python
import cocoindex as coco
import pathlib

# Create two environments with separate databases
env1 = coco.Environment(coco.Settings.from_env(db_path=pathlib.Path("./db1/cocoindex.db")))
env2 = coco.Environment(coco.Settings.from_env(db_path=pathlib.Path("./db2/cocoindex.db")))

@coco.fn
def build1() -> None:
    # ... pipeline logic for env1 ...
    pass

@coco.fn
def build2() -> None:
    # ... pipeline logic for env2 ...
    pass

# Apps in different environments
app1 = coco.App(coco.AppConfig(name="App1", environment=env1), build1)
app2 = coco.App(coco.AppConfig(name="App2", environment=env2), build2)
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::prelude::*;

#[cocoindex::function]
async fn build1(_ctx: &Ctx) -> Result<()> {
    // ... pipeline logic for env1 ...
    Ok(())
}

#[cocoindex::function]
async fn build2(_ctx: &Ctx) -> Result<()> {
    // ... pipeline logic for env2 ...
    Ok(())
}

// Two environments with separate databases
let env1 = Environment::builder().db_path("./db1/cocoindex.db").build().await?;
let env2 = Environment::builder().db_path("./db2/cocoindex.db").build().await?;

// Apps in different environments
let app1 = env1.app("App1").await?;
let app2 = env2.app("App2").await?;
app1.run(|ctx| async move { build1(&ctx).await }).await?;
app2.run(|ctx| async move { build2(&ctx).await }).await?;
```

</Fragment>
</LangTabs>

## Same App Name in Different Environments

Apps with the same name can coexist in different environments. This is useful for multi-tenant scenarios or running the same pipeline against different databases<Lang only="rust">: `env_alpha.app("MyApp")` and `env_default.app("MyApp")` are two apps with their own state, one per environment.</Lang><Lang only="python">:</Lang>

<Lang only="python">

```python
import cocoindex as coco
import pathlib
from typing import Iterator

# Named environment for "alpha" tenant
env_alpha = coco.Environment(
    coco.Settings.from_env(db_path=pathlib.Path("./alpha/cocoindex.db")),
    name="alpha"
)

# Default environment via lifespan
@coco.lifespan
def _lifespan(builder: coco.EnvironmentBuilder) -> Iterator[None]:
    builder.settings.db_path = pathlib.Path("./default/cocoindex.db")
    yield

@coco.fn
def build() -> None:
    # ... pipeline logic ...
    pass

# Same app name, different environments
app_alpha = coco.App(coco.AppConfig(name="MyApp", environment=env_alpha), build)
app_default = coco.App("MyApp", build)  # Uses default environment
```

</Lang>

<Lang only="python">

## CLI Support

When working with multiple environments, the CLI groups apps by their environment. Use the `@env_name` syntax to target a specific app:

```bash
# List all apps grouped by environment
cocoindex ls ./multi_env.py

# Update a specific app in a named environment
cocoindex update ./multi_env.py:MyApp@alpha

# Update the app in the default environment
cocoindex update ./multi_env.py:MyApp@default
```

</Lang>

<RustNote>
The `cocoindex` CLI for Rust drives the one environment that `Environment::from_registered()` builds, so it has no `@env_name` syntax.
</RustNote>

## Testing with Isolated Environments

For tests, create isolated environments to avoid interference between test runs:

{/* Rust: rust/sdk/cocoindex/tests/mount.rs (temp_app), rust/sdk/cocoindex/tests/memo_deps.rs (app_at) */}
<LangTabs>
<Fragment slot="python">

```python
import cocoindex as coco
import pathlib
import tempfile

def create_test_env(test_name: str) -> coco.Environment:
    db_path = pathlib.Path(tempfile.mkdtemp()) / f"{test_name}.db"
    return coco.Environment(coco.Settings.from_env(db_path=db_path))

# In your test
def test_my_pipeline():
    env = create_test_env("test_my_pipeline")
    app = coco.App(
        coco.AppConfig(name="TestApp", environment=env),
        my_main_fn,
    )
    app.update_blocking()
    # ... assertions ...
```

</Fragment>
<Fragment slot="rust">

```rust
async fn temp_app(name: &str) -> (App, tempfile::TempDir) {
    let dir = tempfile::tempdir().unwrap();
    let app = App::builder(name)
        .db_path(dir.path().join(".cocoindex_db"))
        .build()
        .await
        .unwrap();
    (app, dir)
}

#[tokio::test]
async fn my_pipeline() {
    let (app, _dir) = temp_app("TestApp").await;
    app.update(|ctx| async move { my_main_fn(&ctx).await }).await.unwrap();
    // ... assertions ...
}
```

Keep the `TempDir` alive for the test: dropping it deletes the database directory.

</Fragment>
</LangTabs>

## When to Use Multiple Environments

<Lang only="python">

| Use Case | Approach |
|----------|----------|
| Single app, single database | Default environment (no explicit environment needed) |
| Multiple apps sharing state | Default environment |
| Apps needing separate databases | Explicit environments with different `db_path` |
| Multi-tenant isolation | Named environments per tenant |
| Testing | Temporary isolated environments |

</Lang>

<Lang only="rust">

| Use Case | Approach |
|----------|----------|
| Single app, single database | `App::open(name, db_path)` or `App::builder(name)` (a single-app environment) |
| Multiple apps sharing state | One environment, several `env.app(..)` |
| Apps needing separate databases | Explicit environments with different `db_path` |
| Multi-tenant isolation | One environment per tenant |
| Testing | Temporary isolated environments |

</Lang>
