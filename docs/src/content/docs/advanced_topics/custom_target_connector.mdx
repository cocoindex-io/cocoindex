A **custom target connector** is the mechanism that connects CocoIndex's declarative target state system to external systems. When you call methods like <Lang only="python">`dir_target.declare_file()` or `table_target.declare_row()`</Lang><Lang only="rust">`dir_target.declare_file(ctx, name, content)` or `table_target.declare_row(ctx, &row)`</Lang>, a target connector handles the actual synchronization — determining what changed and applying those changes to the external system.

## When to create a custom target connector

Most users will use built-in connectors (like `localfs` or `postgres`) and never need to create their own. Consider creating a custom target connector when:

- You need to integrate with an external system not covered by existing connectors
- You need custom change detection logic (e.g., content-based fingerprinting)
- You need to manage hierarchical target states (containers with children)

:::tip[Start Simple]
For simple use cases where you just need to write data to an external system without sophisticated change tracking, consider using a regular function with memoization instead. Target states providers are most valuable when you need CocoIndex to track and clean up target states automatically.
:::

### TargetHandler *(you implement)*

A `TargetHandler` implements the reconciliation logic. It's a <Lang only="python">protocol</Lang><Lang only="rust">trait</Lang> with one required method and one optional method:

{/* Rust: rust/sdk/cocoindex/src/target_state.rs (TargetHandler) */}
<LangTabs>
<Fragment slot="python">

```python
class TargetHandler(Protocol[ValueT, TrackingRecordT, OptChildHandlerT]):
    def reconcile(
        self,
        key: StableKey,
        desired_target_state: ValueT | NonExistenceType,
        prev_possible_records: Collection[TrackingRecordT],
        prev_may_be_missing: bool,
        /,
    ) -> TargetReconcileOutput[Any, TrackingRecordT, OptChildHandlerT] | None:
        ...

    # Optional: override to support attachment types (see "Implementing attachment providers")
    def attachments(self) -> dict[str, TargetHandler]:
        return {}  # Default: no attachments
```

</Fragment>
<Fragment slot="rust">

```rust
pub trait TargetHandler<V>: Send + Sync + 'static
where
    V: Serialize + DeserializeOwned + Send + 'static,
{
    type TrackingRecord: Serialize + DeserializeOwned + Send + Sync + 'static;
    type Action: Serialize + DeserializeOwned + Send + 'static;

    fn reconcile(
        &self,
        key: StableKey,
        desired_target_state: Option<V>,
        prev_possible_records: Vec<Self::TrackingRecord>,
        prev_may_be_missing: bool,
    ) -> Result<Option<TargetReconcileOutput<Self::Action, Self::TrackingRecord>>>;

    // Optional: attachment handlers, keyed by attachment type name.
    fn attachments(&self) -> Result<Vec<(String, ChildTargetDef)>> {
        Ok(Vec::new())
    }
}
```

The value type `V` is the trait's type parameter; the tracking record and the action are associated types. The child handler type is not part of the trait: a container's sink builds it (see [container targets](#implementing-container-targets)).

</Fragment>
</LangTabs>

<Lang only="python">

**Type Parameters:**

- `ValueT`: The specification for the target state (e.g., file content, row data)
- `TrackingRecordT`: What's stored to detect changes on future runs
- `OptChildHandlerT`: The child handler type, or `None` for leaf targets. A container handler declares it as the third argument of its `reconcile()` return type, `TargetReconcileOutput[Action, TrackingRecord, ChildHandler]`; it types the provider you get from `declare_target_state_with_child()`.

**Parameters:**

- `key`: `StableKey` — a union of `None | bool | int | str | bytes | uuid.UUID | Symbol | tuple[StableKey, ...]`
- `desired_target_state`: What the user declared, or `NON_EXISTENCE` if no longer declared
- `prev_possible_records`: Tracking records from previous runs (may have multiple due to interrupted updates)
- `prev_may_be_missing`: If `True`, the target state might not exist in the external system

**Returns:**

- `TargetReconcileOutput` if an action is needed
- `None` if no changes are required

</Lang>

<Lang only="rust">

**Types:**

- `V`: The specification for the target state (e.g., file content, row data). It is `Serialize + DeserializeOwned`.
- `TrackingRecord`: What's stored to detect changes on future runs
- `Action`: What the sink applies to the external system

**Parameters:**

- `key`: `StableKey` — the key the target state was declared with
- `desired_target_state`: What the user declared, or `None` if no longer declared
- `prev_possible_records`: Tracking records from previous runs (may have multiple due to interrupted updates)
- `prev_may_be_missing`: If `true`, the target state might not exist in the external system

**Returns:**

- `Ok(Some(TargetReconcileOutput { .. }))` if an action is needed
- `Ok(None)` if no changes are required

A container handler (one used with `declare_target_state_with_child` or `mount_target`) must return `Some` output whenever `desired_target_state` is `Some`, even when nothing changed, and its action must be a `Create` or an `Update`: the sink's child handler factory builds the child handler from that action. Returning `None` leaves the child handler missing, and declaring a child target state then fails.

</Lang>

:::warning[Non-blocking and side-effect free]
The `reconcile()` method must be **non-blocking** and **free of side effects**. It should only compare states and return an action — actual I/O operations happen later in the `TargetActionSink`. CocoIndex may call `reconcile()` more than once for the same target state when it retries a commit internally; only the output of the committed attempt is applied.
:::

<Lang only="python">

:::info[Type annotations]
Annotate the `prev_possible_records` parameter with `Collection[YourTrackingRecord]` so CocoIndex can properly reconstruct stored tracking records during deserialization. See [Serialization](../programming_guide/serialization) for details on supported types.
:::

:::info[Values and actions are equal copies]
CocoIndex holds every declared target state until its processing component commits, and every action until its sink has applied it. To keep that cheap, a value made of plain data (builtin containers and scalars, date and time types, `Decimal`, `UUID`, `ipaddress` and `pathlib` objects, numpy arrays and scalars, enum members, and NamedTuples) is held in a compact encoded form from the moment it's declared. `reconcile()` then receives an equal copy of the value, with the same types (a tuple stays a tuple), rather than the declared object itself, and the sink receives equal copies of the actions `reconcile()` returned. A value holding anything else, such as a dataclass, a pydantic model, or a client handle, reaches `reconcile()` as the declared object.

So don't rely on the identity of a declared value or an action, or pass mutable state through them; and since the copy is taken at declaration, changes made to a value after it was declared are not seen.
:::

</Lang>

<Lang only="rust">

:::info[Values and actions are serialized]
A declared value is serialized when it is declared, and `reconcile` receives a `V` deserialized from that form. The actions and tracking records `reconcile` returns are serialized the same way, and the sink receives actions deserialized from them. So changes made to a value after it was declared are not seen, and no state passes through a value or an action other than its serialized fields.
:::

</Lang>

### Tracking record *(you define)*

A **tracking record** captures the essential information needed to detect changes. Good tracking records:

- Are **minimal**: Only include what's needed for change detection
- Are **deterministic**: Same input always produces the same record
- Are **serializable**: Must be persistable<Lang only="python"> (typically a NamedTuple or dataclass). Dataclasses and NamedTuples are serialized with msgspec automatically. For types requiring pickle, use `@coco.serialize_by_pickle`.</Lang><Lang only="rust">: any `Serialize + DeserializeOwned` type.</Lang>

    context_provider: coco.ContextProvider,
    actions: Sequence[_FileAction],

    for action in actions:
        if action.content is None:
            action.path.unlink(missing_ok=True)

```rust
/// A sink that records each applied action into `log` as `"<verb> <key>[=<value>]"`.
fn recording_sink(log: Log) -> TargetActionSink<RowAction> {
    TargetActionSink::from_async_fn(move |actions: Vec<TargetAction<RowAction>>| {
        let log = log.clone();
        async move {
            let mut log = log.lock().unwrap();
            for action in actions {
                let (verb, row) = match action {
                    TargetAction::Create(r) => ("create", r),
                    TargetAction::Update(r) => ("update", r),
                    TargetAction::Delete(r) => ("delete", r),
                };
                log.push(match row.value {
                    Some(v) => format!("{verb} {}={}", row.key, v),
                    None => format!("{verb} {}", row.key),
                });
            }
            Ok(())
        }
    })
}
```

A sink is always async. Its closure receives `Vec<TargetAction<A>>`, where each item is `TargetAction::Create(a)`, `Update(a)` or `Delete(a)`, so the operation kind travels beside your action. The action type must be `Serialize + DeserializeOwned`. The closure gets no connection from the environment: move the connection into it when you build the handler (see [Use `ContextKey` for external resource identity](#use-contextkey-for-external-resource-identity)).

The engine batches actions by sink *identity*: actions returned with the same sink (or a clone of it) are applied together in one call, and every `from_async_fn*` call creates a new identity. Build the sink once and return a clone from each `reconcile`.

</Fragment>
</LangTabs>

A **container** target's sink also takes a `child_handler` factory, <Lang only="python">`child_handler(context_provider, action) -> handler`</Lang><Lang only="rust">`Fn(&A) -> Result<ChildTargetDef>`</Lang>, which returns the handler for the child target states of a created or updated container. The callback stays the same: it applies the actions. See [Implementing container targets](#implementing-container-targets).

## Implementing root target states

Root target states are not nested inside another target.

### Life of a root target state

Understanding what happens at runtime:

1. **Registration**: You define a `TargetHandler` and call `register_root_target_states_provider()`<Lang only="rust"> from inside a component, on every run</Lang>. CocoIndex returns a `TargetStateProvider` — a factory for creating target states associated with your handler.

2. **Declaration**: During execution, user code calls `provider.target_state(key, spec)` to create `TargetState` objects, then `declare_target_state()` to declare them. CocoIndex collects all declared target states.

3. **Reconciliation**: When the processing unit finishes, CocoIndex calls your handler's `reconcile()` method for each target state. For declared target states, `desired_target_state` contains the spec; for previously declared but now missing states, `desired_target_state` is <Lang only="python">`NON_EXISTENCE`</Lang><Lang only="rust">`None`</Lang> (triggering cleanup). Your `reconcile()` compares the desired state with previous records and returns <Lang only="python">`TargetReconcileOutput` if an action is needed, or `None`</Lang><Lang only="rust">`Some(TargetReconcileOutput { .. })` if an action is needed, or `None`</Lang> if no changes are required.

4. **Action Execution**: CocoIndex batches actions by their `TargetActionSink` and executes them. The sink applies changes to the external system (database writes, file operations, API calls, etc.). A batch may combine the actions of several processing components that finish around the same time; if the sink fails, CocoIndex retries in smaller batches along component boundaries, so only the components whose actions actually fail are affected. The sink may therefore see an action from a failed batch again — keep actions idempotent.

5. **Tracking Persistence**: After successful execution, CocoIndex persists the new tracking records. On the next run, these become the `prev_possible_records` for change detection.

:::note[Multiple Previous States]
Due to interrupted updates, `prev_possible_records` may contain multiple records. CocoIndex tracks all possible states until a successful update confirms the current state. Your reconciliation logic should handle this by generating actions that work correctly regardless of which previous state is actual.
:::

### Step 2: Implement the handler

{/* Rust: rust/sdk/cocoindex/tests/target_state.rs (RowHandler, key_str) */}
<LangTabs>
<Fragment slot="python">

```python
class _RowHandler(coco.TargetHandler[_RowSpec, _RowTrackingRecord]):
    """Handler for database rows."""

    def __init__(self, connection: DatabaseConnection, table: str):
        self._conn = connection
        self._table = table
        self._sink = coco.TargetActionSink.from_async_fn(self._apply_actions)

    async def _apply_actions(
        self, context_provider: coco.ContextProvider, actions: Sequence[_RowAction]
    ) -> None:
        # Connection was passed in __init__ — context_provider not needed here,
        # but must be accepted per the sink protocol.
        for action in actions:
            if action.data is None:
                await self._conn.delete(self._table, action.key)
            else:
                await self._conn.upsert(self._table, action.key, action.data)

    def _compute_fingerprint(self, data: dict[str, Any]) -> bytes:
        from cocoindex.connectorkits.fingerprint import fingerprint_object
        return fingerprint_object(data)

    def reconcile(
        self,
        key: coco.StableKey,
        desired_target_state: _RowSpec | coco.NonExistenceType,
        prev_possible_records: Collection[_RowTrackingRecord],
        prev_may_be_missing: bool,
        /,
    ) -> coco.TargetReconcileOutput[_RowAction, _RowTrackingRecord] | None:
        # Handle deletion
        if coco.is_non_existence(desired_target_state):
            if not prev_possible_records and not prev_may_be_missing:
                return None  # Nothing to delete
            return coco.TargetReconcileOutput(
                action=_RowAction(key=key, data=None),
                sink=self._sink,
                tracking_record=coco.NON_EXISTENCE,
            )

        # Handle upsert
        target_fp = self._compute_fingerprint(desired_target_state.data)

        # Skip if unchanged
        if not prev_may_be_missing and all(
            prev.fingerprint == target_fp for prev in prev_possible_records
        ):
            return None

        return coco.TargetReconcileOutput(
            action=_RowAction(key=key, data=desired_target_state.data),
            sink=self._sink,
            tracking_record=_RowTrackingRecord(fingerprint=target_fp),
        )
```

</Fragment>

```rust
/// A flat row handler with full CRUD + no-change detection (tracking record is
/// the row value itself).
#[derive(Clone)]
struct RowHandler {
    sink: TargetActionSink<RowAction>,
}

impl TargetHandler<String> for RowHandler {
    type TrackingRecord = String;
    type Action = RowAction;

    fn reconcile(
        &self,
        key: StableKey,
        desired: Option<String>,
        prev: Vec<String>,
        prev_may_be_missing: bool,
    ) -> Result<Option<TargetReconcileOutput<RowAction, String>>> {
        let k = key_str(&key);
        match desired {
            Some(value) => {
                // Skip if unchanged
                let unchanged =
                    !prev_may_be_missing && !prev.is_empty() && prev.iter().all(|p| *p == value);
                if unchanged {
                    return Ok(None);
                }
                let row = RowAction {
                    key: k,
                    value: Some(value.clone()),
                };
                let action = if prev.is_empty() {
                    TargetAction::Create(row)
                } else {
                    TargetAction::Update(row)
                };
                Ok(Some(TargetReconcileOutput {
                    action,
                    sink: self.sink.clone(),
                    tracking_record: Some(value),
                    child_invalidation: None,
                }))
            }
            // Handle deletion
            None => {
                if prev.is_empty() && !prev_may_be_missing {
                    return Ok(None); // Nothing to delete
                }
                Ok(Some(TargetReconcileOutput {
                    action: TargetAction::Delete(RowAction {
                        key: k,
                        value: None,
                    }),
                    sink: self.sink.clone(),
                    tracking_record: None,
                    child_invalidation: None,
                }))
            }
        }
    }
}
```

`key_str` is a helper of the test that renders the `StableKey` as a string; `sink` is the `recording_sink` [above](#action-and-targetactionsink-you-implement).

## Implementing container targets

Container targets (directories, tables) have children (files, rows). A child is a non-root target state.

### Non-root target states

For targets **nested inside another target** (e.g., files inside a directory), the lifecycle is similar to root targets but **how you get the provider is different**.

For root targets, you call `register_root_target_states_provider()` and immediately get a provider with your handler. For non-root targets, the handler comes from the **`child_handler` factory of the parent's sink**, which CocoIndex calls with the parent's action:

1. **Declaration**: Call <Lang only="python">`declare_target_state_with_child(parent_ts)`</Lang><Lang only="rust">`declare_target_state_with_child(ctx, parent_ts)`</Lang> — returns an **unresolved** child provider immediately<Lang only="rust">. Or call `mount_target(ctx, parent_ts).await`, which declares and commits the parent in a foreground child component and returns a child provider that is already resolved.</Lang>
2. **Resolution**: When the parent reconciles, CocoIndex calls the sink's `child_handler` factory with the parent's action and resolves the child provider with the handler it returns. It does this before the sink applies the action, and in a preview (<Lang only="python">`app.update(preview=True)`</Lang><Lang only="rust">`app.preview(..)`</Lang>) in place of applying it — so the factory must build the handler from the action alone, with no side effects.
3. **Usage**: The child provider can now create child target states, which follow the same reconciliation → execution → tracking flow as root targets.

Some containers only get their identity when created: the external system assigns it (a Notion database or a Google Drive folder gets a server-assigned id). The factory cannot know that id, so let the handler look it up when it applies: the container sink records `key → id` in a connector-level map when it creates (or finds) the container, and the child handler's sink reads the id from that map by the container's key. Containers reconcile and apply on every run, before their children apply, so the map is filled when the children need it; a preview never applies the children, so it never needs the id.

### Child invalidation

When a container target undergoes certain changes, the child target states may be affected. The `child_invalidation` field in `TargetReconcileOutput` lets you signal this to CocoIndex:

- **<Lang only="python">`"destructive"`</Lang><Lang only="rust">`TargetChildInvalidation::Destructive`</Lang>** — The container change destroys all existing children (e.g., a primary key change that requires dropping and recreating a table). CocoIndex will ignore all previous tracking records for children under this container and treat them as new.

- **<Lang only="python">`"lossy"`</Lang><Lang only="rust">`TargetChildInvalidation::Lossy`</Lang>** — The container change may cause data loss for existing children (e.g., a schema change that removes columns). CocoIndex will force an upsert for all children by setting <Lang only="python">`prev_may_be_missing=True`</Lang><Lang only="rust">`prev_may_be_missing` to `true`</Lang>, even if their data appears unchanged.

- **`None`** (default) — No impact on children. Normal change detection applies.

Set `child_invalidation` in the **parent handler's** `reconcile()` method when you detect that the container itself has changed in a way that affects its children:

{/* Rust: rust/sdk/cocoindex/tests/target_state.rs (TableSpec, TableAction, TableHandler) */}

struct TableSpec {
    generation: String,
}

#[derive(Clone, Debug, Serialize, Deserialize, PartialEq, Eq)]
struct TableAction {
    name: String,
    drop: bool,
}

/// A container ("table") handler whose sink produces a child row handler per
/// declared table, and whose child invalidation is configurable.
struct TableHandler {
    sink: TargetActionSink<TableAction>,
    invalidation: Option<TargetChildInvalidation>,
}

impl TargetHandler<TableSpec> for TableHandler {
    type TrackingRecord = TableSpec;
    type Action = TableAction;

    fn reconcile(
        &self,
        key: StableKey,
        desired: Option<TableSpec>,
        prev: Vec<TableSpec>,
        _prev_may_be_missing: bool,
    ) -> Result<Option<TargetReconcileOutput<TableAction, TableSpec>>> {
        let name = key_str(&key);
        match desired {
            // Always emit an output when the table is declared, so the sink
            // builds the child handler.
            Some(spec) => {
                let changed = !prev.is_empty() && !prev.contains(&spec);
                let action = if prev.is_empty() {
                    TargetAction::Create(TableAction { name, drop: false })
                } else {
                    TargetAction::Update(TableAction { name, drop: false })
                };
                Ok(Some(TargetReconcileOutput {
                    action,
                    sink: self.sink.clone(),
                    tracking_record: Some(spec),
                    child_invalidation: changed.then_some(self.invalidation).flatten(),
                }))
            }
            None => Ok(Some(TargetReconcileOutput {
                action: TargetAction::Delete(TableAction { name, drop: true }),
                sink: self.sink.clone(),
                tracking_record: None,
                child_invalidation: Some(TargetChildInvalidation::Destructive),
            })),
        }
    }
}

### Deleting a container

When a container target state is no longer declared, CocoIndex runs the container handler's non-existence action and does **not** reconcile the children individually. The container action is therefore responsible for its children, in one of two shapes:

- **Destroy** — for a container CocoIndex owns, remove it together with its contents (<Lang only="python">`DROP TABLE`, `shutil.rmtree`, `drop_table`, …). The `_apply_dir_actions` sink in Step 2 below does this.</Lang><Lang only="rust">`DROP TABLE`, removing a directory tree, dropping an index, …). The `TableHandler` above returns a `Delete` action with `drop: true` for this.</Lang>
- **Abandon** — for a user-managed container (a message topic, a table the user created), leave the contents untouched. Once the container is no longer declared, CocoIndex has released its claim on it and must not write to it again: another writer may now own those keys, writing to a topic the user has since deleted would recreate it on brokers that auto-create topics, and the deletion policy captured from the old declaration (such as a `deletion_value_fn` closure) no longer exists.

<Lang only="python">

The zvec connector (`python/cocoindex/connectors/zvec/_target.py`, `_apply_collection_actions`) implements both: it destroys system-managed collections and leaves user-managed ones alone. `App.drop()` applies the same shapes to every root container (it drops tables and abandons topics without visiting rows or messages) so document on your connector page which shape it uses.

</Lang>

<Lang only="rust">

The Valkey connector (`rust/sdk/cocoindex/src/connectors/valkey.rs`) implements both: it drops a system-managed index and leaves a user-managed one alone (`ManagedBy::User`, see [statediff](#handle-multiple-previous-states)). Document on your connector page which shape it uses.

</Lang>

The user-facing contract is in [How CocoIndex syncs target states](../programming_guide/target_state#how-cocoindex-syncs-target-states).

<RustNote>
A connector outside the `cocoindex` crate registers its root provider on each run, so a container is deleted only by a run that still registers the provider and no longer declares the container. `App::drop_state` cannot reach such a handler and leaves its target states in place. Built-in connectors such as Valkey register their root provider with every environment when it is built, so `App::drop_state` and a run that no longer declares their targets reach the handler; that registration is internal to the crate.
</RustNote>

/// Build a container sink whose child handler factory gives each
/// created/updated table a fresh child row handler (recording into `row_log`).
fn table_sink(table_log: Log, row_log: Log) -> TargetActionSink<TableAction> {
    TargetActionSink::from_async_fn_with_child_handler(
        move |actions: Vec<TargetAction<TableAction>>| {
            let table_log = table_log.clone();
            async move {
                for action in actions {
                    log_table_action(&table_log, action);
                }
                Ok(())
            }
        },
        move |_: &TableAction| {
            Ok(ChildTargetDef::new::<String, _>(RowHandler {
                sink: recording_sink(row_log.clone()),
            }))
        },
    )
}

fn log_table_action(table_log: &Log, action: TargetAction<TableAction>) {
    let entry = match action {
        TargetAction::Create(t) | TargetAction::Update(t) => format!("ensure {}", t.name),
        TargetAction::Delete(t) => format!("drop {}", t.name),
    };
    table_log.lock().unwrap().push(entry);
}

CocoIndex calls the factory once per action whose target state was declared with a child (a created or updated container, never a delete) before the callback applies the batch, and in a preview in place of the callback. The container handler's `reconcile()` returns an action on every run while the container is declared, even when nothing about it changed: the factory builds the child handler from that action. ### Migrating from child slots and `ChildTargetDef`

Two older container contracts are deprecated and will be removed in a future release. Sinks written against them still run and emit a `DeprecationWarning`, but cannot be previewed:

- `from_fn_with_children()` / `from_async_fn_with_children()`, whose callback takes a third argument, `child_slots`, and calls `child_slots[i].fulfill(handler)` per child-bearing action.
- A `from_fn()` / `from_async_fn()` callback returning a list of `coco.ChildTargetDef(handler=...)` (or `None`) index-aligned with `actions`.

The pre-slot annotations still type-check: `coco.TargetActionSink[Action, ChildHandler]` is accepted (the second type argument is deprecated and ignored; evaluating it at runtime warns), and `coco.TargetReconcileOutput[Action, TrackingRecord, ChildHandler]` is unchanged — the third argument is how a container handler declares its child handler type.

To migrate a container sink:

1. Move the construction of the child handler into a function `(context_provider, action) -> handler` that builds it from the action alone.
2. Drop the `child_slots` parameter and the `fulfill` calls (or the `ChildTargetDef` list and the `return`), so the callback returns `None`.
3. Build the sink with `from_fn()` / `from_async_fn()`, passing the function as `child_handler=`.

```python
# Before
def _apply_dir_actions(
    context_provider: coco.ContextProvider,
    actions: Sequence[_DirAction],
    child_slots: Mapping[int, coco.ChildSlot[_EntryHandler]],
) -> None:
    for i, action in enumerate(actions):
        if action.should_delete:
            shutil.rmtree(action.path, ignore_errors=True)
        else:
            action.path.mkdir(parents=True, exist_ok=True)
            child_slots[i].fulfill(_EntryHandler(action.path))


_dir_sink = coco.TargetActionSink.from_fn_with_children(_apply_dir_actions)


# After
def _apply_dir_actions(
    context_provider: coco.ContextProvider,
    actions: Sequence[_DirAction],
) -> None:
    for action in actions:
        if action.should_delete:
            shutil.rmtree(action.path, ignore_errors=True)
        else:
            action.path.mkdir(parents=True, exist_ok=True)


def _entry_handler(
    context_provider: coco.ContextProvider, action: _DirAction
) -> _EntryHandler:
    return _EntryHandler(action.path)


_dir_sink = coco.TargetActionSink.from_fn(
    _apply_dir_actions, child_handler=_entry_handler
)
```

Leaf sinks need no change. If a leaf sink shares its callback with a container level (one sink per database serving table DDL and row writes), migrate it the same way: leaf actions never reach the factory.

</Lang>

<Lang only="rust">

### Migrating from child slots and child definitions

Two older container sink constructors are deprecated: `TargetActionSink::from_async_fn_with_children`, whose closure receives each action with an `Option<ChildSlot>` and calls `slot.fulfill(ChildTargetDef::new(..))` on each, and `TargetActionSink::from_async_fn_with_child_defs`, whose closure returns a `Vec<Option<ChildTargetDef>>` index-aligned with the actions. A sink built with `from_async_fn_with_children` cannot be previewed.

To migrate, move the construction of the `ChildTargetDef` into a closure `Fn(&A) -> Result<ChildTargetDef>` that builds it from the action alone, drop the slots (or the returned definitions) from the apply closure so it returns `Ok(())`, and build the sink with `from_async_fn_with_child_handler(apply, child_handler)`, as `table_sink` [above](#step-2-build-child-handlers-with-a-child_handler-factory) does.

</Lang>

## Implementing attachment providers

Attachment providers let a child handler expose **auxiliary target states** alongside its regular children. For example, a PostgreSQL table handler manages rows as regular children, but can also manage vector indexes and SQL command attachments as separate attachment types — each tracked independently.

### When to use attachments

Use attachments when a target has auxiliary state beyond its primary children — indexes, triggers, materialized views, or any side-resource that should be managed alongside the main data. Attachments use **symbol keys** as namespace separators so they never conflict with regular child keys.

### Target state path hierarchy

Attachments create additional levels in the target state path using symbol keys (denoted with `@` prefix in documentation):

```
@my_connector/table                    [level 1 — root provider]
  (db_key, schema, table_name)         [level 2 — table state]
    @vector_index                      [level 3 — attachment namespace (symbol key)]
      index_name_1                     [level 4 — attachment instance]
      index_name_2                     [level 4]
    @sql_command_attachment             [level 3 — another attachment namespace]
      cmd_name_1                       [level 4]
    row_pk_1                           [level 3 — regular child (row)]
    row_pk_2                           [level 3]
```

The symbol keys (`@vector_index`, `@sql_command_attachment`) are path namespaces — not target states themselves. They separate attachment instances from regular children at the same level.

### How it works

1. **Handler implements `attachments()`**: The child handler (e.g., row handler) returns <Lang only="python">a dict of</Lang><Lang only="rust">a `Vec` of `(name, ChildTargetDef)` pairs for</Lang> all supported attachment types and their handlers.
2. **Engine eagerly registers attachment providers**: When the child provider is resolved with the handler from the `child_handler` factory, the engine calls `attachments()` and registers all returned types. This ensures orphaned attachments can be cleaned up even when not declared in the current run.
3. **User code calls `provider.attachment()`**: On a resolved child provider, this retrieves the cached attachment sub-provider.
4. **Target states declared under the attachment provider** are tracked independently from regular children.

### Step 1: Implement the attachment handler

An attachment handler is just a regular `TargetHandler` — it implements `reconcile()` and has an action sink<Lang only="rust">. The example below reuses the `RowHandler` from [Step 2 of root target states](#step-2-implement-the-handler) as the attachment handler, with its own recording sink.</Lang><Lang only="python">:</Lang>

## Connector implementation guidelines

### Use `ContextKey` for external resource identity

When a target connector manages state in an external resource (a database, a search index, an object store, etc.), use a `ContextKey` string as part of the target state key — not connection parameters like host, port, or credentials.

Target state keys must be stable across runs for correct reconciliation. CocoIndex uses keys to match current declarations with previously tracked states. If the key is stable, previously tracked states are associated with the current target, so CocoIndex can correctly reconcile — e.g., deleting rows that are no longer declared. If the key changes (because a connection parameter changed), CocoIndex cannot associate previous tracked states with the current target, and treats the target as being in a cleared state — losing the ability to clean up old data.

`ContextKey` solves this by providing a user-defined stable logical name (e.g., `"my_pg"`) that is decoupled from transient connection details:

<Lang only="python">

```python
# User creates a stable logical name for the resource
db = coco.ContextKey[asyncpg.Pool]("my_pg")

# Target connector uses db.key (the string "my_pg") in the target state key
class _TableKey(NamedTuple):
    db_key: str            # Stable — from ContextKey.key
    schema_name: str | None
    table_name: str

key = _TableKey(db_key=db.key, schema_name=schema_name, table_name=table_name)

# At action time, resolve the live connection from context_provider
pool = context_provider.get(key.db_key, asyncpg.Pool)
```

This way, changing a password, switching replicas, or rotating credentials won't invalidate tracked states or break reconciliation.

**Resolve connections at action time, never at declare time.** Target states outlive the code that declared them: when a declaration disappears or an app is dropped, CocoIndex generates delete actions in a run where your mount/declare code never executes. At that point the only inputs available are the persisted target state key and the current environment — which is why the sink receives a `ContextProvider` and why the key must carry `ContextKey.key`. Don't capture a live connection when the target is declared; a connection captured at declare time won't exist for cleanup, and resolving in the sink keeps create, update, and delete on one code path. Once resolved in the root sink, pass the typed connection down to child handlers directly (e.g., store `_pool: asyncpg.Pool`, not the key string).

See `_TableKey` in [`cocoindex/connectors/postgres/_target.py`](https://github.com/cocoindex-io/cocoindex/blob/main/python/cocoindex/connectors/postgres/_target.py) and [`cocoindex/connectors/surrealdb/_target.py`](https://github.com/cocoindex-io/cocoindex/blob/main/python/cocoindex/connectors/surrealdb/_target.py) for reference implementations.

</Lang>

<Lang only="rust">

Put the key's name (`ContextKey::name()`, the string `"my_pg"`) in the target state key. The Valkey connector's index key holds the database's `ContextKey` name plus the index name:

{/* Rust: rust/sdk/cocoindex/src/connectors/valkey.rs (IndexKey) */}
```rust
/// An index target state's key: the database's `ContextKey` name plus the
/// index name.
struct IndexKey {
    db_key: String,
    index_name: String,
}

impl IndexKey {
    fn stable_key(self) -> StableKey {
        StableKey::Array(Arc::from([
            StableKey::Str(Arc::from(self.db_key)),
            StableKey::Str(Arc::from(self.index_name)),
        ]))
    }
}
```

This way, changing a password, switching replicas, or rotating credentials won't invalidate tracked states or break reconciliation.

A sink built with `TargetActionSink::from_async_fn` receives only the actions, not the environment's context values. So resolve the connection with `ctx.get_key(&key)` in the run that registers the provider, and move it into the handler and its sink. The run that registers the provider also produces the delete actions for target states it no longer declares, so the handler has its connection for them too. Pass the typed connection down to child handlers directly, not the key name.

</Lang>

### Idempotent actions

Actions should be idempotent — applying the same action multiple times should have the same effect as applying it once<Lang only="rust">: for example `CREATE TABLE IF NOT EXISTS`, `DROP INDEX IF EXISTS` and `INSERT ... ON CONFLICT DO UPDATE` rather than a plain `CREATE TABLE` or `INSERT`, which fail when the object already exists. A sink may see an action again after a failed batch is retried.</Lang><Lang only="python">:</Lang>

<Lang only="python">

```python
# Good: Idempotent
path.mkdir(parents=True, exist_ok=True)
path.unlink(missing_ok=True)
await conn.execute("INSERT ... ON CONFLICT DO UPDATE ...")

# Bad: Not idempotent
path.mkdir()  # Fails if exists
await conn.execute("INSERT ...")  # Fails on duplicate key
```

</Lang>

### Handle multiple previous states

Due to interrupted updates, `prev_possible_records` may contain multiple records. Design your reconciliation logic to handle this:

```python
# Check if ALL previous states match (conservative approach)
if not prev_may_be_missing and all(
    prev.fingerprint == target_fp for prev in prev_possible_records
):
    return None  # Safe to skip
```

</Fragment>

```rust
// Check if ALL previous states match (conservative approach)
let unchanged =
    !prev_may_be_missing && !prev.is_empty() && prev.iter().all(|p| *p == value);
if unchanged {
    return Ok(None); // Safe to skip
}
```

</Fragment>
</LangTabs>

<Lang only="python">

`cocoindex.connectorkits.statediff` packages this decision. `TrackingRecordTransition(desired, prev, prev_may_be_missing)` holds the inputs of one `reconcile()` call (`desired` is `coco.NON_EXISTENCE` for a removed target state), and `diff(transition)` returns `None` (skip) or a `DiffAction`: `"insert"`, `"upsert"`, `"replace"` or `"delete"`. `"replace"` means a previous record differs from the desired one; `"upsert"` means the records match but the target may be missing. For a target the user may own, wrap records in `MutualTrackingRecord(tracking_record, managed_by)` with `managed_by` `"system"` or `"user"`; `resolve_system_transition(transition)` returns `None` for a user-managed target, so it is left alone.

</Lang>

<Lang only="rust">

`cocoindex::statediff` packages this decision. `TrackingRecordTransition { desired, prev, prev_may_be_missing }` holds the inputs of one `reconcile` call, and `diff(Some(&transition))` returns `None` (skip) or a `DiffAction`: `Insert`, `Upsert`, `Replace` or `Delete`. `Replace` means a previous record differs from the desired one; `Upsert` means the records match but the target may be missing. For a target the user may own, wrap records in `MutualTrackingRecord::new(record, managed_by)` with `ManagedBy::System` or `ManagedBy::User`; `resolve_system_transition(desired, prev, prev_may_be_missing)` returns `None` for a user-managed target, so it is left alone.

</Lang>

For a container with keyed parts (a table's primary key and its columns), `CompositeTrackingRecord` and `diff_composite` return the main action plus one transition per part.

### Skip reconciling unchanged values

When a handler's tracking record is exactly the fingerprint of the declared value, set `tracks_value_fingerprint = True` on the handler class:

```python
from cocoindex.connectorkits.fingerprint import fingerprint_object

class RowHandler(coco.TargetHandler[dict[str, Any], bytes]):
    tracks_value_fingerprint = True

    def reconcile(self, key, desired_target_state, prev_possible_records, prev_may_be_missing, /):
        if coco.is_non_existence(desired_target_state):
            ...
        target_fp = fingerprint_object(desired_target_state)
        if not prev_may_be_missing and all(
            prev == target_fp for prev in prev_possible_records
        ):
            return None
        return coco.TargetReconcileOutput(
            action=..., sink=self._sink, tracking_record=target_fp
        )
```

CocoIndex then doesn't call `reconcile()` for a declared value that is unchanged (one that `reconcile()` above would return `None` for) so an update where most values are unchanged costs almost nothing per value. `reconcile()` is still called for new, changed, and removed target states, and whenever `prev_may_be_missing` is `True`.

Only set it when both hold:

- The tracking record is `fingerprint_object(desired_target_state)` itself — not a fingerprint of a part of the value or of a derived value, and not wrapped in another type.
- An unchanged fingerprint means there is nothing to do.

The attribute has no effect on a container handler, whose `reconcile()` always runs: its sink's `child_handler` factory builds the child handler from the action it returns.

`reconcile()` must keep its own comparison: it is still called for values that aren't plain data (anything other than `None`, `bool`, `int`, `float`, `str`, `bytes`, and `list` / `tuple` / `dict`-with-`str`-keys of those), unchanged or not.

</Lang>

<RustNote>
The `TargetHandler` trait has no `tracks_value_fingerprint` flag: `reconcile` runs for every declared target state, so it keeps its own comparison and returns `Ok(None)` for an unchanged value.
</RustNote>

### Shared action sinks

If all instances of a handler use the same action logic, create a shared sink.<Lang only="python"> The action function must accept `context_provider` as its first argument:</Lang><Lang only="rust"> Build it once, store it in the handler, and return `self.sink.clone()` from each `reconcile`, as `RowHandler` [above](#step-2-implement-the-handler) does: a clone keeps the sink's identity, so the engine applies the actions of every target state that returned it in one call.</Lang>

<Lang only="python">

```python
import cocoindex as coco

def _apply_actions(
    context_provider: coco.ContextProvider, actions: Sequence[_MyAction]
) -> None:
    ...

# Module-level shared sink
_shared_sink = coco.TargetActionSink.from_fn(_apply_actions)

class _MyHandler(coco.TargetHandler[...]):
    def reconcile(self, ...):
        return coco.TargetReconcileOutput(
            action=...,
            sink=_shared_sink,  # Reuse the same sink
            tracking_record=...,
        )
```

</Lang>

## Complete example: local file system

Here's a simplified version of the `localfs` connector showing the complete pattern.

```python
from __future__ import annotations
import pathlib
from dataclasses import dataclass
from typing import Collection, NamedTuple, Sequence
import cocoindex as coco
from cocoindex.connectorkits.fingerprint import fingerprint_bytes


# Types
_FileContent = bytes
_FileFingerprint = bytes


class _FileAction(NamedTuple):
    path: pathlib.Path
    content: _FileContent | None  # None = delete


@dataclass(frozen=True, slots=True)
class _FileTrackingRecord:
    fingerprint: _FileFingerprint


# Action execution
def _apply_actions(context_provider: coco.ContextProvider, actions: Sequence[_FileAction]) -> None:
    for action in actions:
        if action.content is None:
            action.path.unlink(missing_ok=True)
        else:
            action.path.parent.mkdir(parents=True, exist_ok=True)
            action.path.write_bytes(action.content)


_file_sink = coco.TargetActionSink[_FileAction].from_fn(_apply_actions)


# Handler
class _FileHandler(coco.TargetHandler[_FileContent, _FileTrackingRecord]):
    __slots__ = ("_base_path",)
    _base_path: pathlib.Path

    def __init__(self, base_path: pathlib.Path):
        self._base_path = base_path

    def reconcile(
        self,
        key: coco.StableKey,
        desired_target_state: _FileContent | coco.NonExistenceType,
        prev_possible_records: Collection[_FileTrackingRecord],
        prev_may_be_missing: bool,
        /,
    ) -> coco.TargetReconcileOutput[_FileAction, _FileTrackingRecord] | None:
        path = self._base_path / key

        if coco.is_non_existence(desired_target_state):
            if not prev_possible_records and not prev_may_be_missing:
                return None
            return coco.TargetReconcileOutput(
                action=_FileAction(path=path, content=None),
                sink=_file_sink,
                tracking_record=coco.NON_EXISTENCE,
            )

        target_fp = fingerprint_bytes(desired_target_state)

        if not prev_may_be_missing and all(
            prev.fingerprint == target_fp for prev in prev_possible_records
        ):
            return None

        return coco.TargetReconcileOutput(
            action=_FileAction(path=path, content=desired_target_state),
            sink=_file_sink,
            tracking_record=_FileTrackingRecord(fingerprint=target_fp),
        )
```
