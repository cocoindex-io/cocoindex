CocoIndex isolates component failures and provides APIs for observing errors, handling interrupted updates, and reacting to failures in production.

For a quick overview of failure isolation and the two-phase model, see [What happens when a component fails](../programming_guide/processing_component#what-happens-when-a-component-fails) in the Processing Component guide.

## The guiding principle

**Whether a CocoIndex call <Lang only="python">raises</Lang><Lang only="rust">returns an error</Lang> on failure depends on what's on the critical path for the call to finish and return.** Things on that path that fail surface as <Lang only="python">exceptions</Lang><Lang only="rust">errors</Lang>; things off that path don't.

<Lang only="python">

| API | What it takes to return | Raises on failure? |
|---|---|---|
| `coco.mount`, `coco.mount_each`, `LiveComponentOperator.update`/`.delete` | the work is *scheduled* (returns a handle) | **No** — execution runs in the background |
| `await handle.ready()` (any of the above) | reaches *ready state* | **No by default** — logged at `ERROR`; opt into propagation by installing a handler that raises |
| `await LiveComponentOperator.update_full()` | reaches *ready state* of the full cycle | **No by default** — same shape as `handle.ready()` |
| `await coco.use_mount(...)` | the inner component's *value* is produced | **Yes** — component success is on the critical path |
| `await app.drop()` (and `cocoindex drop`) | GC succeeds at *every* level | **Yes**, at any depth — leaking target state would otherwise go silent |

</Lang>

<Lang only="rust">

{/* Rust: rust/sdk/cocoindex/src/ctx.rs (Ctx::mount, mount_each, scope, use_mount_each), src/live_component.rs (LiveComponentOperator), src/app.rs (App::drop_state) */}

| API | What it takes to return | Returns an error on failure? |
|---|---|---|
| `ctx.mount` / `mount!`, `ctx.mount_each` / `mount_each!`, `LiveComponentOperator::start_update` / `start_delete` | the work is *scheduled* (returns a handle) | **No** — execution runs in the background |
| `handle.ready().await` (any of the above) | reaches *ready state* | **No by default** — logged at `ERROR`; opt into propagation by installing a handler that returns `Err` |
| `LiveComponentOperator::update_full`, `update`, `delete` | reaches *ready state* of the full cycle or the child | **No by default** — same shape as `handle.ready()` |
| `ctx.scope` / `use_mount!`, `ctx.use_mount_each` / `use_mount_each!` | the inner component's *value* is produced | **Yes** — component success is on the critical path |
| `app.drop_state().await` (and `cocoindex drop`) | GC succeeds at *every* level | **Yes**, at any depth — leaking target state would otherwise go silent |

</Lang>

**Why `ready`/`update_full` tolerate errors by default:** `handle.ready()` is usually not awaited (callers spawn many mounts in a loop and rely on the parent waiting for its children), so <Lang only="python">raising into nobody</Lang><Lang only="rust">an error returned to nobody</Lang> would silently disappear. Logging the failure gives operators a signal regardless. The same applies to `update_full` — a periodic refresh that died on the first cycle failure would be worse than one that logs and retries on the next tick.

<Lang only="python">

**Why `app.drop` raises at every level:** clearing tracking records is only safe if every component's delete actually ran its sink calls. If a descendant delete silently fails, `await app.drop()` would return Ok while target state is still live in your database — a leak. So failures at any depth surface as an exception.

</Lang>

<Lang only="rust">

**Why `app.drop_state` fails at every level:** clearing tracking records is only safe if every component's delete actually ran its sink calls. If a descendant delete silently fails, `app.drop_state()` would return `Ok` while target state is still live in your database — a leak. So failures at any depth surface as an error.

</Lang>

## How to opt into propagation

<Lang only="python">

Install an exception handler (described below). A handler that **returns normally** swallows; a handler that **raises** propagates through `handle.ready()` (or `update_full()`) up to your awaiting code. For `app.drop`, propagation is built in — you don't need to install anything.

[Live components](./live_component) follow the same principle: their `update`/`delete`/`update_full` calls route failures through this chain with `mount_kind="process_live"`. The operator also exposes [`report_exception(exc)`](./live_component#report_exception) for surfacing errors raised in `process_live`'s body that aren't already routed by `update`/`delete`/`update_full`.

</Lang>

<Lang only="rust">

Install an exception handler (described below). A handler that returns **`Ok(())`** swallows; a handler that returns **`Err(_)`** propagates through `handle.ready()` (or `update_full()`) up to your awaiting code. For `app.drop_state`, propagation is built in — you don't need to install anything.

[Live components](./live_component) follow the same principle: their `update_full`, `update` and `delete` calls route failures through this chain, with `mount_kind` set to `UpdateFull`, `Update` or `Delete`.

</Lang>

<RustNote>
The Rust `LiveComponentOperator` has no `report_exception`: return the error from `process_live` instead.
</RustNote>

## Processing and submit phases

CocoIndex processes each component in two phases:

1. **Processing** — runs your function, declares target states in memory. This phase is side-effect-free. If it fails (e.g., a parsing error, an API timeout), no writes were attempted.
2. **Submit** — writes changes to target backends. This phase only runs after processing completes successfully.

This separation means a processing failure never leaves partial data in your targets.

## Interrupted updates and recovery

An update can be interrupted by various events: a process kill (SIGKILL), Ctrl+C (SIGINT), an unhandled <Lang only="python">exception</Lang><Lang only="rust">error</Lang>, or a target backend failure during submit.

**What state is left behind?**

CocoIndex's internal database (LMDB) uses transactions, so its own state is always consistent even after a crash. CocoIndex tracks all possible states a target could be in — if an update is interrupted partway through a commit, both the old and new states are retained as possibilities. This ensures no state is ever lost.

**Recovery is automatic.** On the next app update, CocoIndex computes the current desired state and reconciles against all possible previous states. The target connector converges the target to the correct state regardless of whether the previous commit partially succeeded or never ran.

For details on how target handlers deal with multiple possible previous states after an interruption, see [Custom Target Connector — Handle multiple previous states](./custom_target_connector#handle-multiple-previous-states).

## Exception handlers

<Lang only="python">

For background-mounted components (`mount()` and `mount_each()`), you can register **exception handlers** to observe or react to failures — for example, to send alerts, record metrics, or implement custom logic.

CocoIndex supports two levels of exception handlers:

- **Global (environment-level)**: registered once in your lifespan function; applies to all background mounts in the environment.
- **Scoped**: an async context manager that applies to all `mount()` / `mount_each()` calls made within it.

:::note
Exception handlers only apply to `mount()` and `mount_each()`. `use_mount()` propagates errors directly to the caller since the parent has an explicit dependency on the result.
:::

</Lang>

<Lang only="rust">

For background-mounted components (`ctx.mount` / `mount!`, `ctx.mount_each` / `mount_each!`, live components and `ctx.auto_refresh`), you can register **exception handlers** to observe or react to failures — for example, to send alerts, record metrics, or implement custom logic.

CocoIndex supports two levels of exception handlers:

- **Global (environment-level)**: registered once with `EnvironmentBuilder::exception_handler`, usually in your lifespan function; applies to all background mounts in the environment.
- **Scoped**: `ctx.with_exception_handler(handler)` returns a scoped `Ctx`; the handler applies to the background mounts made from that `Ctx`. `ctx.mount_live_with_handler` attaches a handler to one live component.

A handler is `Fn(&Error, &ExceptionContext) -> Result<()>`: return `Ok(())` to swallow the failure, `Err(_)` to propagate it.

:::note
Exception handlers only apply to background mounts. `ctx.scope` / `use_mount!` and `use_mount_each!` return the child's error directly to the caller, since the parent has an explicit dependency on the result.
:::

</Lang>

### Global exception handler

Register a handler inside your <Lang only="python">`@coco.lifespan` function using `builder.set_exception_handler()`</Lang><Lang only="rust">`#[cocoindex::lifespan]` function using `builder.exception_handler(...)`</Lang>:

{/* Rust: rust/sdk/cocoindex/tests/mount.rs (temp_app_with_handler), rust/sdk/cocoindex/src/app.rs (EnvironmentBuilder::exception_handler) */}
<LangTabs>
<Fragment slot="python">

```python
import cocoindex as coco

@coco.lifespan
def lifespan(builder: coco.EnvironmentBuilder):
    def on_error(exc: BaseException, ctx: coco.ExceptionContext) -> None:
        print(f"[{ctx.env_name}] {ctx.mount_kind} failed at {ctx.stable_path}: {exc}")

    builder.set_exception_handler(on_error)
    yield
```

</Fragment>
<Fragment slot="rust">

```rust
#[cocoindex::lifespan]
async fn lifespan(builder: EnvironmentBuilder) -> Result<EnvironmentBuilder> {
    Ok(builder.exception_handler(|err, exc| {
        println!("[{}] {:?} failed at {}: {err}", exc.env_name, exc.mount_kind, exc.stable_path);
        Ok(())
    }))
}
```

The same method works on an `Environment::builder()` you build yourself.

</Fragment>
</LangTabs>

This replaces the default "log error" behavior for all background mounts in the environment.

### Scoped exception handler

<Lang only="python">Use `coco.exception_handler()` as an async context manager to apply a handler to a specific dynamic scope:</Lang><Lang only="rust">Use `ctx.with_exception_handler(handler)` to get a `Ctx` whose background mounts go through the handler first:</Lang>

{/* Rust: rust/sdk/cocoindex/tests/mount.rs (scoped_handler_applies_only_to_mounts_from_the_scoped_ctx) */}
<LangTabs>
<Fragment slot="python">

```python
@coco.fn
async def process_all(files):
    def on_error(exc: BaseException, ctx: coco.ExceptionContext) -> None:
        print(f"Failed processing {ctx.stable_path}: {exc}")

    async with coco.exception_handler(on_error):
        for f in files:
            await coco.mount(coco.component_subpath(str(f.path)), process_file, f)
```

</Fragment>
<Fragment slot="rust">

```rust
#[cocoindex::function]
async fn process_all(ctx: &Ctx, files: Vec<FileEntry>) -> Result<()> {
    let scoped = ctx.with_exception_handler(|err, exc| {
        println!("Failed processing {}: {err}", exc.stable_path);
        Ok(())
    });
    for file in files {
        let key = file.relative_path().display().to_string();
        scoped
            .mount(&key, move |child| async move { process_file(&child, file).await })
            .await?;
    }
    Ok(())
}
```

Only mounts made from `scoped` see the handler. A mount made from the unscoped `ctx` goes to the global handler.

</Fragment>
</LangTabs>

<Lang only="python">

The handler applies to all `mount()` / `mount_each()` calls within the `async with` block, including those in nested functions called from within the block, and to every item of a `mount_each()` whether it iterates a collection or a [`LiveMapView` / `LiveMapFeed`](./live_component#livemapfeed-and-livemapview).

It does not reach the mounts those components make themselves: a component's own `mount()` / `mount_each()` calls start from the global handler, plus any handler the component scopes itself. To observe the failures of components at any depth, register a global handler.

</Lang>

<Lang only="rust">

The handler applies to every background mount made from the scoped `Ctx` (or a `Ctx` derived from it, for example with `with_subpath`), including every item of a `mount_each` and every child of a live component mounted from it.

</Lang>

<RustNote>
A child component's `Ctx` inherits the handler chain of the `Ctx` it was mounted from, so a handler installed with `ctx.with_exception_handler` also sees the failures of the mounts that child makes itself, at any depth. In Python, a scoped handler does not reach the mounts those components make themselves. The global handler is the outermost entry of every chain.
</RustNote>

### What `exc` is

Handlers receive the same exception object that a foreground call such as `await coco.use_mount(...)` would raise for the same failure:

- **Python-originated failures** (your component, or a target connector, raised) arrive as the original exception. `type(exc)` is what was raised, `exc.__traceback__` is intact, and `exc.__cause__` / `exc.__context__` are preserved. Route by type with `isinstance`; render the traceback with `traceback.format_exception(exc)` or `logger.error(..., exc_info=exc)`.
- **Engine-native failures** map to Python types: client-side misuse becomes `ValueError`, cooperative deadline expiry becomes `coco.DeadlineExceededError`, and internal engine errors become `RuntimeError`. One family of client errors has its own `ValueError` subclass, `coco.AlreadyDeclaredError`: something declared a second time within one run, where the first declaration is final (a target state key, a `use_state` key, a child component path, an app name). Catch it to branch on that case; `except ValueError` still catches it. The engine never delivers cancellation of the component itself to handlers.

An exception raised by a handler keeps its type as well: `await handle.ready()` raises exactly what the last handler in the chain raised, so `except MyDeadLetterError:` or `except coco.DeadlineExceededError:` work as expected on the awaiting side.

Earlier releases handed every component failure to handlers as a `RuntimeError` whose message embedded the formatted traceback, and re-wrapped handler-raised exceptions the same way. A handler that checked `isinstance(exc, RuntimeError)` or parsed `str(exc)` for the traceback should switch to the checks above.

</Lang>

<Lang only="rust">

### What `err` is

Handlers receive the same `Error` that a foreground call such as `ctx.scope(...)` would return for the same failure. A failure your own code returned with `Error::user(..)` arrives as `Error::User(inner)`; `inner.downcast_ref::<T>()` recovers its type. `Error::DeadlineExceeded` is the cooperative deadline. An error a handler returns keeps its value as well: `handle.ready()` returns exactly what the last handler in the chain returned.

</Lang>

### `ExceptionContext` fields

<Lang only="python">

Your handler receives an `ExceptionContext` dataclass with information about the failure:

| Field | Type | Description |
|---|---|---|
| `env_name` | `str` | Name of the CocoIndex environment |
| `stable_path` | `str` | Full stable path of the failing component |
| `processor_name` | `str \| None` | Name of the processor (best-effort) |
| `mount_kind` | `"mount" \| "mount_each" \| "delete_background" \| "process_live"` | Source of the failure: `"mount"`/`"mount_each"` for background build errors, `"delete_background"` for sweep-driven deletions, `"process_live"` for exceptions surfaced from a live component's `process_live` via `LiveComponentOperator.report_exception` (e.g. a failed `coco.auto_refresh` cycle) |
| `parent_stable_path` | `str \| None` | Stable path of the parent component |
| `is_background` | `bool` | Always `True` for exception handler invocations |
| `source` | `"component" \| "handler"` | `"component"` for the original failure; `"handler"` if a handler itself raised |
| `original_exception` | `BaseException \| None` | The original component exception, set only when `source == "handler"` |

</Lang>

Your handler receives an `ExceptionContext` struct with information about the failure:

| Field | Type | Notes |
|---|---|---|
| `env_name` | `String` | Name of the app the failing component runs under |
| `stable_path` | `String` | Stable path of the failing component |

### Handler stacking and fallback

Handlers are stacked: the most specific (innermost) handler runs first.

<Lang only="python">

If the innermost handler raises an exception, the next outer handler is called with that new exception. In this case `ctx.source` is `"handler"` and `ctx.original_exception` holds the original component error.

</Lang>

<Lang only="rust">

If the innermost handler returns `Err`, the next outer handler is called with that new error. In this case `exc.source` is `ExceptionSource::Handler`.

</Lang>

This continues up the stack. If every handler <Lang only="python">raises, the last handler's exception</Lang><Lang only="rust">returns `Err`, the last handler's error</Lang> propagates through `handle.ready()` (see [How to opt into propagation](#how-to-opt-into-propagation)). If no handler is registered, CocoIndex falls back to the built-in behavior: logging the error at `ERROR` level, with no crash.

{/* Rust: rust/sdk/cocoindex/tests/mount.rs (scoped handler then global handler with source == Handler) */}
<LangTabs>
<Fragment slot="python">

```python
@coco.lifespan
def lifespan(builder: coco.EnvironmentBuilder):
    builder.settings.db_path = "..."

    def global_handler(exc: BaseException, ctx: coco.ExceptionContext) -> None:
        if ctx.source == "handler":
            # A handler itself failed — exc is the handler's exception,
            # ctx.original_exception is the original component error.
            print(f"Handler error: {exc}; original: {ctx.original_exception}")
        else:
            print(f"Component error: {exc}")

    builder.set_exception_handler(global_handler)
    yield

@coco.fn
async def _root() -> None:
    def inner_handler(exc: BaseException, ctx: coco.ExceptionContext) -> None:
        print(f"inner: {exc}")
        raise RuntimeError("inner handler failed")  # falls through to global_handler

    async with coco.exception_handler(inner_handler):
        await coco.mount(coco.component_subpath("child"), _child)
```

</Fragment>
