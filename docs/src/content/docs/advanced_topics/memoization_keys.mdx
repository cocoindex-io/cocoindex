CocoIndex detects [logic, input, and context changes](../programming_guide/function#change-detection) to decide whether it can reuse a memo. It fingerprints function arguments, [`deps`](../programming_guide/function#deps) values, and [context values](../programming_guide/context#change-detection) with `detect_change=True` through the same pipeline. Most types work automatically. You can customize fingerprinting and validation with:

- **Memoization keys** — how to control what CocoIndex uses as the fingerprint for your objects.
- **Memo states** — how to add post-fingerprint validation to check freshness beyond simple equality.

The Rust SDK keeps the same split between **identity** and **freshness**, through one trait: `MemoInput`. Its `write_memo_key` method is the key; its optional `memo_state` method is the state. The arguments of a `#[cocoindex::function(memo)]` function must implement `MemoInput`, unless `memo_key(..)` transforms or skips them. A `context_key!` value takes part only when the key is declared with `detect_change`.

## How data fingerprinting works

For each data value (function argument, `deps` value, or context value), CocoIndex derives a canonical form with this precedence:

1. If the object implements **`__coco_memo_key__()`**, CocoIndex uses its return value.
2. Otherwise, if you registered a **memo key function** for the object's type, CocoIndex uses that.
3. Otherwise, CocoIndex falls back to structural canonicalization for a limited set of primitives/containers.

The following types are handled automatically (no custom key needed):

- **Primitives**: `None`, `bool`, `int`, `float`, `str`, `bytes`, `bytearray`, `memoryview`
- **Containers**: `list`, `tuple`, `dict`, `set`, `frozenset` (recursively canonicalized)
- **Dataclass instances**: all fields included in definition order
- **Pydantic v2 models**: all fields included
- **Class objects** (`type`): identified by module and qualified name
- **Other picklable objects**: used as a fallback via `pickle`

In Rust there is no fallback: a type is a memo input when it implements `MemoInput`. The SDK implements it for the primitives (`bool`, the integer and float types, `char`, `String`, `str`), `PathBuf` / `Path`, `Duration`, `SystemTime`, `uuid::Uuid`, `Fingerprint`, `bytes::Bytes` and `serde_json::Value`; for Chrono date and time values with the `chrono` feature and for `rust_decimal::Decimal` with the `rust_decimal` feature (a connector feature turns these on). `Option`, arrays, slices, `Vec`, tuples, maps, sets, `Box` and `Arc` compose their children's `MemoInput`. For your own structs and enums, derive it:

{/* Rust: examples/rust/conversation_to_knowledge/src/models.rs */}
```rust
#[derive(Clone, Debug, Serialize, Deserialize, cocoindex::MemoInput)]
pub struct Utterance {
    pub speaker: String,
    pub text: String,
}

#[derive(Clone, Debug, Serialize, Deserialize, cocoindex::MemoInput)]
pub struct SessionTranscript {
    pub utterances: Vec<Utterance>,
    pub yt_channel: String,
    pub yt_title: String,
    pub yt_description: Option<String>,
}
```

The derive visits every field recursively, in order; the type itself does not need `Serialize`. Moving or renaming a derived type, or renaming one of its named fields, changes its identity and causes a one-time cache miss. A `Vec<u8>` is hashed element by element like any `Vec<T>`: for a large byte buffer, use `bytes::Bytes` for bulk hashing, or pass a precomputed `Fingerprint` (`cocoindex::Fingerprint`) when the content is already hashed.

The canonical forms are combined into a deterministic fingerprint. If the fingerprint matches a cached entry, the cached result is reused — unless **memo states** indicate it's stale (see [Memo state validation](#memo-state-validation) below).

## Customizing the memoization key

### Define `__coco_memo_key__` (when you control the type)

Implement a method on your class that returns a stable, deterministic value:

{/* Rust: examples/rust/conversation_to_knowledge/src/clients.rs (impl MemoInput for LlmClient) */}
<LangTabs>
<Fragment slot="python">

```python
class MyType:
    def __coco_memo_key__(self) -> object:
        # Return small primitives / tuples.
        return (...)
```

</Fragment>
<Fragment slot="rust">

```rust
impl MemoInput for LlmClient {
    fn write_memo_key(&self, writer: &mut cocoindex::memo::MemoKeyWriter<'_>) -> Result<()> {
        // Write small serializable values: here, the model name.
        writer.write(&self.model)
    }
}
```

`writer.write(&value)` takes any `Serialize` value; `writer.write_input(&value)` nests another `MemoInput`. Add `#[cocoindex::async_trait]` to the impl when it also defines the async `memo_state` method.

Return something that uniquely identifies the **semantic content** your function depends on:

- **Good**: small tuples of primitives, e.g. `(stable_id, version)`
- **Bad**: memory addresses, unstable UUIDs, open file handles, `datetime.now()`, or large raw payloads

### Register a key function (when you don't control the type)

If you can't add `__coco_memo_key__` (stdlib / third-party types), register a handler:

```python
from pathlib import Path
from cocoindex import register_memo_key_function

def path_key(p: Path) -> object:
    p = p.resolve()
    st = p.stat()
    return (str(p), st.st_mtime_ns, st.st_size)

register_memo_key_function(Path, path_key)
```

- Registration is **MRO-aware**: if you register both a base class and a subclass, the **most specific** match wins.
- Your key function must return the same kinds of stable objects as `__coco_memo_key__` (small primitives/tuples).

The Rust SDK has no registry. Rust's orphan rules stop a crate from implementing `MemoInput` for a type it does not own, so wrap a third-party type in a local newtype and implement the trait on that, or transform the argument at the call site with `memo_key(..)` (next section):

{/* Rust: shape of examples/rust/conversation_to_knowledge/src/clients.rs (impl MemoInput), rust/sdk/cocoindex/src/memo.rs module docs */}
```rust
struct ForeignId(third_party::Id);

impl cocoindex::MemoInput for ForeignId {
    fn write_memo_key(
        &self,
        writer: &mut cocoindex::memo::MemoKeyWriter<'_>,
    ) -> cocoindex::Result<()> {
        writer.write(&self.0.to_string())
    }
}
```

### Override at the call site with `memo_key=`

The two approaches above are **type-level**: every memoized function sees the same fingerprint for a given object. To customize fingerprinting **only for a specific function**, pass `memo_key=` to `@coco.fn` (or `@coco.fn.as_async`). It maps parameter names to either a callable (transform the value before fingerprinting) or `None` (exclude the parameter entirely).

{/* Rust: rust/sdk/cocoindex/tests/pipeline.rs (memo_key_transform_and_skip_for_function_macro) */}
<LangTabs>
<Fragment slot="python">

```python
@coco.fn(memo=True, memo_key={"entry": lambda e: (e.name, e.version), "extra": None})
def transform(entry: SourceDataEntry, extra: str) -> str:
    ...
```

</Fragment>
<Fragment slot="rust">

```rust
fn entry_name_version(entry: &Entry) -> (String, u32) {
    (entry.name.clone(), entry.version)
}

#[cocoindex::function(memo, memo_key(entry = entry_name_version, extra = skip))]
async fn transform_entry(ctx: &Ctx, entry: &Entry, extra: &String) -> Result<String> {
    Ok(format!("{}:{extra}", entry.content))
}
```

`memo_key(..)` lists parameters by name: `name = transform_fn` fingerprints the function's return value in place of the argument, `name = skip` leaves the argument out. A skipped parameter needs only `Clone`, not `MemoInput`. The attribute requires `memo`.

</Fragment>
</LangTabs>

Each entry in `memo_key`:

- **Callable** — applied to the argument; its return value is fingerprinted in place of the original. Semantically the same as `__coco_memo_key__()` on the type, but scoped to this one function. Useful when the type's default fingerprint is correct everywhere *else*, and only this function should treat the argument differently.
- **`None`** — the parameter is excluded from the memo key. Changing its value never invalidates the cache. Useful for arguments that don't affect the result (logger handles, debug flags, request-scoped context that isn't part of the computation).
- **Not listed** — the parameter is fingerprinted normally (type-level `__coco_memo_key__`, registered handler, or default canonicalization).

It works for every parameter kind:

- **Positional / keyword parameters** — referenced by name.
- **`self`** — methods can pass `memo_key={"self": lambda self: self.prefix}` to memoize on selected instance state instead of the whole instance. Changes to other attributes on the same instance won't invalidate the memo.
- **`*args`** — name the varargs parameter; the callable receives the full tuple and must return a tuple. `None` excludes all variadic positional arguments.
- **`**kwargs`** — name the varkw parameter; the callable receives a dict and must return a dict. `None` excludes all variadic keyword arguments.

`memo_key` is validated at decoration time: unknown parameter names raise `ValueError`, and values that are neither callable nor `None` raise `TypeError`. In Rust the macro checks the names at compile time. A transform also suppresses the argument type's `memo_state` validation; use a newtype when the freshness check must stay.

**Target handles in Rust.** A target handle is where output goes, not an input of the computation, so it is not `MemoInput`. `DirTarget` and the Postgres, SQLite, Doris, SurrealDB, LanceDB, Neo4j and FalkorDB table and relation targets are `Serialize` instead: as an argument of a memoized function or of `mount!`, `use_mount!` or `mount_each!`, one is keyed by its stable key, as in Python. The other connectors' handles are only `Clone`. Skip those in the memo key; you can skip any handle the same way:

{/* Rust: rust/sdk/cocoindex/tests/pipeline.rs (target_state_of_nested_memo_survives_outer_memo_hit) */}
```rust
#[cocoindex::function(memo, memo_key(target = skip))]
async fn declare_nested(ctx: &Ctx, target: DirTarget, content: String) -> Result<()> {
    target.declare_file(ctx, "nested.txt", content.as_bytes())
}
```

:::tip[Picking the right tool]
- You control the type and the fingerprint is the same wherever it's used → **`__coco_memo_key__`**.
- You don't control the type but want a global handler → **`register_memo_key_function`**.
- Only *this* function should treat an argument specially (transform or skip it) → **`memo_key=`**.
:::

## Memo state validation

Sometimes fingerprint matching alone isn't enough to decide whether a cached result is valid. For example:

- **Multi-level validation**: for files, check the modified time first (cheap), and only read the file for a content fingerprint when the time doesn't match.
- **Async validation**: for an S3 object, send a HEAD request to check freshness — an inherently async operation.
- **Stateful validation**: for HTTP resources, store the last fetch time and use `If-Modified-Since` on the next run.

Memo state validation addresses these by letting you attach a **state function** to your objects. It runs *after* a fingerprint match, giving you a chance to check freshness before the cached result is reused.

### How it works

When CocoIndex finds a fingerprint match, it calls each state function with the stored state from the previous run:

1. **First run** (no previous state): `prev_state` is `coco.NON_EXISTENCE`. Use `coco.is_non_existence(prev_state)` to detect this.
2. **Subsequent runs**: `prev_state` is whatever you returned last time.

Your state function returns a `coco.MemoStateOutcome(state=..., memo_valid=...)`:

- **`state`** — the current state value. CocoIndex stores it for the next run.
- **`memo_valid`** (`bool`, defaults to `False`) — whether the cached result is still valid.

This decouples "has the state changed?" from "can we reuse the memo?":

- `MemoStateOutcome(state=new_state)` → cache is invalid (default). Function re-executes, new state is stored. On the first run (no previous cache), simply return the initial state without setting `memo_valid`.
- `MemoStateOutcome(state=same_state, memo_valid=True)` → nothing changed, cached result reused, no state update needed.
- `MemoStateOutcome(state=new_state, memo_valid=True)` → state changed but cached result is still valid (e.g. mtime changed but content hash unchanged). The new state is persisted so the next run uses the updated state.

### Define `__coco_memo_state__` (when you control the type)

:::info[Type annotations]
Annotate the `prev_state` parameter with its expected type (matching what you return in `MemoStateOutcome(state=...)`) so CocoIndex can properly reconstruct stored state values. See [Serialization](../programming_guide/serialization) for details on supported types.
:::

Add a `__coco_memo_state__` method alongside `__coco_memo_key__`. In Rust, implement the async `memo_state` method of `MemoInput` beside `write_memo_key`; the Rust tab shows the shape with a version number as the state.

{/* Rust: rust/sdk/cocoindex/tests/pipeline.rs (type_owned_context_memo_state_invalidates_cached_function) */}
<LangTabs>
<Fragment slot="python">

```python
import os
import hashlib
import time
from pathlib import Path
import cocoindex as coco

def settled_mtime(st: os.stat_result) -> int | None:
    # Only an mtime older than any filesystem's timestamp tick (FAT: 2 s) at the read
    # can vouch for the content later (see the note below).
    return st.st_mtime_ns if time.time_ns() - st.st_mtime_ns >= 3_000_000_000 else None

class LocalFile:
    def __init__(self, path: Path) -> None:
        self.path = path

    def __coco_memo_key__(self) -> object:
        # Identity only — which file is it?
        return str(self.path.resolve())

    def __coco_memo_state__(self, prev_state: tuple[int | None, str] | coco.NonExistenceType) -> coco.MemoStateOutcome:
        st = os.stat(self.path)
        if coco.is_non_existence(prev_state):
            # First run — compute initial state (memo_valid defaults to False,
            # which is fine since there's no previous cache to reuse)
            content_hash = hashlib.sha256(self.path.read_bytes()).hexdigest()
            return coco.MemoStateOutcome(state=(settled_mtime(st), content_hash))

        prev_mtime, prev_hash = prev_state
        if st.st_mtime_ns == prev_mtime:
            # mtime unchanged, and it was settled when recorded — reusable without reading
            return coco.MemoStateOutcome(state=prev_state, memo_valid=True)
        # mtime changed, or was not settled — read content and check hash
        content_hash = hashlib.sha256(self.path.read_bytes()).hexdigest()
        return coco.MemoStateOutcome(state=(settled_mtime(st), content_hash), memo_valid=content_hash == prev_hash)
```

:::note[An equal mtime and the timestamp tick]
Filesystems stamp modification times in ticks (NTFS follows the system timer, HFS+ and ext3 keep whole seconds, FAT two), and a rewrite in the same tick as the read keeps the old mtime. An equal mtime therefore only shows the content is unchanged if the mtime was already older than any tick when the content was read, which is why the example records `None` in place of a recent mtime. Built-in `FileLike` objects do the same.
:::

</Fragment>

```rust
struct Resource {
    id: &'static str,
    version: u64,
}

#[cocoindex::async_trait]
impl cocoindex::MemoInput for Resource {
    fn write_memo_key(
        &self,
        writer: &mut cocoindex::memo::MemoKeyWriter<'_>,
    ) -> cocoindex::Result<()> {
        // Identity only: which resource is it?
        writer.write(&self.id)
    }

    async fn memo_state(
        &self,
        previous: Option<&cocoindex::memo::MemoStateValue>,
    ) -> cocoindex::Result<Option<cocoindex::memo::MemoStateDecision>> {
        // `previous` is `None` on the first run.
        let previous_version = previous.and_then(|state| state.deserialize::<u64>().ok());
        Ok(Some(cocoindex::memo::MemoStateDecision::new(
            &self.version,
            previous_version == Some(self.version),
        )?))
    }
}
```

`memo_state` runs after an identity match. `MemoStateDecision::new(&state, memo_valid)` is the Rust `MemoStateOutcome`: the state to store, and whether the cached result is still valid. Return `Ok(None)` for a value that needs no validation (the default). A stored state that no longer deserializes counts as a cache miss, not an error.

</Fragment>
</LangTabs>

:::tip[Keys vs states for files]
Without state validation, you'd include `mtime` and `size` directly in the memo key:
```python
def __coco_memo_key__(self):
    st = os.stat(self.path)
    return (str(self.path.resolve()), st.st_mtime_ns, st.st_size)
```
This works for simple cases, though like the mtime shortcut above it misses a same-size rewrite within one timestamp tick. State validation becomes useful when you need multi-level checks (e.g. check mtime first, then content hash only if it differs), async operations, or stored metadata like ETags. With the `MemoStateOutcome` return, you can update the state (e.g. new mtime) without invalidating the cache when the content hasn't actually changed.
:::

### Register a state function (when you don't control the type)

Pass a `state_fn` keyword argument to `register_memo_key_function`. The state function receives the object as its first argument and `prev_state` as its second. Annotate `prev_state` with the expected type:

```python
from pathlib import Path
from cocoindex import register_memo_key_function

def path_key(p: Path) -> object:
    return str(p.resolve())

def path_state(p: Path, prev_state: tuple[int, int] | coco.NonExistenceType) -> coco.MemoStateOutcome:
    st = p.stat()
    new_state = (st.st_mtime_ns, st.st_size)
    memo_valid = not coco.is_non_existence(prev_state) and new_state == prev_state
    return coco.MemoStateOutcome(state=new_state, memo_valid=memo_valid)

register_memo_key_function(Path, path_key, state_fn=path_state)
```

In Rust, the newtype that carries `write_memo_key` for a foreign type carries `memo_state` too.

### State that depends on what the function did

By default the state stored after a re-run is the one the state function returned when it rejected the cached result, before the function ran. That fits a state read from the outside, such as a file's modification time.

Some states are only known once the function has run, for example the set of things it read. Return `recollect_after_run=True` and CocoIndex calls the state function a second time after the function body, with `NON_EXISTENCE` as on a first run, and stores that state:

```python
class Tracked:
    def __init__(self, key: str) -> None:
        self.key = key
        self.observed: list[tuple[str, int]] = []  # filled by the function

    def __coco_memo_key__(self) -> object:
        return self.key

    def __coco_memo_state__(
        self, prev_state: list[tuple[str, int]] | coco.NonExistenceType
    ) -> coco.MemoStateOutcome:
        if coco.is_non_existence(prev_state):
            # After the function ran: report what it read.
            return coco.MemoStateOutcome(state=list(self.observed))
        valid = all(current_version(name) == version for name, version in prev_state)
        return coco.MemoStateOutcome(
            state=prev_state, memo_valid=valid, recollect_after_run=True
        )
```

The flag is only read when the cached result is not reused. It applies to memoized functions; a memoized component that returns it raises an error.

The Rust SDK has no `recollect_after_run`. For reads decided while the body runs, use `ctx.use_data_dep` (see [Dependencies beyond the arguments](#dependencies-beyond-the-arguments-rust) below).

When the state is the set of things the function *read* that are not among its arguments, record each read with [`coco.use_data_dep`](../programming_guide/function#data-dependencies-datadep-and-use_data_dep) (experimental) instead: it works for components too, and validates each read on its own.

### Async state methods

A state method can return an `Awaitable`. CocoIndex handles this automatically:

- **In an async CocoIndex function**: awaitables from all state methods are gathered concurrently.
- **In a sync CocoIndex function**: if no event loop is running, CocoIndex uses `asyncio.run()`. If a loop is already running, it raises an error — switch to an async function or use `@coco.fn.as_async`.

In Rust, `memo_state` is always `async`, and the state checks of nested values run concurrently. CocoIndex stores their results as one opaque state per top-level function argument or context dependency.

```python
import cocoindex as coco

class S3Object:
    def __init__(self, bucket: str, key: str) -> None:
        self.bucket = bucket
        self.key = key

    def __coco_memo_key__(self) -> object:
        return (self.bucket, self.key)

    async def __coco_memo_state__(self, prev_state: str | coco.NonExistenceType) -> coco.MemoStateOutcome:
        etag = await self._head_object()
        memo_valid = not coco.is_non_existence(prev_state) and etag == prev_state
        return coco.MemoStateOutcome(state=etag, memo_valid=memo_valid)

    async def _head_object(self) -> str:
        ...  # boto3 / aioboto3 HEAD call
```

## Dependencies beyond the arguments (Rust)

A function's memo key covers its arguments and the context values it reads. The Rust SDK adds three ways to declare what else a result depends on. Python has the same three: [`deps`](../programming_guide/function#deps), [`LogicDep` / `use_logic_dep`](../programming_guide/function#per-call-dependencies-logicdep-and-use_logic_dep) and [`DataDep` / `use_data_dep`](../programming_guide/function#data-dependencies-datadep-and-use_data_dep).

### `version` and `deps` on the attribute

`version = N` replaces the body hash as the function's logic: bump it to invalidate every memo of the function, for example when a helper the macro cannot see has changed. `deps = <expr>` folds a value into the logic fingerprint, so every call of the function depends on it. The expression is evaluated and fingerprinted once per process, through `MemoInput`.

{/* Rust: rust/sdk/cocoindex_macros/src/lib.rs (version docs), rust/sdk/cocoindex/tests/memo_deps.rs (with_deps) */}
```rust
#[cocoindex::function(memo, version = 2)]
async fn my_fn(ctx: &Ctx, arg: &String) -> Result<String> { /* ... */ }

const PROMPT: &str = "summarize";

#[cocoindex::function(memo, deps = (PROMPT, DEPS_VALUE.load(Ordering::SeqCst)))]
async fn with_deps(_ctx: &Ctx, test: &str, x: &i64) -> Result<i64> {
    Ok(x * 2)
}
```

### `LogicDep`: a dependency decided per call

Some dependencies are known only per call: a tree walk's `visit_file` depends on the parser of *that file's* language, and a new parser release should re-run only the files it parsed. `LogicDep::new(&value)` declares such a dependency; `ctx.use_logic_dep(&dep)?` records it as part of the current call's logic. It travels like the function's own fingerprint: into a memoized caller's entry, and onward through `"full"` callers.

Construct a `LogicDep` before any component runs, never per call: a memo entry is validated against the dependencies registered at that moment, and one that is dropped at the end of a call evicts every entry that recorded it. A `static` behind `LazyLock`, forced in `main` or a lifespan, is the usual form.

{/* Rust: rust/sdk/cocoindex/tests/memo_deps.rs (release, leaf); static form from rust/sdk/SHOWCASE.md, verified against src/deps.rs */}
```rust
use std::sync::LazyLock;

static RUST_PARSER: LazyLock<LogicDep> =
    LazyLock::new(|| LogicDep::new(&("rust-parser", 2)).unwrap());

#[cocoindex::function(memo)]
async fn leaf(ctx: &Ctx, value: &str) -> Result<String> {
    ctx.use_logic_dep(&RUST_PARSER)?;
    Ok(format!("leaf: {value}"))
}
```

A `LogicDep` is itself a `MemoInput`, keyed by its fingerprint, so it can also be passed as an argument.

### `DataDep`: data the body reads while it runs (experimental)

`DataDep` is experimental: its API and semantics may change in a later release.

Logic, arguments and context values are known before a body runs. Some bodies read things decided only while they run: an agent session opens the files the model chose. `DataDep::new(name, validate)` declares such a *kind* of read with a validator; `ctx.use_data_dep(&kind, &key, &state)?` records one read as a key and the state observed. The next probe validates each record from the stored key and state alone, through the validator, so the entry can be reused even though nothing in its arguments covers the read. Construct a `DataDep` before any component runs, as with `LogicDep`; renaming a kind invalidates every entry that recorded it.

{/* Rust: rust/sdk/cocoindex/tests/memo_deps.rs (file_kind, read) */}
```rust
use cocoindex::Fingerprint;

type FileState = (u64, Fingerprint);

fn file_kind() -> DataDep<String, FileState> {
    DataDep::new("test-file", move |key: String, prev: FileState| async move {
        let path = PathBuf::from(&key);
        if !path.exists() {
            return MemoStateDecision::new(&prev, false);
        }
        let mtime = modified_nanos(&path);
        if mtime == prev.0 {
            return MemoStateDecision::new(&prev, true);
        }
        let digest = Fingerprint::from_bytes(&std::fs::read(&path)?);
        MemoStateDecision::new(&(mtime, digest), digest == prev.1)
    })
    .unwrap()
}

/// Read a file and record the read: stat *before* reading, so the recorded
/// mtime is never newer than the bytes it is paired with.
fn read(ctx: &Ctx, kind: &DataDep<String, FileState>, path: &Path) -> Result<Vec<u8>> {
    let mtime = modified_nanos(path);
    let data = std::fs::read(path)?;
    ctx.use_data_dep(
        kind,
        &path.to_string_lossy().into_owned(),
        &(mtime, Fingerprint::from_bytes(&data)),
    )?;
    Ok(data)
}
```

Recording the same kind and key with two different states in one run stores no entry: the function re-runs next time.

### Memo blocks with `ctx.memo`

`ctx.memo(&key, |ctx| async move { .. })` memoizes one block inside a function. The key is any `Serialize` value; the result must be `Serialize + Deserialize`. The closure body is not logic-tracked: when the block must invalidate after its enclosing `#[cocoindex::function]` changes, include that function's generated `__COCO_FN_HASH_<NAME>` constant in the key.

{/* Rust: rust/sdk/cocoindex/src/ctx.rs (Ctx::memo doc comment) */}
```rust
let processed = ctx.memo(&fingerprint, |ctx| async move {
    // ... expensive computation, using `ctx` for `get_key` ...
    Ok("result".to_string())
}).await?;
```

Prefer `#[cocoindex::function(memo)]` for a whole function: it builds the key from the arguments and tracks the body's logic for you.

## Preventing memoization

Some types maintain internal state that makes memoization semantically incorrect. For example, a generator that tracks call counts would produce wrong results if memoized.

In Rust, a type that does not implement `MemoInput` cannot be an argument of a memoized function: the compiler rejects it with a note that names the three ways out (derive, implement, or a `memo_key` override). Leave the trait unimplemented for a stateful type, and use `memo_key(arg = skip)` where it must be passed through.

### Inherit from `NotMemoKeyable` (when you control the type)

```python
import cocoindex as coco

class MyStatefulGenerator(coco.NotMemoKeyable):
    def __init__(self) -> None:
        self._counter = 0

    def next_value(self) -> int:
        self._counter += 1
        return self._counter
```

### Register as not memo-keyable (when you don't control the type)

```python
import cocoindex as coco
from some_library import StatefulGenerator

coco.register_not_memo_keyable(StatefulGenerator)
```

In either case, attempting to use the type as a memo key raises a clear error.

## Choosing keys and states

- **Keep keys small and deterministic**: use identifiers and versions, not full payloads. No `id(obj)`, pointer addresses, or random values.
- **Separate identity from freshness**: put stable identifiers (file path, URL, primary key) in the key. Put freshness checks (mtime, ETag, version) in the state.
- **Use state validation for expensive checks**: if freshness validation is costly (content hashing, network calls), a state function lets you do it only when the fingerprint matches, and only when a cheap pre-check (mtime) fails.
- **Use `MemoStateOutcome(state=new_state, memo_valid=True)` for cheap state updates**: when a cheap property changes (mtime) but the expensive check (content hash) confirms nothing meaningful changed, return `memo_valid=True` while updating the state. This avoids re-executing the function and avoids re-checking the expensive property next time.
- **Mark stateful types as `NotMemoKeyable`**: prevent subtle bugs from incorrect memoization of types with side effects.
