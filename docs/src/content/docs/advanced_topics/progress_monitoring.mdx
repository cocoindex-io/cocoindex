<Lang only="python">

Most runs only need the basics covered in [App](../programming_guide/app#updating-an-app): awaiting `app.update()` for the result, or the built-in stdout progress display — `report_to_stdout=True` on `app.update_blocking()` (or the CLI), or `await coco.show_progress(handle)` with the async API. `report_to_stdout` accepts a `timedelta` to set the refresh interval (`True` uses the default); `show_progress` takes a `refresh_interval` keyword.

</Lang>

<Lang only="rust">

Most runs only need the basics covered in [App](../programming_guide/app#updating-an-app): awaiting `app.update(..)` for the result, or the built-in stdout progress display — `UpdateOptions { report_to_stdout: true, .. }` on `app.update_with_options(..)`. `progress_refresh_interval: Some(duration)` sets the refresh interval (`None` uses the default). The `cocoindex update` command renders the same per-component lines on stderr when stderr is a terminal, and prints the final `[Stats]` line on stdout; `-q` / `--quiet` turns the stdout output off.

</Lang>

Use the structured progress APIs to stream progress from a daemon to a client, build a custom dashboard, or report pipeline phases separately.

## Structured update stats

<Lang only="python">

`app.update()` returns an `UpdateHandle`. Besides being awaitable, it exposes the same stats that drive the terminal display — as Python objects you can read while the update runs.

</Lang>

<Lang only="rust">

`app.start_update(f)` returns an `UpdateHandle<T>`. It starts the update at once; `handle.result().await` waits for the value. The handle exposes the same stats that drive the terminal display: `detailed_stats_snapshot()` (per-component `UpdateStats`), `stats_snapshot()` (the coarse `RunStats`), and `changed().await` to wait for the next change.

</Lang>

### Polling

<Lang only="python">

`handle.stats()` returns a snapshot of the current counters as an `UpdateStats` — or `None` before the handle has started running. It keeps working after completion, returning the final stats:

</Lang>

<Lang only="rust">

`handle.detailed_stats_snapshot()` returns a snapshot of the current counters as an `UpdateStats`. It keeps working after completion, returning the final stats:

</Lang>

<LangTabs>
<Fragment slot="python">

```python
handle = app.update()
result = await handle.result()   # run to completion
final_stats = handle.stats()     # UpdateStats with the final counters
```

</Fragment>
<Fragment slot="rust">

```rust
let mut handle = app.start_update(|ctx| async move {
    // ...
    Ok(42)
})?;

loop {
    if handle.changed().await?.is_done() {
        break;
    }
}
let final_stats = handle.detailed_stats_snapshot(); // UpdateStats with the final counters
let result = handle.result().await?;                // consumes the handle
```

`detailed_stats_snapshot()` works at any time, including before the first change. Read the final stats before `result()`, which consumes the handle.

</Fragment>
</LangTabs>

<Lang only="python">

`app.update()` starts lazily — the handle begins running on the first `await` (or `watch()`), so `stats()` returns `None` until then. To read stats *while* an update is in flight, poll `handle.stats()` from a separate task, or use `watch()` (below) to receive each change as it happens.

</Lang>

<Lang only="rust">

To read stats *while* an update is in flight, loop on `changed()` (below) and read a snapshot after each change.

</Lang>

### Streaming

<Lang only="python">

`handle.watch()` is an async iterator that yields an `UpdateSnapshot` whenever the stats change — `RUNNING` while processing, then a final `READY` snapshot carrying the result:

</Lang>

<Lang only="rust">

`handle.changed().await` waits until the stats change. It returns `Progress::Changed(version)` while the update runs, then `Progress::Done` once it terminates; `result()` then returns the value:

</Lang>

{/* Rust: rust/sdk/cocoindex/tests/detailed_stats.rs, rust/sdk/cocoindex/src/app.rs (Progress, UpdateHandle::changed) */}
<LangTabs>
<Fragment slot="python">

```python
handle = app.update()
async for snapshot in handle.watch():
    print(snapshot.stats.total.num_finished, "items processed")
    # snapshot.status is UpdateStatus.RUNNING or UpdateStatus.READY
    # snapshot.result is set on the final snapshot, when the iterator ends
```

</Fragment>
<Fragment slot="rust">

```rust
let mut handle = app.start_update(|ctx| async move {
    // ...
    Ok(())
})?;
loop {
    let progress = handle.changed().await?; // Progress::Changed(version) or Progress::Done
    let stats = handle.detailed_stats_snapshot();
    println!("{} items processed", stats.total().num_finished());
    // stats.status is UpdateStatus::Running or UpdateStatus::Ready
    if progress.is_done() {
        break;
    }
}
let result = handle.result().await?;
```

There is no snapshot object in Rust: `changed()` wakes you, and `detailed_stats_snapshot()` reads the current counters.

</Fragment>
</LangTabs>

<Lang only="python">

On a processing error, `watch()` raises the exception directly — handle it with a normal `try`/`except` around the loop.

In [live mode](../programming_guide/live_mode), `watch()` does not stop at the first `READY`: it keeps yielding `RUNNING` snapshots as live components deliver incremental updates, ending only when the app stops.

</Lang>

<Lang only="rust">

On a processing error, `changed()` and `result()` return the error.

In [live mode](../programming_guide/live_mode), the update does not terminate at the first ready state: `changed()` keeps returning `Progress::Changed` as live components deliver incremental updates, and returns `Progress::Done` only when the app stops.

</Lang>

```python
class UpdateStats:
    by_component: dict[str, ComponentStats]  # keyed by processor name
    total: ComponentStats                    # summed across all processors

class ComponentStats:
    num_execution_starts: int
    num_unchanged: int
    num_adds: int
    num_deletes: int
    num_reprocesses: int
    num_errors: int
    # derived helpers:
    num_processed: int    # unchanged + adds + deletes + reprocesses
    num_finished: int     # num_processed + num_errors
    num_in_progress: int  # max(0, execution_starts - num_finished)

class UpdateSnapshot:
    stats: UpdateStats
    status: UpdateStatus      # RUNNING | READY
    result: R | None          # set only on the final snapshot
```

</Fragment>
<Fragment slot="rust">

```rust
pub struct UpdateStats {
    pub by_component: BTreeMap<String, ComponentStats>, // keyed by processor name
    pub status: UpdateStatus,                           // Running | Ready
    pub in_groups: ComponentStats,                      // what stats groups under this scope count
}
// UpdateStats::total() sums every component, not in_groups; run_stats() derives the coarse RunStats.

pub struct ComponentStats {
    pub num_execution_starts: u64,
    pub num_unchanged: u64,
    pub num_adds: u64,
    pub num_deletes: u64,
    pub num_reprocesses: u64,
    pub num_errors: u64,
}
// Derived helpers: num_processed(), num_finished(), num_in_progress(), has_errors().

    Changed(u64), // the update advanced; carries a monotonic version
    Done,         // the update terminated
}
```

`stats_snapshot()` returns `RunStats { processed, skipped, written, deleted, elapsed }`, the coarse view that `App::run` returns.

## Scoped reports with `stats_group`

By default every component's stats roll up into one report for the whole update. For a large pipeline you often want to watch a *part* of it on its own — "indexing the docs tree" separately from "indexing the code tree", or one expensive phase by itself.

<Lang only="python">

`coco.stats_group(title)` opens a scope: everything mounted inside the block aggregates into a **separate** report under `title`, **split out** of the parent (the parent report no longer counts that work — there's no double counting). It's a plain `with` block, used inside a processing component like [`coco.component_subpath`](../programming_guide/processing_component#using-component_subpath-as-a-context-manager):

</Lang>

<Lang only="rust">

`ctx.stats_group(title, f)` opens a scope: `f` runs with a scoped `Ctx`, and everything mounted from that `Ctx` aggregates into a **separate** report under `title`, **split out** of the parent (the parent report no longer counts that work — there's no double counting). It returns the closure's value and a `StatsGroupHandle`:

</Lang>

<RustNote>
A group is a closure, not a `with` block. `stats_group` prints nothing; `stats_group_with_options` takes `StatsGroupOptions` to print the group's progress.
</RustNote>

{/* Rust: rust/sdk/cocoindex/tests/pipeline.rs (ctx_stats_group_reports_scoped_child_stats, ctx_stats_group_with_options_reports_scoped_child_stats), rust/sdk/cocoindex/src/ctx.rs (stats_group, stats_group_with_options) */}
<LangTabs>
<Fragment slot="python">

```python
@coco.fn
async def app_main(docs_dir, code_dir, target):
    with coco.stats_group("Indexing docs", report_to_stdout=True):
        files = localfs.walk_dir(docs_dir, ...)
        await coco.mount_each(process_doc, files.items(), target)

    with coco.stats_group("Indexing code", report_to_stdout=True):
        files = localfs.walk_dir(code_dir, ...)
        await coco.mount_each(process_code, files.items(), target)
```

</Fragment>
<Fragment slot="rust">

```rust
                    child

    })
    .await?;

// The same group, with its progress printed to stdout:

    refresh_interval: Some(Duration::from_millis(50)),

let ((), reported_handle) = ctx
    .stats_group_with_options("Indexing docs (reported)", options, |group_ctx, _handle| async move {
        // mount from `group_ctx` ...
        Ok::<_, cocoindex::Error>(())
    })
    .await?;
```

<Lang only="python">

With `report_to_stdout=True`, the group's progress is also printed to stdout, labeled by its title, alongside the main `report_to_stdout` display without disrupting it. Pass a `timedelta` instead of `True` to set the group's refresh interval; while a terminal display runs, the group is a section of that display and redraws with it.

A failure in a group, reported or not, still counts in the final status line of the main display: the run ends in `✗ Done in 2.0s · 3 failed`, even though the group's rows stay out of the main report.

The block yields a `StatsGroupHandle` with the same `stats()` and `watch()` as `UpdateHandle` (a group has no return value, so there's no `result()`):

### Semantics

<Lang only="python">

- **Synchronous and non-blocking.** It's a regular `with` (not `async with`), even though the body `await`s mounts. Leaving the block does **not** wait for the work to finish — it only marks where member registration stops. The group becomes `READY` asynchronously once the block has exited *and* every component mounted inside it is ready; observe that via `sg.watch()` / `sg.stats()`.

</Lang>

<Lang only="rust">

- **Non-blocking.** Returning from the closure does **not** wait for background work mounted inside it (`mount`, `mount_each`) to finish — it only marks where member registration stops. The group becomes ready asynchronously once the closure has returned *and* every component mounted inside it is ready; observe that via `handle.changed()` / `handle.detailed_stats_snapshot()`.

</Lang>

- **Identity is unchanged.** Grouping only redirects where stats are *reported*. Component paths, change detection, target-state ownership, and the run's overall completion are unaffected — the grouped components are still ordinary children of the surrounding component.
- **Nesting.** Groups may nest. The **innermost** group owns a mount's stats; an outer group's readiness still waits for the inner group's work to finish.
- **Live members.** A group containing [live components](./live_component) becomes ready after their initial catch-up and reports their ongoing incremental stats, just like the root.
