The `valkey` connector provides utilities for writing documents to Valkey with vector search support, using the valkey-search module for similarity search indexes.

```rust
pub struct ClientConfig {
    pub host: String,                 // default "localhost"
    pub port: u16,                    // default 6379
    pub password: Option<String>,
    pub use_tls: bool,
    pub client_name: Option<String>,  // default Some("cocoindex_vector_store")
}

impl Valkey {
    pub async fn connect(uri: &str) -> Result<Self>
    pub async fn connect_with_config(config: ClientConfig) -> Result<Self>
    pub async fn from_client(state_id: impl Into<String>, client: &redis::Client) -> Result<Self>
}
```

`Valkey::connect("redis://localhost:6379")` takes a URI. `Valkey::connect_with_config(ClientConfig { .. })` takes the fields below. For anything `ClientConfig` does not cover (client certificates, a username, a database number), build a `redis::Client` yourself and pass it to `from_client`.

<Lang only="python">

**Parameters:**

- `host` — Valkey server host (default: `"localhost"`).
- `port` — Valkey server port (default: `6379`).
- `password` — Optional authentication password.
- `use_tls` — Whether to use TLS for the connection (default: `False`).
- `client_name` — Client name for the connection, visible in `CLIENT LIST` and monitoring dashboards (default: `"cocoindex_vector_store"`). Pass `None` to disable.
- `**kwargs` — Additional keyword arguments passed to `GlideClientConfiguration`. `client_info_tag` defaults to `"cocoindex"`, so the server attributes the connection to CocoIndex via `CLIENT SETINFO LIB-NAME` unless you override it.

For advanced configurations not covered by these parameters, construct `GlideClientConfiguration` directly.

**Returns:** A `GlideClientConfiguration` instance.

</Lang>
<Lang only="rust">

**`ClientConfig` fields:**

- `host` — Valkey server host (default: `"localhost"`).
- `port` — Valkey server port (default: `6379`).
- `password` — Optional authentication password. The `Debug` output of `ClientConfig` shows it as redacted.
- `use_tls` — Whether to use TLS for the connection (default: `false`).
- `client_name` — Client name for the connection, set with `CLIENT SETNAME` and visible in `CLIENT LIST` and monitoring dashboards (default: `Some("cocoindex_vector_store")`). Pass `None` to set no name.

**Returns:** A `Valkey` handle. It is cheap to clone: the multiplexed connection is shared, and every command or pipeline runs on a clone of it.

The handle's `state_id()` is the server's address and database number as a URI, for example `redis://localhost:6379`. It never holds the username or password, so a credential does not leak into memo dependencies or the target-state store, and rotating a credential does not invalidate them. With `from_client(state_id, client)`, you choose the `state_id`: name the server, not a secret.

</Lang>

## As target

The `valkey` connector provides target state APIs for writing documents to search indexes. CocoIndex tracks what documents should exist and automatically handles upserts and deletions.

### Declaring target states

#### Setting up a connection

<Lang only="python">

Create a `ContextKey[GlideClient]` to identify your Valkey client, then provide it in your lifespan:

</Lang>
<Lang only="rust">

Declare a context key for a `valkey::Valkey` to identify your Valkey connection, then provide the connection on the environment builder:

</Lang>

:::note
The key name is load-bearing across runs — it's the stable identity CocoIndex uses to track managed indexes. See [ContextKey as stable identity](../programming_guide/context#contextkey-as-stable-identity) before renaming.
:::

```rust
impl IndexTarget {
    pub fn declare_document(&self, ctx: &Ctx, document: Document) -> Result<()>
}

pub struct Document {
    pub id: String,
    pub vector: Vec<f32>,
    pub payload: Option<BTreeMap<String, PayloadValue>>,
}

pub enum PayloadValue {
    Str(String),
    Int(i64),
    Float(f64),
}

let mut payload = BTreeMap::new();
payload.insert("text".to_string(), text.to_string());
index.declare_document(&ctx, Document::new(id, vector).with_payload(payload))?;

// A numeric payload value for a NUMERIC field:
index.declare_document(
    &ctx,
    Document::new("d3", vec![0.7, 0.8, 0.9]).with_payload([
        ("text", PayloadValue::from("priced")),
        ("price", PayloadValue::from(42i64)),
    ]),
)?;
```

`with_payload` takes any iterator of `(key, value)` pairs whose values convert into `PayloadValue` (`String`, `&str`, `i64` or `f64`).

</Fragment>
</LangTabs>

**Parameters:**

<Lang only="python">

- `document` — A `valkey.Document` containing:
  - `id` — Document ID (string)
  - `vector` — Vector data (list of floats or numpy array)
  - `payload` — Optional metadata dict (values must be str, int, or float). The key `vector` is reserved for the vector field (see [Data storage](#data-storage)), so a payload with that key raises a `ValueError`.

</Lang>
<Lang only="rust">

- `document` — A `valkey::Document` containing:
  - `id` — Document ID (string)
  - `vector` — Vector data (`Vec<f32>`). It must have the index's dimension and finite elements: the search module stores a hash whose vector it cannot read but never indexes it, so `declare_document` returns an error instead.
  - `payload` — Optional metadata map (values are text, `i64` or `f64`). The key `vector` is reserved for the vector field (see [Data storage](#data-storage)), so `declare_document` returns an error for a payload with that key.

```rust
pub struct VectorDef<'a> {
    pub schema: &'a (dyn VectorSchemaProvider + 'a),
    pub distance: Distance,          // Cosine (default), L2, Ip
```

### Distance metrics

The `distance` parameter in `VectorDef` specifies the similarity metric:

<Lang only="python">

- `"cosine"` — Cosine similarity (default)
- `"l2"` — Euclidean distance (L2)
- `"ip"` — Inner product (dot product)

</Lang>
<Lang only="rust">

- `Distance::Cosine` — Cosine similarity (default)
- `Distance::L2` — Euclidean distance (L2)
- `Distance::Ip` — Inner product (dot product)

</Lang>

### Index algorithms

The `algorithm` parameter specifies the vector indexing strategy:

<Lang only="python">

- `"hnsw"` — Hierarchical Navigable Small World graph (default, best for most use cases)
- `"flat"` — Brute-force flat index (exact results, slower for large datasets)

</Lang>
<Lang only="rust">

- `VectorAlgorithm::Hnsw` — Hierarchical Navigable Small World graph (default, best for most use cases)
- `VectorAlgorithm::Flat` — Brute-force flat index (exact results, slower for large datasets)

</Lang>

### Data storage

Documents are stored as Valkey HASH keys with a prefix pattern:

- Key format: `{index_name}:{document_id}`
- Vector field: stored as binary float32 blob in a `vector` hash field
- Payload fields: stored as individual hash fields (string values)

The search index is created with `FT.CREATE ON HASH PREFIX 1 {index_name}:` to automatically index all documents with the matching prefix.

<Lang only="rust">

A batch of document changes is sent in pipelines: one `DEL` for every deleted key, then the upserts in pipelines of up to 1,000 documents. Each document is written as its own `MULTI` `DEL` `HSET` `EXEC` transaction, so no stale payload field survives an update and a document is never half written. A batch of `n` documents costs `1 + ceil(n / 1000)` round trips, not `n`.

</Lang>

```python
from glide import GlideClient
import cocoindex as coco
from cocoindex.connectors import valkey
from cocoindex.ops.sentence_transformers import SentenceTransformerEmbedder
from typing import AsyncIterator

VALKEY_DB = coco.ContextKey[GlideClient]("main_vectors")
EMBEDDER = coco.ContextKey[SentenceTransformerEmbedder]("embedder")

@coco.lifespan
async def coco_lifespan(builder: coco.EnvironmentBuilder) -> AsyncIterator[None]:
    config = valkey.create_client_config("localhost", 6379)
    client = await GlideClient.create(config)
    builder.provide(VALKEY_DB, client)
    builder.provide(EMBEDDER, SentenceTransformerEmbedder("all-MiniLM-L6-v2"))
    yield
    await client.close()

@coco.fn
async def process_document(
    doc_id: str,
    text: str,
    target: valkey.IndexTarget,
) -> None:
    embedder = coco.use_context(EMBEDDER)
    embedding = await embedder.embed(text)

    target.declare_document(valkey.Document(
        id=doc_id,
        vector=embedding.tolist(),
        payload={"text": text},
    ))

@coco.fn
async def app_main() -> None:
    embedder = coco.use_context(EMBEDDER)

    index = await valkey.mount_index_target(
        VALKEY_DB,
        "documents",
        await valkey.IndexSchema.create(
            vectors=valkey.VectorDef(schema=embedder, distance="cosine"),
        ),
    )

    for doc_id, text in documents:
        await coco.mount(
            coco.component_subpath("doc", doc_id),
            process_document,
            doc_id,
            text,
            index,
        )
```

```rust
use std::collections::BTreeMap;

use cocoindex::connectors::valkey::{
    self, Distance, Document, FieldDef, FieldType, IndexSchema, VectorAlgorithm, VectorDef,
};
use cocoindex::prelude::*;

cocoindex::context_key!(static VK: valkey::Valkey, key = "valkey_target_conn");

async fn schema() -> IndexSchema {
    IndexSchema::create(
        VectorDef {
            schema: &VectorSchema::f32(3),
            distance: Distance::Cosine,
            algorithm: VectorAlgorithm::Hnsw,
        },
        vec![FieldDef::new("text", FieldType::Text)],

    .await
    .unwrap()
}

fn doc(id: &str, vector: Vec<f32>, text: &str) -> Document {
    let mut payload = BTreeMap::new();
    payload.insert("text".to_string(), text.to_string());
    Document::new(id, vector).with_payload(payload)
}
```

## Vector search

<Lang only="python">

The connector focuses on writing documents to Valkey. For vector search queries, use the Valkey GLIDE client directly.

```python
from glide import GlideClient
from glide.async_commands import ft
from glide.async_commands.ft import FtSearchOptions
import struct

# Build a KNN query
query_vec = struct.pack(f"<{len(embedding)}f", *embedding)
query = f"*=>[KNN 10 @vector $query_vec AS score]"

results = await ft.search(
    client,
    "documents",
    query,
    options=FtSearchOptions(params={"query_vec": query_vec}),
)
```

</Lang>
<Lang only="rust">

The connector focuses on writing documents to Valkey and has no search helper. For vector search queries, run `FT.SEARCH` through the `redis` crate directly.

</Lang>
