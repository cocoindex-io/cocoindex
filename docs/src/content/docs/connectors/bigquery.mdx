The `bigquery` connector provides target state APIs for writing rows to BigQuery tables. CocoIndex tracks the rows that should exist and applies table creation, upserts, updates, and deletes incrementally.

## Connection setup

<Lang only="python">

Create a `ContextKey[bigquery.ConnectionConfig]` to identify the BigQuery connection, then provide it in your lifespan:

</Lang>

<Lang only="rust">

Declare a context key for a `BigQueryConnection` with `cocoindex::context_key!`, then provide the connection when you build the environment:

</Lang>

:::note
The key name is load-bearing across runs. It is the stable identity CocoIndex uses to track managed rows. See [ContextKey as stable identity](../programming_guide/context#contextkey-as-stable-identity) before renaming.

<LangTabs>
<Fragment slot="python">

```python
import os
from collections.abc import Iterator

import cocoindex as coco
from cocoindex.connectors import bigquery

BIGQUERY = coco.ContextKey[bigquery.ConnectionConfig]("bigquery")

@coco.lifespan
def coco_lifespan(builder: coco.EnvironmentBuilder) -> Iterator[None]:
    builder.provide(
        BIGQUERY,
        bigquery.ConnectionConfig(
            project=os.environ.get("BIGQUERY_PROJECT"),
            credentials_path=os.environ.get("GOOGLE_APPLICATION_CREDENTIALS") or None,
            location=os.environ.get("BIGQUERY_LOCATION"),
        ),
    )
    yield
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::connectors::bigquery::{BigQueryConfig, BigQueryConnection};

cocoindex::context_key!(static BIGQUERY: BigQueryConnection, key = "bigquery_demo");

let optional = |name: &str| std::env::var(name).ok().filter(|v| !v.is_empty());
let conn = BigQueryConnection::connect(BigQueryConfig {
    project: optional("BIGQUERY_PROJECT"),
    credentials_path: optional("GOOGLE_APPLICATION_CREDENTIALS").map(Into::into),

let app = cocoindex::Environment::builder()
    .db_path(".cocoindex_db")
    .provide_key(&BIGQUERY, conn)
    .build()
    .await?
    .app("BigQueryTarget")
    .await?;
```

`BigQueryConnection::connect(config)?` resolves the credentials and makes no request until the first query. The connection is `Clone`; `conn.query(sql).await?` runs a query and returns its rows as JSON objects.

## As target

The `bigquery` connector provides target state APIs for writing rows to tables.

### Tables

Declares a table as a target state. Returns a `TableTarget` for declaring rows.

{/* Rust: rust/sdk/cocoindex/src/connectors/bigquery.rs */}
<LangTabs>
<Fragment slot="python">

```python
def declare_table_target(
    db: ContextKey[ConnectionConfig],
    table_name: str,
    table_schema: TableSchema[RowT],
    *,
    dataset: str,
    project: str | None = None,
    managed_by: Literal["system", "user"] = "system",
) -> TableTarget[RowT, coco.PendingS]
```

</Fragment>
<Fragment slot="rust">

```rust
pub async fn mount_table_target(
    ctx: &Ctx,
    conn: &ContextKey<BigQueryConnection>,
    dataset: impl Into<String>,

    table_schema: TableSchema,

pub async fn mount_table_target_with_options(

    dataset: impl Into<String>,
    table_name: impl Into<String>,
    table_schema: TableSchema,

    /// Project that owns the table. `None` means the connection's project.

    pub managed_by: ManagedBy,
}
```

`declare_table_target` and `declare_table_target_with_options` take the same arguments and declare the table in the current component.

</Fragment>
</LangTabs>

**Parameters:**

<Lang only="python">

- `db` - A `ContextKey[ConnectionConfig]` identifying the connection to use.
- `table_name` - Name of the table.
- `table_schema` - Schema definition including columns and primary key.
- `dataset` - BigQuery dataset name.
- `project` - Optional project that owns the target table. If omitted, BigQuery uses the client project. Omitting `project` and naming the client project explicitly are two different keys for the same table (see the caution below).
- `managed_by` - Whether CocoIndex manages the table lifecycle (`"system"`) or assumes it exists (`"user"`).

When `managed_by="system"`, CocoIndex creates the dataset and table if needed. Table changes use BigQuery DDL, and row changes use BigQuery `MERGE` for upserts.

</Lang>

<Lang only="rust">

- `conn` - The context key of the `BigQueryConnection` to use.
- `dataset` - BigQuery dataset name.
- `table_name` - Name of the table.
- `table_schema` - Schema definition including columns and primary key.
- `options.project` - Optional project that owns the target table. If `None`, the connection's project is used. `None` and naming the connection's project explicitly are two different keys for the same table (see the caution below).
- `options.managed_by` - Whether CocoIndex manages the table lifecycle (`ManagedBy::System`, the default) or assumes it exists (`ManagedBy::User`).

With `ManagedBy::System`, CocoIndex creates the dataset and table if needed. Table changes use BigQuery DDL, and row changes use BigQuery `MERGE` for upserts.

</Lang>

:::note
BigQuery primary key constraints are not enforced by BigQuery. CocoIndex still uses the primary key list to reconcile rows and generate `MERGE` and `DELETE` statements.
:::

:::caution[One table, one key]
CocoIndex identifies a table by its key: the connection's context key, the project, `dataset` and `table_name`. <Lang only="python">`project=None` and `project="<client project>"`</Lang><Lang only="rust">`project: None` and `project: Some("<connection project>")`</Lang> reach the same table through two different keys. Declare each table through one form only. Switching a table from one form to the other changes its key: CocoIndex then cleans up the table it tracked under the old key, which is the same table. See [ContextKey as stable identity](../programming_guide/context#contextkey-as-stable-identity).
:::

## Table schema: from a Rust struct

Define the table structure with a struct that derives `SchemaFields`:

</Lang>

{/* Rust: examples/rust/bigquery_target/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
from dataclasses import dataclass

@dataclass
class ProductRow:
    id: str
    name: str
    price: float
    metadata: dict[str, object]

schema = await bigquery.TableSchema.from_class(
    ProductRow,
    primary_key=["id"],
)
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::prelude::*;
use serde::{Deserialize, Serialize};
use serde_json::Value as JsonValue;

#[derive(Clone, Serialize, Deserialize, SchemaFields)]
struct BigQueryOrder {
    order_id: String,
    customer: String,
    quantity: i64,
    unit_price: f64,
    #[coco(json)]
    attributes: JsonValue,
}

let schema = TableSchema::from_row::<BigQueryOrder>(["order_id"])?;
```

`TableSchema::from_row::<Row>(primary_key)` takes the primary-key columns as an iterator of names. A `serde_json::Value` field needs `#[coco(json)]`; a `Vec<T>`, map or nested struct maps to `JSON` on its own.

</Fragment>
</LangTabs>

<Lang only="python">

Python types are automatically mapped to BigQuery column types:

| Python Type | BigQuery Type |
|-------------|---------------|
| `bool` | `BOOL` |
| `int` | `INT64` |
| `float` | `FLOAT64` |
| `decimal.Decimal` | `NUMERIC` |
| `str` | `STRING` |
| `bytes` | `BYTES` |
| `uuid.UUID` | `STRING` |
| `datetime.date` | `DATE` |
| `datetime.time` | `TIME` |
| `datetime.datetime` | `TIMESTAMP` |
| `datetime.timedelta` | `FLOAT64` |
| `list`, `dict`, nested structs | `JSON` |

`JSON` values are JSON-serialized and written with `PARSE_JSON`.

### BigQueryType

Use `BigQueryType` to specify a custom BigQuery type and optional encoder:

</Lang>

<Lang only="rust">

Rust field types are automatically mapped to BigQuery column types:

| Rust Type | BigQuery Type |
|-----------|---------------|
| `bool` | `BOOL` |
| `i16`, `i32`, `i64` (and the unsigned widths) | `INT64` |
| `f32`, `f64` | `FLOAT64` |
| `rust_decimal::Decimal` | `NUMERIC` |
| `String` | `STRING` |
| `Vec<u8>` | `BYTES` |
| `uuid::Uuid` | `STRING` |
| `chrono::NaiveDate` | `DATE` |
| `chrono::NaiveTime` | `TIME` |
| `chrono::DateTime`, `chrono::NaiveDateTime` | `TIMESTAMP` |
| `std::time::Duration` | `FLOAT64` |
| other `Vec<T>`, maps, nested structs, `#[coco(json)]` | `JSON` |
| `#[coco(vector)] Vec<f32>` | `ARRAY<FLOAT64>` |

`JSON` values are JSON-serialized and written with `PARSE_JSON`. An `Option<T>` field is a nullable column; every other field is `NOT NULL`.

### Custom column types

Use `#[coco(type = "…")]` on a field to specify a custom BigQuery type:

</Lang>

{/* Rust: rust/sdk/cocoindex/tests/bigquery_target.rs; #[coco(type)] from rust/sdk/cocoindex_macros/src/lib.rs */}
<LangTabs>
<Fragment slot="python">

```python
from dataclasses import dataclass
from typing import Annotated

from cocoindex.connectors.bigquery import BigQueryType

@dataclass
class ProductRow:
    id: Annotated[int, BigQueryType("NUMERIC")]
    embedding: Annotated[list[float], BigQueryType("ARRAY<FLOAT64>")]
```

</Fragment>
<Fragment slot="rust">

```rust
#[derive(Serialize, SchemaFields)]
struct ProductRow {
    #[coco(type = "NUMERIC")]
    id: i64,
    #[coco(type = "ARRAY<FLOAT64>")]
    embedding: Vec<f64>,
}
```

`#[coco(type = "…")]` sets the column type verbatim. Explicit columns are also possible: `TableSchema::new([("id", ColumnDef::new("INT64").not_null()), ("payload", ColumnDef::new("JSON").parse_json())], ["id"])?`. A `ColumnDef` is nullable unless `.not_null()` is called, and `.parse_json()` writes the value through `PARSE_JSON`.

</Fragment>
</LangTabs>

<RustNote>
There is no per-column `encoder`: a value is written as it serializes with serde.
</RustNote>

<Lang only="python">You can also pass `column_overrides` when constructing the schema:</Lang><Lang only="rust">You can also override one column of a derived schema with `with_column_type`, which replaces the column's type and its `parse_json` flag and keeps its derived nullability:</Lang>

{/* Rust: rust/sdk/cocoindex/src/connectors/bigquery.rs (TableSchema::with_column_type and its test) */}
<LangTabs>
<Fragment slot="python">

```python
schema = await bigquery.TableSchema.from_class(
    ProductRow,
    primary_key=["id"],
    column_overrides={
        "id": bigquery.BigQueryType("NUMERIC"),
    },
)
```

</Fragment>
<Fragment slot="rust">

```rust
let schema = TableSchema::from_row::<Row>(["id"])?
    .with_column_type("payload", ColumnDef::new("JSON").parse_json())?;
```

## Example

{/* Rust: examples/rust/bigquery_target/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
from dataclasses import dataclass

@dataclass
class ProductRow:
    id: str
    name: str
    price: float
    metadata: dict[str, object]

async def declare_products(rows: list[ProductRow]) -> None:
    table = await bigquery.mount_table_target(
        BIGQUERY,
        table_name="product_index",
        table_schema=await bigquery.TableSchema.from_class(
            ProductRow,
            primary_key=["id"],
        ),
        project="my-project",
        dataset="analytics",
    )

    for row in rows:
        table.declare_row(row=row)
```

</Fragment>
<Fragment slot="rust">

```rust
let schema = TableSchema::from_row::<BigQueryOrder>(["order_id"])?;
let table = bigquery::mount_table_target(
    &ctx,
    &BIGQUERY,
    "analytics",
    "product_index",
    schema,

.await?;
let rows = use_mount_each!(orders, |order| process_order(ctx, order)).await?;
for row in &rows {
    table.declare_row(&ctx, row)?;
}
```

## Identifier handling

Dataset, table, and column names must be simple BigQuery identifiers containing letters, numbers, and underscores, and must not start with a number. The connector quotes identifiers when generating SQL.
