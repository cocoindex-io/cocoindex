## Stable memoization with FilePath

A key feature of the <Lang only="python">`localfs`</Lang><Lang only="rust">local filesystem</Lang> connector is [**stable memoization**](../programming_guide/function) through `FilePath`. When you move your entire project directory, memoization keys remain stable as long as you use the same `ContextKey` key <Lang only="python">string</Lang><Lang only="rust">name</Lang> for the base directory.

### Using ContextKey for stable base directories

<Lang only="python">

Define a `ContextKey[pathlib.Path]` with a stable string identifier. Provide the actual path in your app's lifespan, then pass the key directly to `walk_dir()`, `declare_dir_target()`, and related functions.

</Lang>

<Lang only="rust">

Declare a `ContextKey<PathBuf>` with `context_key!`; its name is the stable identifier. Provide the actual path when you build the environment, then build paths under it with `FilePath::under_context_dir` and pass them to `walk_dir`, `DirTarget::mount` and related functions.

</Lang>

{/* Rust: rust/sdk/cocoindex/tests/fs_target.rs */}
<LangTabs>
<Fragment slot="python">

```python
import pathlib
import cocoindex as coco
from cocoindex.connectors import localfs

# Define a stable key (the string "source_dir" is the stable memo identifier)
SOURCE_DIR = coco.ContextKey[pathlib.Path]("source_dir")

@coco.fn
async def app_main() -> None:
    async for file in localfs.walk_dir(SOURCE_DIR, recursive=True):
        # file.file_path has a stable memo key based on "source_dir"
        await process(file)

# In your lifespan, provide the actual path:
async def lifespan(builder: coco.EnvironmentBuilder) -> None:
    builder.provide(SOURCE_DIR, pathlib.Path("./data"))
```

</Fragment>
<Fragment slot="rust">

```rust
use std::path::PathBuf;

use cocoindex::resources::fs::{DirTarget, FilePath};
use cocoindex::Environment;

// The key's name ("OUT_DIR") is the stable identifier.
cocoindex::context_key!(static OUT_DIR: PathBuf);

// Provide the actual directory when you build the environment:
let app = Environment::builder()
    .db_path(&db)
    .provide_key(&OUT_DIR, base)
    .build()
    .await?
    .app("fs_context_dir")
    .await?;

app.update(move |ctx| async move {
    // A path under the key's directory. Memo keys and target keys name
    // the key, not the directory.
    let root = FilePath::under_context_dir(&ctx, &OUT_DIR, "out")?;
    let t = DirTarget::mount(&ctx, root)?;
    t.declare_file(&ctx, "a.txt", b"a")?;
    Ok(())
})
.await?;
```

`FilePath::under_context_dir(ctx, &KEY, path)` builds the path under the key's directory. Every function that takes `impl Into<FilePath>`, such as `walk_dir` and `DirTarget::mount`, accepts that `FilePath`.

</Fragment>
</LangTabs>

When you move your project to a different location, just update the path in <Lang only="python">`builder.provide()`</Lang><Lang only="rust">`provide_key`</Lang> — memoization keys remain the same because they're based on the stable key <Lang only="python">string (`"source_dir"`)</Lang><Lang only="rust">name (`OUT_DIR`)</Lang>, not the filesystem path.

Target files are keyed the same way, by the key name and the relative path. Because the base directory isn't part of the key, CocoIndex can't tell when two keys reach the same file. See [One file, one declaration](#one-file-one-declaration).

### FilePath

<Lang only="python">

`FilePath` combines an optional base directory key and a relative path. Passing a `ContextKey[Path]` directly to any localfs function is equivalent to constructing `FilePath(base_dir=key)`.

`FilePath` supports all `pathlib.PurePath` operations:

</Lang>

<Lang only="rust">

`FilePath` combines an optional base directory key and a relative path. Its path operations are methods:

</Lang>

{/* Rust: rust/sdk/cocoindex/src/resources/file.rs (FilePath methods), tests/fs_target.rs */}
<LangTabs>
<Fragment slot="python">

```python
SOURCE_DIR = coco.ContextKey[pathlib.Path]("source_dir")
source = localfs.FilePath(base_dir=SOURCE_DIR)

# Create paths using the / operator
config_path = source / "config" / "settings.json"

# Access path properties
print(config_path.name)      # "settings.json"
print(config_path.suffix)    # ".json"
print(config_path.parent)    # FilePath pointing to "config/"

# Resolve to absolute path (requires active component context)
abs_path = config_path.resolve()  # pathlib.Path
```

</Fragment>
<Fragment slot="rust">

```rust
// Under a context directory: the key and the directory it was provided with.
let source = FilePath::under_context_dir(&ctx, &SOURCE_DIR, "")?;

// Create paths with join
let config_path = source.join("config").join("settings.json");

// Access path properties
config_path.name();      // "settings.json"
config_path.suffix();    // ".json"
config_path.parent();    // Some(FilePath pointing to "config")

// Resolve to the full path

```

`FilePath::new(path)` builds a path with no base directory. The other path operations are `stem`, `suffixes`, `parts`, `with_name`, `with_stem`, `with_suffix`, `relative_to` and `as_posix`.

## As source

<Lang only="python">

Use `walk_dir()` to iterate over files in a directory. It returns a `DirWalker` that supports both synchronous and asynchronous iteration.

</Lang>

<Lang only="rust">

Use `walk_dir()` to list the files in a directory. It returns a `DirWalker`, a builder whose `walk()` and `items()` return the matching files.

</Lang>

{/* Rust: rust/sdk/cocoindex/src/resources/fs.rs, examples/rust/text_embedding/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
def walk_dir(
    path: FilePath | Path | ContextKey[Path],
    *,
    live: bool = False,
    recursive: bool = False,
    path_matcher: FilePathMatcher | None = None,
    rescan_interval: datetime.timedelta | None = datetime.timedelta(hours=1),
) -> DirWalker
```

</Fragment>
<Fragment slot="rust">

```rust
pub fn walk_dir(path: impl Into<FilePath>) -> DirWalker

impl DirWalker {
    pub fn recursive(self, recursive: bool) -> Self
    pub fn path_matcher(self, matcher: impl FilePathMatcher + 'static) -> Self
    pub fn walk(&self) -> Result<Vec<FileEntry>>
    pub fn items(&self) -> Result<Vec<(String, FileEntry)>>
    pub fn live(self) -> LiveDirWalker   // `fs_live` feature
}

impl LiveDirWalker {
    pub fn poll_interval(self, interval: Duration) -> Self
    pub fn rescan_interval(self, interval: Option<Duration>) -> Self
}
```

</Fragment>
</LangTabs>

**Parameters:**

<Lang only="python">

- `path` — The root directory path to walk through. Can be a `FilePath`, a `pathlib.Path`, or a `ContextKey[Path]` (equivalent to `FilePath(base_dir=path)`).
- `live` — If `True`, `items()` returns a [`LiveMapView`](../advanced_topics/live_component#livemapfeed-and-livemapview) that supports live file watching via `mount_each()`.
- `recursive` — If `True`, recursively walk subdirectories.
- `path_matcher` — Optional filter for files and directories. See [PatternFilePathMatcher](../common_resources/data_types#patternfilepathmatcher).
- `rescan_interval` — When `live=True`, the interval between periodic full rescans, which recreate the OS-level file watcher and walk the whole directory, as a safety net against events the platform dropped (for example macOS FSEvents silently stopping). Defaults to one hour; `None` disables it. Ignored when `live=False`.

**Returns:** A `DirWalker` that supports async iteration via `async for`.

</Lang>

<Lang only="rust">

- `path` — The root directory to walk: any `impl Into<FilePath>`, such as a `&str`, a `PathBuf`, or a `FilePath` under a context directory.
- `.recursive(bool)` — If `true`, recursively walk subdirectories. Defaults to `false`.
- `.path_matcher(matcher)` — Filter for files and directories. Defaults to match-all. See [PatternFilePathMatcher](../common_resources/data_types#patternfilepathmatcher).
- `.live()` — Turns the walker into a `LiveDirWalker` for `ctx.mount_each_live` (`fs_live` feature). See [Live file watching](#live-file-watching).
- `.poll_interval(interval)`, `.rescan_interval(interval)` — `LiveDirWalker` only: how often to poll where the native watcher is unavailable (default one second), and the interval between periodic full rescans (default one hour; `None` disables it).

**Returns:** A `DirWalker`. `walk()` returns the matching `FileEntry`s and `items()` the `(key, file)` pairs; both block on the directory walk, so call them before the pipeline starts or from a blocking context (a live feed walks on a blocking thread). A missing root directory yields no files; a root that is not a directory is an error.

</Lang>

Symlinked directories are followed, except into a directory that is already an ancestor (a cycle); a symlink to a file is a file. A directory the process can't read, and an entry that vanishes or can't be stat-ed during the walk, are skipped.

### Iterating files

<Lang only="python">

`walk_dir()` returns a `DirWalker` that supports async iteration, yielding `File` objects (implementing the [`FileLike`](../common_resources/data_types#filelike) base class):

</Lang>

<Lang only="rust">

`walk()` returns `FileEntry` values, which implement the [`FileLike`](../common_resources/data_types#filelike) trait:

<LangTabs>
<Fragment slot="python">

```python
async for file in localfs.walk_dir("/path/to/documents", recursive=True):

```

</Fragment>
<Fragment slot="rust">

`walk()` reads the directory and returns a `Vec<FileEntry>`, sorted by relative path. `content()` and `content_str()` are blocking reads. In an async function prefer the `FileLike` reads: `file.read().await?` reads on the runtime's blocking pool and caches the content, returned as a shared `bytes::Bytes`, and `file.read_text().await?` decodes it.

</Fragment>
</LangTabs>

<Lang only="python">

File I/O runs in a thread pool, keeping the event loop responsive.

</Lang>

<RustNote>
The walker has no async iteration: `walk()` and `items()` return the full list.
</RustNote>

### Filtering files

use cocoindex::prelude::*;

// Include only .py and .md files, exclude hidden directories and test files
let matcher = PatternFilePathMatcher::new(
    ["**/*.py", "**/*.md"],
    ["**/.*", "**/test_*", "**/__pycache__"],

`PatternFilePathMatcher::new(included, excluded)` takes two iterables of patterns; `PatternFilePathMatcher::include(patterns)` takes only included patterns. An excluded pattern that starts with `!` is a negation, as in Python.

### Live file watching

<Lang only="python">

When `live=True`, `items()` returns a [`LiveMapView`](../advanced_topics/live_component#livemapfeed-and-livemapview) instead of a plain `AsyncIterable`. Combined with [`mount_each()`](../programming_guide/processing_component#mount_each), this enables automatic incremental file watching — new, modified, and deleted files are processed without a full rescan:

</Lang>

<Lang only="rust">

`.live()` turns the walker into a `LiveDirWalker`, a [`LiveMapView`](../advanced_topics/live_component#livemapfeed-and-livemapview) plus `LiveMapFeed`. Combined with `ctx.mount_each_live`, this enables automatic incremental file watching — new, modified, and deleted files are processed without a full rescan:

</Lang>

{/* Rust: examples/rust/text_embedding/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
files = localfs.walk_dir(
    sourcedir, recursive=True,
    path_matcher=PatternFilePathMatcher(included_patterns=["**/*.md"]),
    live=True,
)
await coco.mount_each(process_file, files.items(), target)
```

</Fragment>
<Fragment slot="rust">

```rust
// One component per markdown file; each declares its own rows. In live
// mode (`cocoindex update -L`) the walker keeps watching the directory.
let files = walk_dir(sourcedir)
    .recursive(true)
    .path_matcher(PatternFilePathMatcher::new(
        ["**/*.md"],
        std::iter::empty::<&str>(),
    )?)
    .live()
    .poll_interval(Duration::from_secs(1));
ctx.mount_each_live(&"files", files, move |ctx, file: FileEntry| {
    let table = table.clone();
    async move {
        for row in process_file(&ctx, &file).await? {
            table.declare_row(&ctx, &row)?;
        }
        Ok(())
    }
})
.await
```

`.live()` needs the `fs_live` Cargo feature. The `LiveDirWalker` follows the directory through the platform's native watcher: each event re-runs or removes that file's component alone (whether its work can be skipped is the file's memo decision), a directory that appears is walked, and a directory that moves away removes every file under it. Where the native watcher cannot be set up, it polls instead, every `poll_interval` (default one second). Every `rescan_interval` (default one hour; `None` disables it) it recreates the watcher and walks the whole directory, as a safety net against events the platform dropped. `ctx.mount_each_live(&key, feed, |ctx, file| ...)` mounts one child component per file. See `examples/rust/text_embedding` for the full program.

</Fragment>
</LangTabs>

See [Live Mode](../programming_guide/live_mode) for how this works and how to enable it on the app.

### Example

{/* Rust: examples/rust/files_to_sqlite/src/main.rs, examples/rust/text_embedding/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
import pathlib
import cocoindex as coco
from cocoindex.connectors import localfs
from cocoindex.resources.file import FileLike, PatternFilePathMatcher

SOURCE_DIR = coco.ContextKey[pathlib.Path]("source_dir")

@coco.fn
async def app_main() -> None:
    matcher = PatternFilePathMatcher(included_patterns=["**/*.md"])

    async for file in localfs.walk_dir(SOURCE_DIR, recursive=True, path_matcher=matcher):
        await coco.mount(
            coco.component_subpath("file", str(file.file_path.path)),
            process_file,
            file,
        )

@coco.fn(memo=True)
async def process_file(file: FileLike) -> None:
    text = await file.read_text()
    # ... process the file content ...
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::prelude::*;

/// Memoized on the file: an unchanged file is not processed again.
#[cocoindex::function(memo)]
async fn process_file(_ctx: &Ctx, file: FileEntry) -> Result<()> {
    let text = file.content_str()?;
    // ... process the file content ...
    Ok(())
}

let app = cocoindex::App::open("files_transform", ".cocoindex_db").await?;
let stats = app
    .run(move |ctx| {
        let source_dir = source_dir.clone();
        async move {
            let files = cocoindex::resources::fs::walk_items(&source_dir, &["**/*.md"])?;
            // One processing component per file.
            mount_each!(files, |file| process_file(ctx, file)).await?;
            Ok(())
        }
    })
    .await?;
```

`mount_each!(items, |item| f(ctx, item))` mounts one processing component per `(key, file)` pair; `FileEntry::key()` is the component subpath. See `examples/rust/files_transform` and `examples/rust/text_embedding` for full programs.

async fn process_file(ctx: &Ctx, file: FileEntry, target: DirTarget) -> Result<()> {

### One file, one declaration

CocoIndex identifies each target file by its key: the `ContextKey` name (none for a path relative to the current directory) and the path under it. The base directory isn't part of the key, which is what lets you move it. The cost is that CocoIndex can't tell when two keys reach the same file on disk. Declare each physical file through exactly one key.

Two keys can reach one file in these ways:

- **Overlapping roots.** Two root directory targets are the same directory, or one is inside the other: under two `ContextKey`s, a `ContextKey` and a plain path, or two paths that reach one directory through a symlink. CocoIndex logs a warning when it applies two such targets. Two `ContextKey`s that point at one base directory are fine if their roots are disjoint, such as <Lang only="python">`FilePath("foo", base_dir=A)` and `FilePath("bar", base_dir=B)`</Lang><Lang only="rust">`FilePath::under_context_dir(&ctx, &A, "foo")?` and `FilePath::under_context_dir(&ctx, &B, "bar")?`</Lang>.
- **One file named two ways.** Names are normalized, so `./a.txt`, `x/../a.txt` and `a.txt` are one key. A flat path and a nested directory target are not: <Lang only="python">`target.declare_file("sub/a.txt")` and `target.declare_dir_target("sub")` with `declare_file("a.txt")`</Lang><Lang only="rust">`target.declare_file(&ctx, "sub/a.txt", ..)` and `target.declare_dir_target(&ctx, "sub", false)` with `declare_file(&ctx, "a.txt", ..)`</Lang> are two keys for one file.
- **Names that differ only in case** on a case-insensitive file system (the default on macOS and Windows). There, `A.txt` and `a.txt` are one file.
- **A file declared through a path into a directory target.** If `sub` is a directory target and its parent also declares `sub/a.txt`, removing the `sub` directory target removes `sub/a.txt` too. Removing a directory target removes the whole directory.

You can switch a file from one key to another in one update if the processing component that declares the file stays the same. Examples are a case-only rename, or a flat path `sub/a.txt` moved to a nested `sub` directory target. CocoIndex writes the file under the new key and skips the delete under the old key. After a case-only rename on a case-insensitive file system, the file keeps its old spelling on disk.

The opposite switch, from a nested directory target to flat paths, takes two updates. A nested directory target is resolved in its own processing component, so CocoIndex removes it after it writes the flat files, and that removal deletes them. Remove the directory target and run an update first. Then declare the flat files and run a second update.

A relative path, such as <Lang only="python">`pathlib.Path("out")`</Lang><Lang only="rust">`PathBuf::from("out")`</Lang>, uses the current directory as its base, and the key holds only the relative path. If you run the app from another directory, the same keys reach other files: CocoIndex doesn't write unchanged files to the new place, and the old files stay. Run the app from one directory, or use a `ContextKey`.
