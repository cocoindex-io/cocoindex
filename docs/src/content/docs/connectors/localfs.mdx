## Stable memoization with FilePath

A key feature of the `localfs` connector is [**stable memoization**](../programming_guide/function) through `FilePath`. When you move your entire project directory, memoization keys remain stable as long as you use the same `ContextKey` key string for the base directory.

### Using ContextKey for stable base directories

Define a `ContextKey[pathlib.Path]` with a stable string identifier. Provide the actual path in your app's lifespan, then pass the key directly to `walk_dir()`, `declare_dir_target()`, and related functions.

{/* Rust: rust/sdk/cocoindex/tests/fs_target.rs */}
<LangTabs>
<Fragment slot="python">

```python
import pathlib
import cocoindex as coco
from cocoindex.connectors import localfs

# Define a stable key (the string "source_dir" is the stable memo identifier)
SOURCE_DIR = coco.ContextKey[pathlib.Path]("source_dir")

@coco.fn
async def app_main() -> None:
    async for file in localfs.walk_dir(SOURCE_DIR, recursive=True):
        # file.file_path has a stable memo key based on "source_dir"
        await process(file)

# In your lifespan, provide the actual path:
async def lifespan(builder: coco.EnvironmentBuilder) -> None:
    builder.provide(SOURCE_DIR, pathlib.Path("./data"))
```

</Fragment>
<Fragment slot="rust">

```rust
use std::path::PathBuf;

use cocoindex::resources::fs::{DirTarget, FilePath};
use cocoindex::Environment;

// The key's name ("OUT_DIR") is the stable identifier.
cocoindex::context_key!(static OUT_DIR: PathBuf);

// Provide the actual directory when you build the environment:
let app = Environment::builder()
    .db_path(&db)
    .provide_key(&OUT_DIR, base)
    .build()
    .await?
    .app("fs_context_dir")
    .await?;

app.update(move |ctx| async move {
    // A path under the key's directory. Memo keys and target keys name
    // the key, not the directory.
    let root = FilePath::under_context_dir(&ctx, &OUT_DIR, "out")?;
    let t = DirTarget::mount(&ctx, root)?;
    t.declare_file(&ctx, "a.txt", b"a")?;
    Ok(())
})
.await?;
```

A `ContextKey<PathBuf>` is declared with `context_key!` and provided with `provide_key`. `FilePath::under_context_dir(ctx, &KEY, path)` builds the path under it. Every function that takes `impl Into<FilePath>`, such as `walk_dir` and `DirTarget::mount`, accepts that `FilePath`.

</Fragment>
</LangTabs>

When you move your project to a different location, just update the path in `builder.provide()` — memoization keys remain the same because they're based on the stable key string (`"source_dir"`), not the filesystem path.

Target files are keyed the same way, by the key string and the relative path. Because the base directory isn't part of the key, CocoIndex can't tell when two keys reach the same file. See [One file, one declaration](#one-file-one-declaration).

### FilePath

`FilePath` combines an optional base directory key and a relative path. Passing a `ContextKey[Path]` directly to any localfs function is equivalent to constructing `FilePath(base_dir=key)`.

`FilePath` supports all `pathlib.PurePath` operations:

{/* Rust: rust/sdk/cocoindex/src/resources/file.rs (FilePath methods), tests/fs_target.rs */}
<LangTabs>
<Fragment slot="python">

```python
SOURCE_DIR = coco.ContextKey[pathlib.Path]("source_dir")
source = localfs.FilePath(base_dir=SOURCE_DIR)

# Create paths using the / operator
config_path = source / "config" / "settings.json"

# Access path properties
print(config_path.name)      # "settings.json"
print(config_path.suffix)    # ".json"
print(config_path.parent)    # FilePath pointing to "config/"

# Resolve to absolute path (requires active component context)
abs_path = config_path.resolve()  # pathlib.Path
```

</Fragment>
<Fragment slot="rust">

```rust
// Under a context directory: the key and the directory it was provided with.
let source = FilePath::under_context_dir(&ctx, &SOURCE_DIR, "")?;

// Create paths with join
let config_path = source.join("config").join("settings.json");

// Access path properties
config_path.name();      // "settings.json"
config_path.suffix();    // ".json"
config_path.parent();    // Some(FilePath pointing to "config")

// Resolve to the full path
let abs_path = config_path.resolve();  // std::path::PathBuf
```

`FilePath::new(path)` builds a path with no base directory. The other `PurePath` operations are `stem`, `suffixes`, `parts`, `with_name`, `with_stem`, `with_suffix`, `relative_to` and `as_posix`.

</Fragment>
</LangTabs>

See [FilePath](../common_resources/data_types#filepath) in Resource Types for full details.

## As source

Use `walk_dir()` to iterate over files in a directory. It returns a `DirWalker` that supports both synchronous and asynchronous iteration.

{/* Rust: rust/sdk/cocoindex/src/resources/fs.rs, examples/rust/text_embedding/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
def walk_dir(
    path: FilePath | Path | ContextKey[Path],
    *,
    live: bool = False,
    recursive: bool = False,
    path_matcher: FilePathMatcher | None = None,
) -> DirWalker
```

</Fragment>
<Fragment slot="rust">

```rust
pub fn walk_dir(path: impl Into<FilePath>) -> DirWalker

impl DirWalker {
    pub fn recursive(self, recursive: bool) -> Self
    pub fn path_matcher(self, matcher: impl FilePathMatcher + 'static) -> Self
    pub fn walk(&self) -> Result<Vec<FileEntry>>
    pub fn items(&self) -> Result<Vec<(String, FileEntry)>>
    pub fn live(self) -> LiveDirWalker   // `fs_live` feature
}

impl LiveDirWalker {
    pub fn poll_interval(self, interval: Duration) -> Self
    pub fn rescan_interval(self, interval: Option<Duration>) -> Self
}
```

The Rust walker is a builder: `walk_dir(path).recursive(true).path_matcher(matcher)`. The `live` flag becomes the `.live()` method, which turns the walker into a `LiveDirWalker` for `ctx.mount_each_live`; `rescan_interval` is a method on it. `walk()` and `items()` block on the directory walk (a live feed walks on a blocking thread).

</Fragment>
</LangTabs>

**Parameters:**

- `path` — The root directory path to walk through. Can be a `FilePath`, a `pathlib.Path`, or a `ContextKey[Path]` (equivalent to `FilePath(base_dir=path)`).
- `live` — If `True`, `items()` returns a [`LiveMapView`](../advanced_topics/live_component#livemapfeed-and-livemapview) that supports live file watching via `mount_each()`.
- `recursive` — If `True`, recursively walk subdirectories.
- `path_matcher` — Optional filter for files and directories. See [PatternFilePathMatcher](../common_resources/data_types#patternfilepathmatcher).

**Returns:** A `DirWalker` that supports async iteration via `async for`.

### Iterating files

`walk_dir()` returns a `DirWalker` that supports async iteration, yielding `File` objects (implementing the [`FileLike`](../common_resources/data_types#filelike) base class):

{/* Rust: rust/sdk/cocoindex/src/resources/fs.rs (DirWalker::walk, FileEntry) */}
<LangTabs>
<Fragment slot="python">

```python
async for file in localfs.walk_dir("/path/to/documents", recursive=True):
    text = await file.read_text()
    ...
```

</Fragment>
<Fragment slot="rust">

```rust
for file in walk_dir("/path/to/documents").recursive(true).walk()? {
    let text = file.content_str()?;
    // ...
}
```

`walk()` reads the directory and returns a `Vec<FileEntry>`, sorted by relative path. `FileEntry` implements `FileLike`, so `file.read_text().await?` works too; `content()` and `content_str()` are the synchronous reads.

</Fragment>
</LangTabs>

File I/O runs in a thread pool, keeping the event loop responsive. The Rust walker has no async iteration: `walk()` and `items()` return the full list.

### Keyed iteration with `items()`

`DirWalker.items()` yields keyed `(str, File)` pairs, useful for associating each file with a stable string key (its relative path):

<LangTabs>
<Fragment slot="python">

```python

```

</Fragment>
<Fragment slot="rust">

```rust

// Shorthand: recursive walk with glob patterns, as `(key, file)` pairs
// ready for `mount_each!`.

```

The key is `FileEntry::key()`: the relative path with forward slashes.

### Filtering files

Use `PatternFilePathMatcher` to filter which files and directories are included:

{/* Rust: examples/rust/text_embedding/src/main.rs, rust/sdk/cocoindex/src/resources/file.rs */}
<LangTabs>
<Fragment slot="python">

```python
from cocoindex.connectors import localfs
from cocoindex.resources.file import PatternFilePathMatcher

# Include only .py and .md files, exclude hidden directories and test files
matcher = PatternFilePathMatcher(
    included_patterns=["**/*.py", "**/*.md"],
    excluded_patterns=["**/.*", "**/test_*", "**/__pycache__"],
)

async for file in localfs.walk_dir("/path/to/project", recursive=True, path_matcher=matcher):
    await process(file)
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::prelude::*;

// Include only .py and .md files, exclude hidden directories and test files
let matcher = PatternFilePathMatcher::new(
    ["**/*.py", "**/*.md"],
    ["**/.*", "**/test_*", "**/__pycache__"],
)?;

for file in walk_dir("/path/to/project")
    .recursive(true)
    .path_matcher(matcher)

}
```

`PatternFilePathMatcher::new(included, excluded)` takes two iterables of patterns; `PatternFilePathMatcher::include(patterns)` takes only included patterns. An excluded pattern that starts with `!` is a negation, as in Python.

### Live file watching

When `live=True`, `items()` returns a [`LiveMapView`](../advanced_topics/live_component#livemapfeed-and-livemapview) instead of a plain `AsyncIterable`. Combined with [`mount_each()`](../programming_guide/processing_component#mount_each), this enables automatic incremental file watching — new, modified, and deleted files are processed without a full rescan:

{/* Rust: examples/rust/text_embedding/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
files = localfs.walk_dir(
    sourcedir, recursive=True,
    path_matcher=PatternFilePathMatcher(included_patterns=["**/*.md"]),
    live=True,
)
await coco.mount_each(process_file, files.items(), target)
```

</Fragment>
<Fragment slot="rust">

```rust
// One component per markdown file; each declares its own rows. In live
// mode (`cocoindex update -L`) the walker keeps watching the directory.
let files = walk_dir(sourcedir)
    .recursive(true)
    .path_matcher(PatternFilePathMatcher::new(
        ["**/*.md"],
        std::iter::empty::<&str>(),
    )?)
    .live()
    .poll_interval(Duration::from_secs(1));
ctx.mount_each_live(&"files", files, move |ctx, file: FileEntry| {
    let table = table.clone();
    async move {
        for row in process_file(&ctx, &file).await? {
            table.declare_row(&ctx, &row)?;
        }
        Ok(())
    }
})
.await
```

`.live()` needs the `fs_live` Cargo feature. It returns a `LiveDirWalker`, a `LiveMapView` plus `LiveMapFeed` that follows the directory through the platform's native watcher: each event updates or removes that file's component alone, and a directory that appears is walked. Where the native watcher cannot be set up, it polls instead, every `poll_interval` (default one second). Every `rescan_interval` (default one hour; `None` disables it) it recreates the watcher and walks the whole directory, as a safety net against events the platform dropped. `ctx.mount_each_live(&key, feed, |ctx, file| ...)` mounts one child component per file. See `examples/rust/text_embedding` for the full program.

</Fragment>
</LangTabs>

See [Live Mode](../programming_guide/live_mode) for how this works and how to enable it on the app.

async fn process_file(ctx: &Ctx, file: FileEntry, target: DirTarget) -> Result<()> {

### One file, one declaration

CocoIndex identifies each target file by its key: the `ContextKey` name (none for a path relative to the current directory) and the path under it. The base directory isn't part of the key, which is what lets you move it. The cost is that CocoIndex can't tell when two keys reach the same file on disk. Declare each physical file through exactly one key. The Rust SDK uses the same keys, so the rules below apply to both SDKs.

Two keys can reach one file in these ways:

- **Overlapping roots.** Two root directory targets are the same directory, or one is inside the other: under two `ContextKey`s, a `ContextKey` and a plain path, or two paths that reach one directory through a symlink. CocoIndex logs a warning when it applies two such targets. Two `ContextKey`s that point at one base directory are fine if their roots are disjoint, such as `FilePath("foo", base_dir=A)` and `FilePath("bar", base_dir=B)`.
- **One file named two ways.** Names are normalized, so `./a.txt`, `x/../a.txt` and `a.txt` are one key. A flat path and a nested directory target are not: `target.declare_file("sub/a.txt")` and `target.declare_dir_target("sub")` with `declare_file("a.txt")` are two keys for one file.
- **Names that differ only in case** on a case-insensitive file system (the default on macOS and Windows). There, `A.txt` and `a.txt` are one file.
- **A file declared through a path into a directory target.** If `sub` is a directory target and its parent also declares `sub/a.txt`, removing the `sub` directory target removes `sub/a.txt` too. Removing a directory target removes the whole directory.

You can switch a file from one key to another in one update if the processing component that declares the file stays the same. Examples are a case-only rename, or a flat path `sub/a.txt` moved to a nested `sub` directory target. CocoIndex writes the file under the new key and skips the delete under the old key. After a case-only rename on a case-insensitive file system, the file keeps its old spelling on disk.

The opposite switch, from a nested directory target to flat paths, takes two updates. A nested directory target is resolved in its own processing component, so CocoIndex removes it after it writes the flat files, and that removal deletes them. Remove the directory target and run an update first. Then declare the flat files and run a second update.

A relative path, such as `pathlib.Path("out")`, uses the current directory as its base, and the key holds only the relative path. If you run the app from another directory, the same keys reach other files: CocoIndex doesn't write unchanged files to the new place, and the old files stay. Run the app from one directory, or use a `ContextKey`.
