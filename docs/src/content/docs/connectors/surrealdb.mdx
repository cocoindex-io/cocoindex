## Connection setup

<Lang only="python">

Create a `ConnectionFactory` and provide it via a `ContextKey`. It holds connection parameters and opens one authenticated connection per event loop, shared by all tables and batches. Call `await factory.close()` at shutdown (in the lifespan, after `yield`) to close it.

</Lang>

<Lang only="rust">

Connect a `surrealdb::Graph` and provide it under a context key. A `Graph` holds one authenticated WebSocket connection to a namespace and database, shared by all tables and batches.

</Lang>

:::note
The key name is load-bearing across runs — it's the stable identity CocoIndex uses to track managed rows. See [ContextKey as stable identity](../programming_guide/context#contextkey-as-stable-identity) before renaming.
:::

```python
        namespace="test",
```

```rust
use cocoindex::connectors::surrealdb::Graph;
use cocoindex::prelude::*;

#[tokio::main]
async fn main() -> Result<()> {

        .await?

        .await?;
    // ...
    Ok(())
}
```

`Graph::connect(url, ns, db, user, pass)` opens one WebSocket connection and signs in as a root user. `url` is the host and port, without the `ws://` scheme or `/rpc` path. A `Graph` has no `close()` method; `builder.on_shutdown(..)` in a `#[cocoindex::lifespan]` function is the place for teardown.

</Fragment>
</LangTabs>

<Lang only="rust">

To sign in as another kind of user, use `Graph::connect_with_credentials(url, ns, db, credentials)`:

{/* Rust: rust/sdk/cocoindex/tests/surrealdb_target.rs (surrealdb_connects_with_a_database_user_when_available) */}
```rust
let graph = Graph::connect_with_credentials(
    &url,
    &ns,
    &db_name,
    surrealdb::Credentials::Database {
        username: "writer".to_string(),
        password: "writer-pass".to_string(),
    },
)
.await?;
```

`surrealdb::Credentials` has one variant per sign-in:

- `Root { username, password }` — a root user (what `Graph::connect` uses).
- `Namespace { username, password }` — a user of the connection's namespace.
- `Database { username, password }` — a user of the connection's database.
- `Record { access, params }` — a record user, through the access method `access` of the connection's database, with the `params` (a `serde_json::Value`) that method expects.
- `None` — no sign-in, for a server started without authentication.

The graph's stable identity is the context key's name; the credentials are not part of any stored state. `graph.client()` returns the underlying `surrealdb::Surreal` client, for queries of your own.

</Lang>

## As target

The `surrealdb` connector provides target state APIs for writing records to normal tables and relation tables. CocoIndex tracks what records should exist and automatically handles upserts and deletions.

<Lang only="python">

Writes are sent as typed parameters (`datetime`, `date`, `Decimal`, `UUID`, `bytes`, `timedelta`, lists and dicts arrive as native SurrealDB types, not strings).

</Lang>

<Lang only="rust">

Writes are sent as typed parameters, never inlined in the statement: top-level values of `datetime`, `uuid`, `decimal`, `duration` and `bytes` columns arrive as native SurrealDB types, not strings, and a top-level `None` is sent as `NONE`.

</Lang>

**Transactions and errors.** The changes of each table are applied in chunks of at most 500 actions, each chunk one transaction and one round trip (`Transaction conflict` errors are retried with backoff, five attempts in all). Atomicity is per chunk, not across tables. Any statement error rolls the chunk back and raises, so the update fails and the affected components are retried on the next run.

<Lang only="python">

**Record IDs** may be a string, an integer, or a tuple/list, which becomes an array ID (`person:['sap', '0001']`). Relation endpoints (`from_id`, `to_id`) take the same forms.

</Lang>

<Lang only="rust">

**Record IDs** are any `IntoRecordId` value: an integer (`i8` through `i64`, `u8` through `u64`, `isize`, `usize`), a `String` or a `&str`. Relation endpoints (`from_id`, `to_id`) take the same forms.

</Lang>

<RustNote>
Array record IDs (`person:['sap', '0001']`) are not supported: `IntoRecordId` has no tuple or list form.
</RustNote>

<Lang only="python">

**Ownership.** `declare_record` writes with `UPSERT ... MERGE`, never `CONTENT`: fields written by other owners survive, and fields you stop declaring are unset. Use `declare_fields` when a pipeline contributes only some fields of a record that another pipeline owns. Relation records are single-owner and are replaced whole.

</Lang>

<Lang only="rust">

**Ownership.** `declare_record` writes with `UPSERT ... SET`, one assignment per field, never `CONTENT`: fields written by other owners survive, and fields you stop declaring are unset. Each declared field's value is replaced whole, nested objects included. Field names must be identifiers (ASCII letters, digits and `_`). Use `declare_fields` when a pipeline contributes only some fields of a record that another pipeline owns. Relation records are single-owner and are replaced whole.

</Lang>

<RustNote>
Python writes a record with `UPSERT ... MERGE`, which merges nested objects. Rust writes `SET`, one assignment per field, so a nested key a row stops declaring is removed with the rest of the old value.
</RustNote>

<Lang only="rust">

**Server version.** A relation record whose fields change is replaced in place. A relation record whose endpoints change (one with an explicit `id`) is replaced with `DELETE` and then `RELATE` in one transaction. SurrealDB 3.2 rejects that with "already exists"; use SurrealDB 3.3.5 or later to move such a relation.

</Lang>

**DDL.** Table and field definitions use `OVERWRITE`, so they are idempotent. <Lang only="python">With `managed_by="user"`</Lang><Lang only="rust">For a user-managed table (`ManagedTargetOptions::user_managed()`)</Lang> CocoIndex never runs DDL on tables (indexes declared with `declare_vector_index` are still created).

### Declaring target states

#### Normal tables (parent state)

Declares a table as a target state. Returns a `TableTarget` for declaring records.

```python
def declare_table_target(
    db: ContextKey,
    table_name: str,
    table_schema: TableSchema[RowT] | None = None,
    *,
    managed_by: Literal["system", "user"] = "system",
) -> TableTarget[RowT, coco.PendingS]
```

</Fragment>
<Fragment slot="rust">

```rust

    ctx: &Ctx,
    graph: &ContextKey<Graph>,
    table_name: impl Into<String>,

    ctx: &Ctx,
    graph: &ContextKey<Graph>,
    table_name: impl Into<String>,
```

`declare_table_target` declares a schemaless, system-managed table in the current component; its records resolve when the component commits. The `mount_*` forms (`mount_table_target`, `mount_table_target_with_schema`, `mount_table_target_with_options`, `mount_table_target_with_schema_and_options`) are `async` and return a target whose records can be declared at once.

</Fragment>
</LangTabs>

**Parameters:**

<Lang only="python">

- `db` — A `ContextKey[surrealdb.ConnectionFactory]` for the SurrealDB connection.
- `table_name` — Name of the table.
- `table_schema` — Optional schema definition (see [Table Schema](#table-schema-from-python-class)). When provided, the table is `SCHEMAFULL`; when omitted, the table is `SCHEMALESS`.
- `managed_by` — Whether CocoIndex manages the table lifecycle (`"system"`) or assumes it exists (`"user"`).

**Returns:** A pending `TableTarget`. Use `await surrealdb.mount_table_target(SURREAL_DB, ...)` to get a resolved target.

</Lang>

<Lang only="rust">

- `graph` — The context key of the `surrealdb::Graph`.
- `table_name` — Name of the table.
- `table_schema` — Optional schema definition (see [Table schema: from a row struct](#table-schema-from-a-row-struct)). When provided, the table is `SCHEMAFULL`; when `None`, the table is `SCHEMALESS`.
- `options` — `ManagedTargetOptions::user_managed()` assumes the table exists; the default lets CocoIndex manage its lifecycle.

**Returns:** A `TableTarget`. It serializes to its stable key (the graph's context key and the table name), so it can be an argument of `mount!`, `use_mount!`, `mount_each!` and memoized functions.

</Lang>

`fields` is a struct or map that serializes to an object of field name to value; it cannot name `id`. For example:

```rust
// Component A owns the record.
players.declare_record(ctx, "ann", &json!({ "name": "Ann" }))?;
// Component B owns the `stats` fields of the same record.
players.declare_fields(ctx, "ann", "stats", &json!({ "score": 7, "rank": 1 }))?;
```

</Fragment>
</LangTabs>

Declares the fields one owner (`group`) contributes to a record. It runs <Lang only="python">`UPDATE $id MERGE {fields}`</Lang><Lang only="rust">`UPDATE $id SET …` with only these fields</Lang> and touches nothing else. When the declaration goes away, or a field is dropped from it, those fields are unset. If the record does not exist, the write raises and is retried on the next run, so declare the base record in the same or another pipeline.

The row type derives `cocoindex::SchemaFields`. The record id is passed to `declare_record` separately, so the struct has no `id` field:

```rust
#[derive(Serialize, SchemaFields)]
struct Session {
    name: String,
    description: Option<String>,        // option<string>
    recorded_at: chrono::DateTime<chrono::Utc>, // datetime
    #[coco(vector = 384)]
    embedding: Vec<f32>,                // array<float, 384>
}

let sessions = surrealdb::mount_table_target_with_schema(
    ctx, &GRAPH, "session", Some(surrealdb::TableSchema::from_row::<Session>()?),
)
.await?;
sessions.declare_record(ctx, session_id, &session)?;
```

A vector field needs its dimension: give it in the attribute (`#[coco(vector = N)]`), or mark the field `#[coco(vector)]` and resolve the dimension with `with_vector_schema` (see [Column overrides](#column-overrides)). Declaring a table with a vector dimension still unresolved is an error.

```python
    column_overrides={"value": surrealdb.SurrealType("decimal")},
)
```

#### VectorSchemaProvider

For `NDArray` fields, a [`VectorSchemaProvider`](../common_resources/vector_schema#vectorschemaprovider) annotation specifies the vector dimension and dtype. See [Vector Schema](../common_resources/vector_schema#vectorschemaprovider) for the full list of annotation options.

</Lang>

<Lang only="rust">

Or override a column of the derived schema. `with_column_type(field, surreal_type)` replaces the type of one column and keeps its nullability. `with_vector_schema(field, provider)` types a `#[coco(vector)]` column as `array<float, N>` from a [`VectorSchemaProvider`](../common_resources/vector_schema#vectorschemaprovider), typically the embedder that fills it (for an embedder held in the context, pass `ctx.get_key(&EMBEDDER)?`):

{/* Rust: rust/sdk/cocoindex/tests/surrealdb_target.rs (surrealdb_from_row_takes_column_overrides) */}
```rust
#[derive(cocoindex::SchemaFields)]
struct Doc {
    title: String,
    rank: Option<i64>,
    #[coco(vector)]
    embedding: Vec<f32>,
}

let embedder = cocoindex::VectorSchema {
    element_type: cocoindex::VectorElementType::Float32,
    size: 4,
};
let schema = TableSchema::from_row::<Doc>()?
    .with_vector_schema("embedding", &embedder)
    .await?                          // embedding: array<float, 4>
    .with_column_type("rank", "float")?; // rank: option<float>
```

Both fail if the schema has no column of that name; `with_vector_schema` also fails on a column that is not a vector.

</Lang>

```rust
#[derive(Clone, Debug, Serialize, cocoindex::SchemaFields)]
pub struct StatementRow {
    pub statement: String,
}

/// A person, tech or org node.
#[derive(Clone, Debug, Serialize, cocoindex::SchemaFields)]
pub struct EntityRow {
    pub name: String,
}

pub async fn create_knowledge_base(ctx: &Ctx, processed: &[ProcessedSession]) -> Result<()> {
    let session_target = surrealdb::mount_table_target_with_schema(
        ctx,
        &GRAPH,
        "session",
        Some(surrealdb::TableSchema::from_row::<SessionRow>()?),
    )
    .await?;
    let statement_target = surrealdb::mount_table_target_with_schema(
        ctx,
        &GRAPH,
        "statement",
        Some(surrealdb::TableSchema::from_row::<StatementRow>()?),
    )
    .await?;
    let person_target = surrealdb::mount_table_target_with_schema(
        ctx,
        &GRAPH,
        "person",
        Some(surrealdb::TableSchema::from_row::<EntityRow>()?),
    )
    .await?;
    let tech_target = surrealdb::mount_table_target_with_schema(
        ctx,
        &GRAPH,
        "tech",
        Some(surrealdb::TableSchema::from_row::<EntityRow>()?),
    )
    .await?;
    // Declare a relation table (schemaless, no id needed)
    let session_statement_target = surrealdb::mount_relation_target(
        ctx,
        &GRAPH,
        "session_statement",
        &session_target,
        &statement_target,
    )
    .await?;
    // A polymorphic relation: a statement mentions a person or a tech.
    let statement_mentions_target = surrealdb::mount_relation_target_many(
        ctx,
        &GRAPH,
        "statement_mentions",
        &[&statement_target],
        &[&person_target, &tech_target],
        None,
    )
    .await?;

    for ps in processed {
        for st in &ps.statements {
            statement_target.declare_record(
                ctx,
                st.id,
                &StatementRow {
                    statement: st.raw.statement.clone(),
                },
            )?;
            // Declare relations — id is auto-derived from endpoints
            session_statement_target.declare_relation(ctx, ps.session_id, st.id)?;
            for name in st.raw.mentioned("person") {
                statement_mentions_target.declare_relation_between(
                    ctx,
                    "statement",
                    st.id,
                    "person",
                    name,
                )?;
            }
        }
    }
    Ok(())
}
```
