The `kafka` connector supports Kafka as both a **source** (consuming messages as a live keyed map, or as a raw event stream) and a **target** (producing messages for declared target states).

## As source

The `kafka` connector can treat a Kafka topic as a live keyed map — each message is an upsert or delete for a key. It returns a [`LiveMapFeed`](../advanced_topics/live_component#livemapfeed-and-livemapview) for use with `mount_each()`. In Rust the feed is a `KafkaTopicMap`, a `LiveMapFeed<String, KafkaMessage>` for `ctx.mount_each_live`.

### Setting up a consumer

Create an `AIOConsumer` directly — no `ContextKey` needed. The consumer must be **unsubscribed** (the connector handles subscription internally to manage partition rebalance callbacks).

{/* Rust: examples/rust/kafka_consume/src/main.rs; SASL/TLS from rust/sdk/SHOWCASE.md, verified against rust/sdk/cocoindex/src/connectors/kafka.rs */}
<LangTabs>
<Fragment slot="python">

```python
from confluent_kafka.aio import AIOConsumer

consumer = AIOConsumer({
    "bootstrap.servers": "localhost:9092",
    "group.id": "my-group",
    "enable.auto.commit": "false",
})
```

</Fragment>
<Fragment slot="rust">

```rust
let consumer = kafka::KafkaConsumer::connect_with_options(
    &["localhost:9092"],
    kafka::KafkaConsumerOptions {
        consumer_group: Some("my-group".to_string()),
        ..Default::default()
    },
)
.await?;
```

`KafkaConsumer::connect(&["localhost:9092"])` connects in plaintext, without authentication and without a consumer group. `KafkaConsumerOptions` adds the consumer group and the connection options; SASL and TLS go through `KafkaConnectOptions`:

```rust
let consumer = kafka::KafkaConsumer::connect_with_options(
    &["broker:9093"],
    kafka::KafkaConsumerOptions {
        consumer_group: Some("my_app".into()),
        connect: kafka::KafkaConnectOptions {
            sasl: Some(kafka::KafkaSasl::ScramSha256 { username, password }),
            tls: Some(kafka::KafkaTls::default()),
        },
    },
)
.await?;
```

`KafkaSasl` is `Plain`, `ScramSha256` or `ScramSha512`, each with a `username` and a `password`. `KafkaTls::default()` trusts the Mozilla root certificates; its `ca_cert_pem`, `client_cert_pem` and `client_key_pem` fields add a private CA and a client certificate for mutual TLS.

The Rust client does not speak the consumer-group protocol. A `consumer_group` is CocoIndex's own durable cursor, kept in the app's state database: the broker does not see its lag, and two processes with the same group name do not share partitions.

</Fragment>
</LangTabs>

**Parameters:**

- `consumer` — An unsubscribed `AIOConsumer`. Auto-commit should be disabled.
- `topic` — The topic to consume. To consume several topics, see [Consuming several topics](#consuming-several-topics).
- `is_deletion` — Optional predicate `(message: Message) -> bool` for custom deletion detection on non-tombstone messages (see [Deletion handling](#deletion-handling)).

**Returns:** A `LiveMapFeed[bytes | str, Message]` where each item is keyed by the message key and the value is the full `confluent_kafka.Message` object. The Rust feed is keyed by the message key as a `String` and yields a `KafkaMessage`: its `topic`, `partition`, `offset`, `key`, `value`, `headers` and `timestamp` fields, with `key_str()` and `value_str()` for the text forms.

### Deletion handling
Messages with `None` value (Kafka tombstones) are **always** treated as deletions. The optional `is_deletion` predicate provides additional deletion logic for non-tombstone messages:

{/* Rust: rust/sdk/cocoindex/src/connectors/kafka.rs (KafkaSourceOptions) */}
<LangTabs>
<Fragment slot="python">

```python
# Default: only tombstones are deletions
items = kafka.topic_as_map(consumer, "my-topic")

# Custom: also treat messages with a specific header as deletions
items = kafka.topic_as_map(
    consumer, "my-topic",
    is_deletion=lambda msg: msg.value() == b"DELETED",
)
```

</Fragment>
<Fragment slot="rust">

```rust
// Default: only tombstones are deletions
let feed = kafka::topic_as_map(&consumer, "my-topic");

// Custom: also treat messages with a specific value as deletions
let feed = kafka::topic_as_map_with_options(
    &consumer,
    "my-topic",
    kafka::KafkaSourceOptions {
        is_deletion: Some(Arc::new(|msg: &KafkaMessage| {
            msg.value.as_deref() == Some(b"DELETED")
        })),
    },
);
```

</Fragment>

### Offset management

Offsets are committed automatically with at-least-once semantics. Messages are processed in parallel, but an offset is only committed after all earlier messages in the same partition have been fully processed. Messages with `None` keys are logged as errors and skipped.

In Rust, a consumer with a `consumer_group` commits the offsets of the records a live run has processed, per partition, to the app's state database under that group name once their child components have synced. The next live run resumes from them. A consumer without a group re-reads the topic on every run. A record with no key is skipped.

### Readiness

The feed signals readiness after catching up to the high watermark offsets that existed when consumption started. After that, it continues consuming indefinitely until the app is stopped.

### Example

{/* Rust: examples/rust/kafka_consume/src/main.rs */}

<Fragment slot="python">

```python
import pathlib

from confluent_kafka import Message
from confluent_kafka.aio import AIOConsumer
from cocoindex.connectors import kafka, localfs
import cocoindex as coco


@coco.fn(memo=True)
async def process_message(msg: Message, target: localfs.DirTarget) -> None:
    key = msg.key()
    value = msg.value()
    if isinstance(key, bytes):
        key = key.decode()
    target.declare_file(filename=f"{key}.bin", content=value)


@coco.fn
async def app_main(outdir: pathlib.Path) -> None:
    target = await localfs.mount_dir_target(outdir)

    consumer = AIOConsumer({
        "bootstrap.servers": "localhost:9092",
        "group.id": "my-group",
        "enable.auto.commit": "false",
    })
    items = kafka.topic_as_map(consumer, "my-topic")
    await coco.mount_each(process_message, items, target)


app = coco.App(
    coco.AppConfig(name="KafkaToFiles"),
    app_main,
    outdir=pathlib.Path("./out"),
)
app.update_blocking(live=True)
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::connectors::kafka::{self, KafkaMessage};
use cocoindex::{App, UpdateOptions};

#[tokio::main]
async fn main() -> cocoindex::Result<()> {
    let consumer = kafka::KafkaConsumer::connect_with_options(
        &["localhost:9092"],
        kafka::KafkaConsumerOptions {
            consumer_group: Some("kafka_consume".to_string()),
            ..Default::default()
        },
    )
    .await?;

    let app = App::open("kafka_consume", ".cocoindex_db").await?;

    let body = move |ctx: cocoindex::Ctx| {
        let consumer = consumer.clone();
        async move {
            let feed = kafka::topic_as_map(&consumer, "my-topic");
            ctx.mount_each_live(&"messages", feed, move |_ctx, message: KafkaMessage| {
                async move {
                    println!(
                        "message {}@{}/{}: {}",
                        message.key_str().unwrap_or_default(),
                        message.partition,
                        message.offset,
                        message.value_str().unwrap_or_default()
                    );
                    Ok(())
                }
            })
            .await
        }
    };

    let handle = app.start_update_with_options(
        UpdateOptions {
            full_reprocess: false,
            live: true,
            ..UpdateOptions::default()
        },
        body,
    )?;
    handle.result().await?;
    Ok(())
}
```

`ctx.mount_each_live(&"messages", feed, process_fn)` mounts one child component per message key. Without `live: true`, `app.run(body)` takes one snapshot of the topic up to its high watermark and stops. The full program is `examples/rust/kafka_consume`; it pairs with `examples/rust/csv_to_kafka`.

### Consuming several topics

`topic_as_map()` keys each item by its message key alone, so one feed reads one topic. To consume several topics, create one feed per topic, each with its own consumer, and mount each feed under its own `mount_each()` subpath. The subpath keeps the same message key on two topics (for example, `42` on `users` and `42` on `orders`) in two separate components.

{/* Rust: examples/rust/kafka_consume/src/main.rs (one feed per topic) */}
<LangTabs>
<Fragment slot="python">

```python
@coco.fn
async def app_main(outdir: pathlib.Path) -> None:
    for topic in ["users", "orders"]:
        target = await localfs.mount_dir_target(outdir / topic)
        consumer = AIOConsumer({
            "bootstrap.servers": "localhost:9092",
            "group.id": "my-group",
            "enable.auto.commit": "false",
        })
        items = kafka.topic_as_map(consumer, topic)
        await coco.mount_each(
            coco.component_subpath(topic), process_message, items, target
        )
```

</Fragment>
<Fragment slot="rust">

```rust
for topic in ["users", "orders"] {
    let feed = kafka::topic_as_map(&consumer, topic);
    ctx.mount_each_live(&topic, feed, move |_ctx, message: KafkaMessage| {
        async move {
            println!("{}: {}", message.topic, message.key_str().unwrap_or_default());
            Ok(())
        }
    })
    .await?;
}
```

The first argument of `mount_each_live` is the subpath; here it is the topic name. One `KafkaConsumer` can serve several feeds.

</Fragment>
</LangTabs>

Each topic also writes to its own directory here, because `process_message` names a file by the message key only.

#### Switching from a list of topics

This section applies to the Python SDK. The Rust `topic_as_map` takes one topic.

Passing a list of topics to `topic_as_map()` is deprecated and emits a `DeprecationWarning`.

- **One topic in the list:** change `["my-topic"]` to `"my-topic"`. The item keys stay the same, so nothing else changes.
- **Several topics in the list:** the list form keys items by the message key alone, so the same key on two topics is one item, and a tombstone on one topic deletes what the other topic's message produced. The list form keeps working this way until you switch.

Switching from several topics in a list to one feed per topic changes the item keys. The live map resumes from the committed offsets and never re-reads a topic, so the components under the old keys are never cleaned up, and the new components get only messages that arrive after the switch. Replay the topics when you switch:

1. Stop the app and drop it: `cocoindex drop main.py` (or `App.drop()`). This removes the outputs of the old components.
2. Reset the consumer group to the earliest offset of each topic, for example:

   ```bash
   kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group my-group \
     --reset-offsets --to-earliest --topic users --topic orders --execute
   ```

3. Change the code to one feed per topic and start the app again. It processes every message the topics still retain.

## As a live stream

Some downstream connectors don't model Kafka messages as a keyed map — they treat each message as an opaque event payload (e.g. the [OCI Object Storage](./oci_object_storage#live-bucket-watching) live mode ingests Object Storage event JSON delivered through OCI Streaming). For these, the `kafka` connector exposes a topic as a [`LiveStream`](../advanced_topics/live_component#livestream) — CocoIndex's keyless counterpart to `LiveMapFeed`, an opaque sequence of messages with the same readiness and back-pressure machinery but no key/delete semantics.

Set up the consumer the same way as for [`topic_as_map()`](#setting-up-a-consumer).

### `topic_as_stream()`

{/* Rust: rust/sdk/cocoindex/src/connectors/kafka.rs; usage in rust/sdk/cocoindex/tests/kafka_source.rs */}
<LangTabs>
<Fragment slot="python">

```python
def topic_as_stream(
    consumer: AIOConsumer,
    topics: list[str],
) -> TopicStream:
```

</Fragment>
<Fragment slot="rust">

```rust
pub fn topic_as_stream(
    consumer: &KafkaConsumer,
    topics: impl IntoIterator<Item = impl Into<String>>,
) -> KafkaTopicStream
```

For example:

```rust
let feed = kafka::topic_as_stream(&consumer, ["users", "orders"]);
ctx.mount_each_live(&"events", feed, move |_ctx, message: KafkaMessage| {
    async move { Ok(()) }
})
.await?;
```

The Rust SDK has no `LiveStream` type. `KafkaTopicStream` is a `LiveMapFeed<String, KafkaMessage>` keyed by the record's `"{topic}:{partition}:{offset}"` position, so every record, tombstones included, becomes a distinct child of `mount_each_live`, and nothing is compacted or deleted.

</Fragment>
</LangTabs>

**Parameters:**

- `consumer` — An unsubscribed `AIOConsumer`. Auto-commit should be disabled.
- `topics` — Topics to subscribe to.

**Returns:** A `TopicStream` (a `LiveStream[Message]`) that delivers raw `confluent_kafka.Message` objects to its subscriber. [Offset management](#offset-management) and [readiness](#readiness) behave identically to `topic_as_map()`.

### `TopicStream.payloads()`

```python
def payloads(self) -> LiveStream[bytes]:
```

A view over the same `TopicStream` that yields each message's value (the byte payload) instead of the full `Message`. Null-valued messages (Kafka tombstones) are filtered out of this view; consumers that need tombstone semantics should subscribe to the `TopicStream` directly.

This is the typical input for sources that consume opaque event payloads:

```python
from confluent_kafka.aio import AIOConsumer
from cocoindex.connectors import kafka, oci_object_storage

consumer = AIOConsumer({
    "bootstrap.servers": "localhost:9092",
    "group.id": "my-group",
    "enable.auto.commit": "false",
})
topic_stream = kafka.topic_as_stream(consumer, ["object-storage-events"])

walker = oci_object_storage.list_objects(
    client, "my-namespace", "my-bucket",
    live_stream=topic_stream.payloads(),
)
```

For a complete app using this pattern, see the [OCI Object Storage live-mode example](./oci_object_storage#example).

The Rust SDK has no `payloads()` view: filter on `KafkaMessage::value` (`None` for a tombstone) in the `mount_each_live` closure. The Rust OCI live walker, `oci_object_storage::list_objects_live`, takes a `futures::Stream<Item = Vec<u8>>` of event payloads rather than a Kafka feed.

:::caution
A `TopicStream` (and any `payloads()` view of it) supports at most one active watcher — the underlying consumer can hold only one subscription. A second concurrent `watch()` raises `RuntimeError`.
:::

## As target

The `kafka` connector provides target state APIs for producing messages to Kafka topics. Topics are user-managed (CocoIndex does not create or drop topics) — CocoIndex only produces messages to them.

### Setting up a producer

Create a `ContextKey[AIOProducer]` to identify your producer, then provide it in your lifespan:

:::note
The key name is load-bearing across runs — it's the stable identity CocoIndex uses to track target state for topics produced through this key. See [ContextKey as stable identity](../programming_guide/context#contextkey-as-stable-identity) before renaming.
:::

The key is a non-empty `&str`, sent as its UTF-8 bytes; the value is any byte slice, so a `&str`, `String` or `Vec<u8>` works.

</Fragment>

**Parameters:**

- `key` — The message key, used as the stable identity for change detection. A `str` key is sent as its UTF-8 bytes, so `"a"` and `b"a"` are the same Kafka key: declare each key in one form only. If a key changes form between runs (for example, from `"a"` to `b"a"`), CocoIndex publishes the new form and sends no deletion message for the old form, so the record stays.
- `value` — The message value.

CocoIndex fingerprints the value and only produces a message when it has changed since the last run.

### Deletion handling

While the topic is still declared, a message target state that is no longer declared gets a deletion message. The behavior depends on `deletion_value_fn`:

- **Without callback** (default): Produces a message with the key and no value (Kafka tombstone).
- **With callback**: Calls `deletion_value_fn(key)` to produce the deletion value.

{/* Rust: rust/sdk/cocoindex/tests/kafka_target.rs */}

#### Abandoning a topic

Removing the topic declaration itself — or calling `App.drop()` — **abandons** the topic: CocoIndex stops producing to it and emits no tombstones for the messages it produced earlier. Renaming the topic in code abandons the old topic the same way. Avoid reusing an abandoned topic in a later declaration: its stale keys remain and are never tombstoned, and keys you declare again are republished as new even when their values are unchanged.

To tombstone everything before abandoning a topic, drain it first:

1. Keep the topic declared, but declare no messages in it.
2. Run an update — every previously produced key gets a deletion message.
3. Remove the topic declaration.

### Example

{/* Rust: examples/rust/csv_to_kafka/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
from collections.abc import AsyncIterator

from confluent_kafka import AIOProducer
from cocoindex.connectors import kafka, localfs
import cocoindex as coco

KAFKA_PRODUCER = coco.ContextKey[AIOProducer]("my_kafka_producer")


@coco.lifespan
async def coco_lifespan(builder: coco.EnvironmentBuilder) -> AsyncIterator[None]:
    producer = AIOProducer({"bootstrap.servers": "localhost:9092"})
    builder.provide(KAFKA_PRODUCER, producer)
    yield


@coco.fn(memo=True)
async def process_file(
    file: localfs.File, topic_target: kafka.KafkaTopicTarget
) -> None:
    content = await file.read_bytes()
    topic_target.declare_target_state(
        key=file.file_path.path.as_posix().encode(),
        value=content,
    )


@coco.fn
async def app_main() -> None:
    topic_target = await kafka.mount_kafka_topic_target(
        KAFKA_PRODUCER, "file-contents"
    )

    files = localfs.walk_dir(localfs.FilePath(path="./data"))
    await coco.mount_each(process_file, files.items(), topic_target)


app = coco.App(
    coco.AppConfig(name="FilesToKafka"),
    app_main,
)
app.update_blocking(report_to_stdout=True)
```

use cocoindex::connectors::kafka::{self, KafkaProducer};
use cocoindex::prelude::*;
use cocoindex::resources::fs::FileEntry;
use cocoindex::Environment;

cocoindex::context_key!(static PRODUCER: KafkaProducer);

/// Parse one CSV file into `(message_key, json_value)` pairs. Memoized: a file
/// whose content is unchanged since the last run is not re-parsed.
#[cocoindex::function(memo)]

                    &PRODUCER,
                    topic,
                    kafka::KafkaTopicOptions::default(),

                let per_file = mount_each!(files, |file| process_csv(ctx, file)).await?;

                for messages in &per_file {
                    for (key, value) in messages {
                        target.declare_message(&ctx, key, value)?;
                    }
                }
                Ok(())
            }
        })
        .await?;
    println!("{stats}");
    Ok(())
