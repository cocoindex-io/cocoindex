## As source

The `kafka` connector can treat a Kafka topic as a live keyed map — each message is an upsert or delete for a key. It returns a [`LiveMapFeed`](../advanced_topics/live_component#livemapfeed-and-livemapview) for use with <Lang only="python">`mount_each()`</Lang><Lang only="rust">`ctx.mount_each_live`: a `KafkaTopicMap`, which is a `LiveMapFeed<String, KafkaMessage>`</Lang>.

### Setting up a consumer

<Lang only="python">

Create an `AIOConsumer` directly — no `ContextKey` needed. The consumer must be **unsubscribed** (the connector handles subscription internally to manage partition rebalance callbacks).

</Lang>

<Lang only="rust">

Create a `KafkaConsumer` directly — no `ContextKey` needed. It is cheap to clone, and one consumer can serve several feeds.

</Lang>

{/* Rust: examples/rust/kafka_consume/src/main.rs; SASL/TLS from rust/sdk/SHOWCASE.md, verified against rust/sdk/cocoindex/src/connectors/kafka.rs */}
<LangTabs>
<Fragment slot="python">

```python
from confluent_kafka.aio import AIOConsumer

consumer = AIOConsumer({
    "bootstrap.servers": "localhost:9092",
    "group.id": "my-group",
    "enable.auto.commit": "false",
})
```

</Fragment>
<Fragment slot="rust">

```rust
let consumer = kafka::KafkaConsumer::connect_with_options(
    &["localhost:9092"],
    kafka::KafkaConsumerOptions {
        consumer_group: Some("my-group".to_string()),
        ..Default::default()
    },
)
.await?;
```

`KafkaConsumer::connect(&["localhost:9092"])` connects in plaintext, without authentication and without a consumer group. `KafkaConsumerOptions` adds the consumer group and the connection options; SASL and TLS go through `KafkaConnectOptions`:

```rust
let consumer = kafka::KafkaConsumer::connect_with_options(
    &["broker:9093"],
    kafka::KafkaConsumerOptions {
        consumer_group: Some("my_app".into()),
        connect: kafka::KafkaConnectOptions {
            sasl: Some(kafka::KafkaSasl::ScramSha256 { username, password }),
            tls: Some(kafka::KafkaTls::default()),
        },
    },
)
.await?;
```

`KafkaSasl` is `Plain`, `ScramSha256` or `ScramSha512`, each with a `username` and a `password`. `KafkaTls::default()` trusts the Mozilla root certificates; its `ca_cert_pem`, `client_cert_pem` and `client_key_pem` fields add a private CA and a client certificate for mutual TLS. For a connection setup these options cannot express, build an `rskafka` client yourself and wrap it with `KafkaConsumer::from_client(client, state_id, consumer_group)`, where `state_id` is the cluster's stable identity (for example its bootstrap-server list), never a credential.

</Fragment>
</LangTabs>

<RustNote>
The client does not speak the consumer-group protocol. A `consumer_group` is CocoIndex's own durable cursor, kept in the app's state database: the broker does not see its lag, and two processes with the same group name do not share partitions.
</RustNote>

### Deletion handling
Messages with <Lang only="python">`None` value</Lang><Lang only="rust">a `None` value</Lang> (Kafka tombstones) are **always** treated as deletions. The optional `is_deletion` predicate provides additional deletion logic for non-tombstone messages:

{/* Rust: rust/sdk/cocoindex/src/connectors/kafka.rs (KafkaSourceOptions) */}
<LangTabs>
<Fragment slot="python">

```python
# Default: only tombstones are deletions
items = kafka.topic_as_map(consumer, "my-topic")

# Custom: also treat messages with a specific header as deletions
items = kafka.topic_as_map(
    consumer, "my-topic",
    is_deletion=lambda msg: msg.value() == b"DELETED",
)
```

</Fragment>
<Fragment slot="rust">

```rust
// Default: only tombstones are deletions
let feed = kafka::topic_as_map(&consumer, "my-topic");

// Custom: also treat messages with a specific value as deletions
let feed = kafka::topic_as_map_with_options(
    &consumer,
    "my-topic",
    kafka::KafkaSourceOptions {
        is_deletion: Some(Arc::new(|msg: &KafkaMessage| {
            msg.value.as_deref() == Some(b"DELETED")
        })),
    },
);
```

</Fragment>

### Offset management

Offsets are committed automatically with at-least-once semantics. Messages are processed in parallel, but an offset is only committed after all earlier messages in the same partition have been fully processed. Messages with `None` keys are <Lang only="python">logged as errors and </Lang>skipped.

<Lang only="rust">

A consumer with a `consumer_group` commits the offsets of the records a live run has processed, per partition, to the app's state database under that group name once their child components have synced. The next live run resumes from them. A consumer without a group re-reads the topic on every run.

</Lang>

### Readiness

The feed signals readiness after catching up to the high watermark offsets that existed when consumption started. After that, it continues consuming indefinitely until the app is stopped.

### Example

{/* Rust: examples/rust/kafka_consume/src/main.rs */}
<LangTabs>
<Fragment slot="python">

```python
import pathlib

from confluent_kafka import Message
from confluent_kafka.aio import AIOConsumer
from cocoindex.connectors import kafka, localfs
import cocoindex as coco


@coco.fn(memo=True)
async def process_message(msg: Message, target: localfs.DirTarget) -> None:
    key = msg.key()
    value = msg.value()
    if isinstance(key, bytes):
        key = key.decode()
    target.declare_file(filename=f"{key}.bin", content=value)


@coco.fn
async def app_main(outdir: pathlib.Path) -> None:
    target = await localfs.mount_dir_target(outdir)

    consumer = AIOConsumer({
        "bootstrap.servers": "localhost:9092",
        "group.id": "my-group",
        "enable.auto.commit": "false",
    })
    items = kafka.topic_as_map(consumer, "my-topic")
    await coco.mount_each(process_message, items, target)


app = coco.App(
    coco.AppConfig(name="KafkaToFiles"),
    app_main,
    outdir=pathlib.Path("./out"),
)
app.update_blocking(live=True)
```

</Fragment>
<Fragment slot="rust">

```rust
use cocoindex::connectors::kafka::{self, KafkaMessage};
use cocoindex::{App, UpdateOptions};

#[tokio::main]
async fn main() -> cocoindex::Result<()> {
    let consumer = kafka::KafkaConsumer::connect_with_options(
        &["localhost:9092"],
        kafka::KafkaConsumerOptions {
            consumer_group: Some("kafka_consume".to_string()),
            ..Default::default()
        },
    )
    .await?;

    let app = App::open("kafka_consume", ".cocoindex_db").await?;

    let body = move |ctx: cocoindex::Ctx| {
        let consumer = consumer.clone();
        async move {
            let feed = kafka::topic_as_map(&consumer, "my-topic");
            ctx.mount_each_live(&"messages", feed, move |_ctx, message: KafkaMessage| {
                async move {
                    println!(
                        "message {}@{}/{}: {}",
                        message.key_str().unwrap_or_default(),
                        message.partition,
                        message.offset,
                        message.value_str().unwrap_or_default()
                    );
                    Ok(())
                }
            })
            .await
        }
    };

    let handle = app.start_update_with_options(
        UpdateOptions {
            full_reprocess: false,
            live: true,
            ..UpdateOptions::default()
        },
        body,
    )?;
    handle.result().await?;
    Ok(())
}
```

`ctx.mount_each_live(&"messages", feed, process_fn)` mounts one child component per message key. Without `live: true`, `app.run(body)` takes one snapshot of the topic up to its high watermark and stops. The full program is `examples/rust/kafka_consume`; it pairs with `examples/rust/csv_to_kafka`.

### Consuming several topics

`topic_as_map()` keys each item by its message key alone, so one feed reads one topic. To consume several topics, create one feed per topic<Lang only="python">, each with its own consumer,</Lang> and mount each feed under its own <Lang only="python">`mount_each()`</Lang><Lang only="rust">`mount_each_live`</Lang> subpath. The subpath keeps the same message key on two topics (for example, `42` on `users` and `42` on `orders`) in two separate components.

{/* Rust: examples/rust/kafka_consume/src/main.rs (one feed per topic) */}
<LangTabs>
<Fragment slot="python">

```python
@coco.fn
async def app_main(outdir: pathlib.Path) -> None:
    for topic in ["users", "orders"]:
        target = await localfs.mount_dir_target(outdir / topic)
        consumer = AIOConsumer({
            "bootstrap.servers": "localhost:9092",
            "group.id": "my-group",
            "enable.auto.commit": "false",
        })
        items = kafka.topic_as_map(consumer, topic)
        await coco.mount_each(
            coco.component_subpath(topic), process_message, items, target
        )
```

</Fragment>
<Fragment slot="rust">

```rust
for topic in ["users", "orders"] {
    let feed = kafka::topic_as_map(&consumer, topic);
    ctx.mount_each_live(&topic, feed, move |_ctx, message: KafkaMessage| {
        async move {
            println!("{}: {}", message.topic, message.key_str().unwrap_or_default());
            Ok(())
        }
    })
    .await?;
}
```

The first argument of `mount_each_live` is the subpath; here it is the topic name. One `KafkaConsumer` can serve several feeds.

</Fragment>
</LangTabs>

Each topic also writes to its own directory here, because `process_message` names a file by the message key only.

<Lang only="python">

#### Switching from a list of topics

Passing a list of topics to `topic_as_map()` is deprecated and emits a `DeprecationWarning`.

- **One topic in the list:** change `["my-topic"]` to `"my-topic"`. The item keys stay the same, so nothing else changes.
- **Several topics in the list:** the list form keys items by the message key alone, so the same key on two topics is one item, and a tombstone on one topic deletes what the other topic's message produced. The list form keeps working this way until you switch.

Switching from several topics in a list to one feed per topic changes the item keys. The live map resumes from the committed offsets and never re-reads a topic, so the components under the old keys are never cleaned up, and the new components get only messages that arrive after the switch. Replay the topics when you switch:

1. Stop the app and drop it: `cocoindex drop main.py` (or `App.drop()`). This removes the outputs of the old components.
2. Reset the consumer group to the earliest offset of each topic, for example:

   ```bash
   kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group my-group \
     --reset-offsets --to-earliest --topic users --topic orders --execute
   ```

3. Change the code to one feed per topic and start the app again. It processes every message the topics still retain.

</Lang>

## As a live stream

Some downstream connectors don't model Kafka messages as a keyed map — they treat each message as an opaque event payload (e.g. the [OCI Object Storage](./oci_object_storage#live-bucket-watching) live mode ingests Object Storage event JSON delivered through OCI Streaming). For these, the `kafka` connector exposes a topic as a [`LiveStream`](../advanced_topics/live_component#livestream) — CocoIndex's keyless counterpart to `LiveMapFeed`, an opaque sequence of messages with the same readiness and back-pressure machinery but no key/delete semantics.

Set up the consumer the same way as for [`topic_as_map()`](#setting-up-a-consumer).

### `topic_as_stream()`

</Fragment>
<Fragment slot="rust">

For example:

```rust
let feed = kafka::topic_as_stream(&consumer, ["users", "orders"]);
ctx.mount_each_live(&"events", feed, move |_ctx, message: KafkaMessage| {
    async move { Ok(()) }
})
.await?;
```

`KafkaTopicStream` is a `LiveStream<KafkaMessage>`. It is also a `LiveMapFeed<String, KafkaMessage>` for `mount_each_live`, as above: each record becomes a distinct child keyed by its `"{topic}:{partition}:{offset}"` position, tombstones included, and nothing is compacted or deleted. The position keys are stable, so a replayed catch-up reconciles to no-ops.

</Fragment>
</LangTabs>

<Lang only="python">

- `consumer` — An unsubscribed `AIOConsumer`. Auto-commit should be disabled.
- `topics` — Topics to subscribe to.

**Returns:** A `TopicStream` (a `LiveStream[Message]`) that delivers raw `confluent_kafka.Message` objects to its subscriber. [Offset management](#offset-management) and [readiness](#readiness) behave identically to `topic_as_map()`.

</Lang>

<Lang only="rust">

- `consumer` — A `KafkaConsumer`.
- `topics` — Topics to read, across all their partitions.

**Returns:** A `KafkaTopicStream` (a `LiveStream<KafkaMessage>`) that delivers every record, tombstones included, to its subscriber. [Offset management](#offset-management) and [readiness](#readiness) behave identically to `topic_as_map()`.

</Lang>

## As target

The `kafka` connector provides target state APIs for producing messages to Kafka topics. Topics are user-managed (CocoIndex does not create or drop topics) — CocoIndex only produces messages to them.

### Setting up a producer

<Lang only="python">Create a `ContextKey[AIOProducer]` to identify your producer, then provide it in your lifespan:</Lang><Lang only="rust">Declare a `ContextKey<KafkaProducer>` with `context_key!` to identify your producer, then provide it when you build the environment:</Lang>

:::note
The key name is load-bearing across runs — it's the stable identity CocoIndex uses to track target state for topics produced through this key. See [ContextKey as stable identity](../programming_guide/context#contextkey-as-stable-identity) before renaming.
:::

- `key` — The message key, used as the stable identity for change detection. A `str` key is sent as its UTF-8 bytes, so `"a"` and `b"a"` are the same Kafka key: declare each key in one form only. If a key changes form between runs (for example, from `"a"` to `b"a"`), CocoIndex publishes the new form and sends no deletion message for the old form, so the record stays.
- `value` — The message value.

</Lang>

- `value` — The message value: any byte slice, so a `&str`, `String` or `Vec<u8>` works.

</Lang>

CocoIndex fingerprints the value and only produces a message when it has changed since the last run.

### Deletion handling

While the topic is still declared, a message target state that is no longer declared gets a deletion message. The behavior depends on `deletion_value_fn`:

- **Without callback** (default): Produces a message with the key and no value (Kafka tombstone).
- **With callback**: Calls `deletion_value_fn(key)` to produce the deletion value.

<RustNote>
The callback lives in your process: a run that declares the topic target, or drops the app from a process that did, applies it. `App::drop_state` from a process that never declared the topic target produces tombstones.
</RustNote>

#### Abandoning a topic

Removing the topic declaration itself — or calling <Lang only="python">`App.drop()`</Lang><Lang only="rust">`App::drop_state`</Lang> — **abandons** the topic: CocoIndex stops producing to it and emits no tombstones for the messages it produced earlier. Renaming the topic in code abandons the old topic the same way. Avoid reusing an abandoned topic in a later declaration: its stale keys remain and are never tombstoned, and keys you declare again are republished as new even when their values are unchanged.

To tombstone everything before abandoning a topic, drain it first:

1. Keep the topic declared, but declare no messages in it.
2. Run an update — every previously produced key gets a deletion message.
3. Remove the topic declaration.
