The `neo4j` connector writes records to [Neo4j](https://neo4j.com), a property graph database. It supports node tables (labels), relationship tables (edge types), per-database multitenancy (one Neo4j cluster, many isolated databases), real Cypher uniqueness constraints, and vector indexes via the `CREATE VECTOR INDEX` DDL form.

## Connection setup

<Lang only="python">

Create a `ConnectionFactory` and provide it via a `ContextKey`. The factory holds the Bolt URI, optional auth, and the target database name; it opens one connection-pooled Neo4j async driver per event loop, on first use on that loop, shared by all tables and batches. Call `await factory.close()` at shutdown (in the lifespan, after `yield`) to close it.

</Lang>

<Lang only="rust">

Connect a `neo4j::Graph` and provide it under a context key. A `Graph` holds a connection pool and the name of the database its statements run on; all tables and batches share it.

</Lang>

:::note
The key name is load-bearing across runs — it's the stable identity CocoIndex uses to track managed rows. See [ContextKey as stable identity](../programming_guide/context#contextkey-as-stable-identity) before renaming.
:::

{/* Rust: examples/rust/meeting_notes_graph_neo4j/src/main.rs */}
<LangTabs>

```python
from collections.abc import AsyncIterator
from cocoindex.connectors import neo4j
import cocoindex as coco

KG_DB: coco.ContextKey[neo4j.ConnectionFactory] = coco.ContextKey("kg_db")

@coco.lifespan
async def coco_lifespan(builder: coco.EnvironmentBuilder) -> AsyncIterator[None]:
    factory = neo4j.ConnectionFactory(
        uri="bolt://localhost:7687",
        auth=("neo4j", "cocoindex"),
        database="neo4j",
    )
    builder.provide(KG_DB, factory)
    yield
    await factory.close()
```

A single Neo4j cluster can host many isolated databases. Pair each database with its own context key and <Lang only="python">`ConnectionFactory(database=...)`</Lang><Lang only="rust">`neo4j::Graph`</Lang>:

```python
KG_DB: coco.ContextKey[neo4j.ConnectionFactory] = coco.ContextKey("kg_db")
APIS_DB: coco.ContextKey[neo4j.ConnectionFactory] = coco.ContextKey("apis_db")

@coco.lifespan
async def coco_lifespan(builder: coco.EnvironmentBuilder) -> AsyncIterator[None]:
    uri = "bolt://localhost:7687"

    apis_factory = neo4j.ConnectionFactory(uri=uri, auth=auth, database="apis")
    builder.provide(KG_DB, kg_factory)
    builder.provide(APIS_DB, apis_factory)
    yield
    await kg_factory.close()
    await apis_factory.close()
```

## Running Cypher queries

Reuse the same factory for reads and graph algorithms: `await factory.acquire()` returns a graph handle with `query(cypher, params=None)`. Each call opens a session in the factory's database, consumes the result into a list of dictionaries, and closes the session before returning. The connection-pooled driver is shared with the targets; do not create a second driver for retrieval.

For example, using `KG_DB` from the lifespan above:

```python
@coco.fn
async def outgoing_neighbors(node_id: str) -> list[dict[str, object]]:
    graph = await coco.use_context(KG_DB).acquire()
    return await graph.query(
        "MATCH (n:Entity {id: $node_id})-[r]->(neighbor) "
        "RETURN type(r) AS relationship, neighbor.id AS neighbor_id",
        {"node_id": node_id},
    )
```

Pass values in the parameter dictionary, not by interpolating them into Cypher. Parameter names such as `query` and `parameters` are valid too; the dictionary is passed to the driver separately from its own method arguments. Queries return all rows in memory, so use Cypher filters and `LIMIT` for large graphs.

When a query depends on target writes from a mounted component, wait for that component's `handle.ready()` before querying. `await coco.mount(...)` alone dispatches the component and returns its handle; it does not wait for its target states to be synced. Keep graph reads non-memoized, as in the example: the query helper does not track changes to database contents for memo invalidation. Direct Cypher writes are not declared target states and therefore do not receive CocoIndex's incremental reconciliation or cleanup.

## As target

The `neo4j` connector provides target state APIs for writing nodes to node tables and edges to relationship tables. CocoIndex tracks what records should exist and automatically handles upserts and deletions.

The record writes of all tables of one database are applied together, in batches. Within a batch, writes are ordered as **node upserts → relation upserts → relation deletes → node deletes** so dependent edges always see their endpoints. A batch is applied in Neo4j transactions of at most 1,000 record writes each, one after the other. A transaction that fails rolls back, and the components of the batch are retried; earlier transactions of the batch stay committed, which is safe because the writes are idempotent (`MERGE`). A transaction that fails with a transient error (typically a deadlock between concurrent writers merging edges onto the same nodes) is retried with backoff, up to 8 attempts, before the failure is reported. A transaction that goes over the server's transaction memory limit is split in two instead.

<Lang only="rust">

Within a transaction, the records of one statement shape (the node upserts of one label, the edge upserts of one relationship type and endpoint labels, and so on) are written by one `UNWIND $rows AS row …` statement.

</Lang>

<Lang only="python">

:::note
The node and relationship APIs below replace the table and relation APIs (`mount_table_target`, `mount_relation_target`, …), which are deprecated. To move an existing table over, see [Deprecated: table and relation APIs](#deprecated-table-and-relation-apis).
:::

</Lang>

<RustNote>
The Rust functions keep the names `mount_table_target` / `TableTarget` and `mount_relation_target` / `RelationTarget`. They have the semantics of Python's node and relationship APIs (`mount_node_target`, `mount_relationship_target`), not of Python's deprecated table and relation APIs: a node table and a relationship table live in separate key spaces, so a label and a relationship type may share a name, and a derived edge id has the length-prefixed form described under [Relationships](#relationships-child-states). The Rust SDK has no deprecated API.
</RustNote>

**Parameters:**

- `from_id` — The source node's primary-key value. The connector MERGEs `(s:FromLabel {pk: $from_id})` so endpoints are auto-created if absent.
- `to_id` — The target node's primary-key value. Same MERGE behavior.
- `record` — <Lang only="python">Optional row object whose fields populate the relationship's properties.</Lang><Lang only="rust">The row whose fields populate the relationship's properties (`declare_relation_record` only).</Lang> Its primary key field, if present, is the edge's id.

If <Lang only="python">`record` is omitted</Lang><Lang only="rust">the edge is declared with `declare_relation`</Lang> or the record has no primary key value, the connector derives the edge id from its endpoints: the source label, source id, target label and target id, each written as `<UTF-8 byte length>:<value>;`. For example, an edge from `Person` `"alice"` to `Task` `42` gets the id `6:Person;5:alice;4:Task;2:42;`. A string id that reads as an integer, or that starts with `s:`, is written with an `s:` prefix, so the ids `1` and `"1"` never share an edge. <Lang only="python">Endpoint ids must then be `int` or `str`; for other types, pass a `record` that carries the primary key.</Lang>

An edge id names one edge. When the endpoints of an edge with an explicit id change, the edge moves: the upsert deletes the relationship of this type with the same id between the old endpoints. To find it, every upsert looks the edge up by its primary key property. A system-managed relationship table has an index on it; for a user-managed table, create one yourself.

- `field` — The node property holding the vector.
- `metric` — Similarity metric: <Lang only="python">`"cosine"` or `"euclidean"`</Lang><Lang only="rust">`VectorMetric::Cosine` or `VectorMetric::Euclidean`</Lang>. Translated to Neo4j's `vector.similarity_function` option.
- `dimension` — The vector's dimension. Required.

The connector emits:

```cypher
CREATE VECTOR INDEX `coco_vec_<Label>__<field>` IF NOT EXISTS
FOR (n:`Label`) ON n.`field`
OPTIONS { indexConfig: {
  `vector.dimensions`: <N>,
  `vector.similarity_function`: '<metric>'
} }
```

The Neo4j index is named after the label and field, not after `name`, so a field has at most one vector index. Renaming `name` keeps the index. Declaring a second name for the same field is an error.

Vectors are float32 only.

### DDL: indexes and constraints

For each managed table, the connector creates supporting Cypher artifacts on first run:

- For node tables: a uniqueness constraint on the primary key —
  ```cypher
  CREATE CONSTRAINT `coco_uniq_<Label>__<pk>` IF NOT EXISTS
  FOR (n:`<Label>`) REQUIRE n.`<pk>` IS UNIQUE
  ```
  Neo4j auto-creates a backing index for each constraint, so a separate `CREATE INDEX` is redundant on nodes.
- For relationship tables:
  ```cypher
  CREATE INDEX `coco_idx_rel_<RelType>__<pk>` IF NOT EXISTS
  FOR ()-[r:`<RelType>`]-() ON (r.`<pk>`)
  ```

A system-managed table owns its label or relationship type, the way a Postgres table owns its rows. When the table is no longer declared, or on `cocoindex drop`, the connector destroys it: every node carrying the label is deleted (`DETACH DELETE`, so the relationships attached to those nodes go with them) or every relationship of the type is deleted, and then the constraint or index is dropped. A node table's vector indexes (the `coco_vec_<Label>__<field>` indexes on its label) are dropped with it. This includes nodes and relationships written under that label or type by anything other than CocoIndex — to share a label with data CocoIndex doesn't own, declare the table <Lang only="python">with `managed_by="user"`</Lang><Lang only="rust">with `ManagedTargetOptions::user_managed()`</Lang>.

The same teardown happens when a table's identity changes — its primary key field, or a relationship table's endpoint tables or their primary keys: the table is destroyed and recreated, and the components that declared its records are reprocessed. Its vector indexes are dropped and created again. Attaching a schema or changing a property type does not rebuild the table; at most the records are re-upserted.

When <Lang only="python">`managed_by="user"` is set</Lang><Lang only="rust">a table is user-managed</Lang>, the connector skips DDL entirely (you're responsible for creating and dropping the schema) and never bulk-deletes: when the table is no longer declared or the app is dropped, its nodes or relationships are left as-is (see [Destroy vs. Abandon](../programming_guide/target_state#how-cocoindex-syncs-target-states)). Record-level upserts and deletes still work while the table is declared.<Lang only="rust"> Pass `ManagedTargetOptions::user_managed()` to `mount_table_target_with_options` or `mount_relation_target_with_options`.</Lang>

## Deprecated: table and relation APIs

The table and relation APIs are deprecated. They emit a `DeprecationWarning` and otherwise work as before. Each has a replacement with the same parameters:

| Deprecated | Replacement |
|---|---|
| `table_target`, `declare_table_target`, `mount_table_target` (returns `TableTarget`) | `node_target`, `declare_node_target`, `mount_node_target` (returns `NodeTarget`) |
| `relation_target`, `declare_relation_target`, `mount_relation_target` (returns `RelationTarget`) | `relationship_target`, `declare_relationship_target`, `mount_relationship_target` (returns `RelationshipTarget`) |
| `RelationTarget.declare_relation` | `RelationshipTarget.declare_relationship` |

One parameter check differs: the relationship APIs require `primary_key` to match the schema's primary key, as the node APIs do, where the relation APIs used the schema's.

The deprecated APIs keep the keys and edge ids of existing tables, and with them three limits the replacements remove:

- A node table and a relationship table share one key space, so a label and a relationship type must have different names. Declaring both under one name fails the update.
- The derived edge id is `{from_label}_{from_id}_{to_label}_{to_id}`. Two endpoint pairs can share it (the ids `1` and `"1"`, or ids that contain `_`), and declaring both fails the update.
- A label or relationship type may contain `__` or end with `_`, so two tables' constraint or index names can coincide.

A label belongs to one table: don't declare the same label (or relationship type) through both the deprecated and the new API. The two declarations are separate tables, and removing either one deletes every node of the label (or edge of the type).

### Switching an existing table

Switching a table from the deprecated API to its replacement keeps its nodes, edges, constraints and indexes. It takes two updates:

1. Add `managed_by="user"` to each deprecated declaration you switch, and run one update. Nothing in the database changes. From now on, removing these declarations deletes nothing.
2. Replace the deprecated calls with their replacements (and `declare_relation` with `declare_relationship`), without `managed_by="user"`, and run one update. The new tables find their constraints and indexes in place, under the same names. Every node and edge of a switched table is written once more, and its vector indexes are rebuilt. An edge with a derived id gets the new id: the edge with the old id between the same endpoints is replaced.

Run the two steps as separate updates, in this order. Without step 1, removing a deprecated declaration destroys its table: every node of the label or edge of the type is deleted, possibly after the new table has written it.

You can switch tables one at a time: a new relationship table accepts node targets of both APIs.
