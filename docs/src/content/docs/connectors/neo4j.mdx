The `neo4j` connector writes records to [Neo4j](https://neo4j.com), a property graph database. It supports node tables (labels), relationship tables (edge types), per-database multitenancy (one Neo4j cluster, many isolated databases), real Cypher uniqueness constraints, and vector indexes via the `CREATE VECTOR INDEX` DDL form.

## Connection setup

Create a `ConnectionFactory` and provide it via a `ContextKey`. The factory holds the Bolt URI, optional auth, and the target database name; it opens one connection-pooled Neo4j async driver per event loop, on first use on that loop, shared by all tables and batches. Call `await factory.close()` at shutdown (in the lifespan, after `yield`) to close it.

:::note
The key name is load-bearing across runs — it's the stable identity CocoIndex uses to track managed rows. See [ContextKey as stable identity](../programming_guide/context#contextkey-as-stable-identity) before renaming.
:::

{/* Rust: examples/rust/meeting_notes_graph_neo4j/src/main.rs */}

```python
from collections.abc import AsyncIterator
from cocoindex.connectors import neo4j
import cocoindex as coco

KG_DB: coco.ContextKey[neo4j.ConnectionFactory] = coco.ContextKey("kg_db")

@coco.lifespan
async def coco_lifespan(builder: coco.EnvironmentBuilder) -> AsyncIterator[None]:
    factory = neo4j.ConnectionFactory(
        uri="bolt://localhost:7687",
        auth=("neo4j", "cocoindex"),
        database="neo4j",
    )
    builder.provide(KG_DB, factory)
    yield
    await factory.close()
```

For TLS or other driver settings, build a `neo4rs::Graph` yourself and wrap it with `neo4j::Graph::from_client(client, database)`. A `Graph` has no `close()` method.

`auth` is optional — omit it for unauthenticated dev instances. `database` defaults to `"neo4j"` (the default db that ships with every Neo4j 5 installation). The Rust `connect` takes the user, password and database as required arguments.

### Multitenancy

A single Neo4j cluster can host many isolated databases. Pair each database with its own `ContextKey` and `ConnectionFactory(database=...)`:

{/* Rust: examples/rust/meeting_notes_graph_neo4j/src/main.rs (two keys instead of one) */}
<LangTabs>
<Fragment slot="python">

```python
KG_DB: coco.ContextKey[neo4j.ConnectionFactory] = coco.ContextKey("kg_db")
APIS_DB: coco.ContextKey[neo4j.ConnectionFactory] = coco.ContextKey("apis_db")

@coco.lifespan
async def coco_lifespan(builder: coco.EnvironmentBuilder) -> AsyncIterator[None]:
    uri = "bolt://localhost:7687"
    auth = ("neo4j", "cocoindex")
    kg_factory = neo4j.ConnectionFactory(uri=uri, auth=auth, database="kg")
    apis_factory = neo4j.ConnectionFactory(uri=uri, auth=auth, database="apis")
    builder.provide(KG_DB, kg_factory)
    builder.provide(APIS_DB, apis_factory)
    yield
    await kg_factory.close()
    await apis_factory.close()
```

</Fragment>

Different `ContextKey`s with different database names produce fully separate target-state trees — changes to one never spill into the other.

## As target

The `neo4j` connector provides target state APIs for writing nodes to node tables and edges to relationship tables. CocoIndex tracks what records should exist and automatically handles upserts and deletions.

Each apply batch is wrapped in a single Neo4j transaction (`tx.commit()` on success, rollback on exception), so partial writes never leak into the database. Within a batch, writes are ordered as **node upserts → relation upserts → relation deletes → node deletes** so dependent edges always see their endpoints. A batch that fails with a transient error (typically a deadlock between concurrent batches merging edges onto the same nodes) is rolled back and retried with backoff before the failure is reported.

:::note
The node and relationship APIs below replace the table and relation APIs (`mount_table_target`, `mount_relation_target`, …), which are deprecated. To move an existing table over, see [Deprecated: table and relation APIs](#deprecated-table-and-relation-apis).
:::

The Rust SDK names its functions `mount_table_target` / `TableTarget` and `mount_relation_target` / `RelationTarget`. They are the Rust node and relationship APIs, not the deprecated Python ones: a node table and a relationship table live in separate key spaces, so a label and a relationship type may share a name, and a derived edge id has the length-prefixed form described under [Relationships](#relationships-child-states). The Rust SDK has no deprecated API.

The schema is required. **Parameters:**

- `db` — A `ContextKey[neo4j.ConnectionFactory]` for the Neo4j connection.
- `table_name` — The Cypher node label (e.g. `"Document"`). It must not contain `__` or end with `_`: constraint and index names join the label to a property name with `__`, so such a label could share a name with another table's.
- `table_schema` — Optional schema definition (see [Table Schema](#table-schema-from-python-class)). The schema participates in CocoIndex's fingerprint (so two flows declaring the same label must agree); per-property type DDL is not emitted in v1.
- `primary_key` — Single property name used as the node's primary key. Defaults to `"id"`. Must match the schema's primary key when `table_schema` is given. Compound primary keys are not supported in v1.0.
- `managed_by` — Whether CocoIndex manages the table lifecycle (`"system"`) or assumes it exists (`"user"`).

**Returns:** A pending `NodeTarget`. Use `await neo4j.mount_node_target(KG_DB, ...)` to get a resolved target.

`declare_relation` declares an edge without properties. `declare_relation_record` adds the properties of `record`; a record that carries the primary key is keyed by it (a string or an integer), otherwise the id is derived from the endpoints.

</Fragment>
</LangTabs>

**Parameters:**

- `from_id` — The source node's primary-key value. The connector MERGEs `(s:FromLabel {pk: $from_id})` so endpoints are auto-created if absent.
- `to_id` — The target node's primary-key value. Same MERGE behavior.
- `record` — Optional row object whose fields populate the relationship's properties. Its `primary_key` field, if present, is the edge's id.

If `record` is omitted or has no primary key value, the connector derives the edge id from its endpoints: the source label, source id, target label and target id, each written as `<UTF-8 byte length>:<value>;`. For example, an edge from `Person` `"alice"` to `Task` `42` gets the id `6:Person;5:alice;4:Task;2:42;`. A string id that reads as an integer, or that starts with `s:`, is written with an `s:` prefix, so the ids `1` and `"1"` never share an edge. Endpoint ids must then be `int` or `str`; for other types, pass a `record` that carries the primary key.

An edge id names one edge. When the endpoints of an edge with an explicit id change, the edge moves: the upsert deletes the relationship of this type with the same id between the old endpoints. To find it, every upsert looks the edge up by its primary key property. A system-managed relationship table has an index on it; for a `managed_by="user"` table, create one yourself.

`VectorMetric::Cosine` and `VectorMetric::Euclidean` are the Neo4j metrics; `VectorMetric::InnerProduct` is FalkorDB-only and fails on Neo4j. The Rust `TableTarget` also has `declare_node_index(ctx, &["name"])`, which declares a plain secondary index on the listed properties.

</Fragment>

**Parameters:**

- `name` — Optional logical name for the index. Defaults to `f"vec_{table_name}__{field}"`.
- `field` — The node property holding the vector.
- `metric` — Similarity metric: `"cosine"` or `"euclidean"`. Translated to Neo4j's `vector.similarity_function` option.
- `dimension` — The vector's dimension. Required.

The connector emits:

```cypher
CREATE VECTOR INDEX `coco_vec_<Label>__<field>` IF NOT EXISTS
FOR (n:`Label`) ON n.`field`
OPTIONS { indexConfig: {
  `vector.dimensions`: <N>,
  `vector.similarity_function`: '<metric>'
} }
```

The Neo4j index is named after the label and field, not after `name`, so a field has at most one vector index. Renaming `name` keeps the index. Declaring a second name for the same field is an error.

Vectors are float32 only.

#### Default Python → Neo4j type mapping

Most types pass through native Bolt encoding — no per-value transform applied:

| Python type | Rust type | Neo4j type | Notes |
|---|---|---|---|
| `bool` | `bool` | `BOOLEAN` | |
| `int`, NumPy integer scalars | `i16`, `i32`, `i64` (and the unsigned widths) | `INTEGER` | |
| `float`, NumPy float scalars | `f32`, `f64` | `FLOAT` | |
| `decimal.Decimal` | `rust_decimal::Decimal` | `STRING` | Encoded via `str()` — Neo4j has no decimal type. |
| `str` | `String` | `STRING` | |
| `bytes` | `Vec<u8>` | `BYTES` | Native Bolt type — no encoder. |
| `uuid.UUID` | `uuid::Uuid` | `STRING` | Encoded via `str()`. |
| `datetime.date` | `chrono::NaiveDate` | `DATE` | Native Bolt type. |
| `datetime.datetime` | `chrono::DateTime`, `chrono::NaiveDateTime` | `ZONED_DATETIME` | Native Bolt type. |
| `datetime.time` | `chrono::NaiveTime` | `LOCAL_TIME` | Native Bolt type. |
| `datetime.timedelta` | `std::time::Duration` | `DURATION` | Native Bolt type. |
| `numpy.ndarray` (with `VectorSchema` annotation) | `#[coco(vector)] Vec<f32>` | `LIST<FLOAT>` | Encoded via `tolist()`; paired with vector-index DDL. |
| `dict`, list, nested record, `Any` | other `Vec<T>`, maps, nested structs, `#[coco(json)]` | `MAP` / `LIST<ANY>` | Passed through native parameter binding. In Rust the recorded type is `MAP`. |

### DDL: indexes and constraints

For each managed table, the connector creates supporting Cypher artifacts on first run:

- For node tables: a uniqueness constraint on the primary key —
  ```cypher
  CREATE CONSTRAINT `coco_uniq_<Label>__<pk>` IF NOT EXISTS
  FOR (n:`<Label>`) REQUIRE n.`<pk>` IS UNIQUE
  ```
  Neo4j auto-creates a backing index for each constraint, so a separate `CREATE INDEX` is redundant on nodes.
- For relationship tables:
  ```cypher
  CREATE INDEX `coco_idx_rel_<RelType>__<pk>` IF NOT EXISTS
  FOR ()-[r:`<RelType>`]-() ON (r.`<pk>`)
  ```

A system-managed table owns its label or relationship type, the way a Postgres table owns its rows. When the table is no longer declared, or on `cocoindex drop`, the connector destroys it: every node carrying the label is deleted (`DETACH DELETE`, so the relationships attached to those nodes go with them) or every relationship of the type is deleted, and then the constraint or index is dropped. A node table's vector indexes (the `coco_vec_<Label>__<field>` indexes on its label) are dropped with it. This includes nodes and relationships written under that label or type by anything other than CocoIndex — to share a label with data CocoIndex doesn't own, declare the table with `managed_by="user"`.

The same teardown happens when a table's identity changes — its primary key field, or a relationship table's endpoint tables or their primary keys: the table is destroyed and recreated, and the components that declared its records are reprocessed. Its vector indexes are dropped and created again. Attaching a schema or changing a property type does not rebuild the table; at most the records are re-upserted.

When `managed_by="user"` is set, the connector skips DDL entirely (you're responsible for creating and dropping the schema) and never bulk-deletes: when the table is no longer declared or the app is dropped, its nodes or relationships are left as-is (see [Destroy vs. Abandon](../programming_guide/target_state#how-cocoindex-syncs-target-states)). Record-level upserts and deletes still work while the table is declared. In Rust, pass `ManagedTargetOptions::user_managed()` to `mount_table_target_with_options` or `mount_relation_target_with_options`.

## Deprecated: table and relation APIs

This section applies to the Python SDK only. The Rust SDK's `mount_table_target` and `mount_relation_target` are its current API, with the node and relationship semantics described above.

The table and relation APIs are deprecated. They emit a `DeprecationWarning` and otherwise work as before. Each has a replacement with the same parameters:

| Deprecated | Replacement |
|---|---|
| `table_target`, `declare_table_target`, `mount_table_target` (returns `TableTarget`) | `node_target`, `declare_node_target`, `mount_node_target` (returns `NodeTarget`) |
| `relation_target`, `declare_relation_target`, `mount_relation_target` (returns `RelationTarget`) | `relationship_target`, `declare_relationship_target`, `mount_relationship_target` (returns `RelationshipTarget`) |
| `RelationTarget.declare_relation` | `RelationshipTarget.declare_relationship` |

One parameter check differs: the relationship APIs require `primary_key` to match the schema's primary key, as the node APIs do, where the relation APIs used the schema's.

The deprecated APIs keep the keys and edge ids of existing tables, and with them three limits the replacements remove:

- A node table and a relationship table share one key space, so a label and a relationship type must have different names. Declaring both under one name fails the update.
- The derived edge id is `{from_label}_{from_id}_{to_label}_{to_id}`. Two endpoint pairs can share it (the ids `1` and `"1"`, or ids that contain `_`), and declaring both fails the update.
- A label or relationship type may contain `__` or end with `_`, so two tables' constraint or index names can coincide.

A label belongs to one table: don't declare the same label (or relationship type) through both the deprecated and the new API. The two declarations are separate tables, and removing either one deletes every node of the label (or edge of the type).

### Switching an existing table

Switching a table from the deprecated API to its replacement keeps its nodes, edges, constraints and indexes. It takes two updates:

1. Add `managed_by="user"` to each deprecated declaration you switch, and run one update. Nothing in the database changes. From now on, removing these declarations deletes nothing.
2. Replace the deprecated calls with their replacements (and `declare_relation` with `declare_relationship`), without `managed_by="user"`, and run one update. The new tables find their constraints and indexes in place, under the same names. Every node and edge of a switched table is written once more, and its vector indexes are rebuilt. An edge with a derived id gets the new id: the edge with the old id between the same endpoints is replaced.

Run the two steps as separate updates, in this order. Without step 1, removing a deprecated declaration destroys its table: every node of the label or edge of the type is deleted, possibly after the new table has written it.

You can switch tables one at a time: a new relationship table accepts node targets of both APIs.
