Slice of #2823 (the battle-test fixes): the SQL target connectors. Postgres `NOT NULL` restore, the Doris atomic upsert, the `_table_key` refactor of the four SQL targets, and the vec0 column-name check.

## What changes

**Postgres: `NOT NULL` restored once per run, by the table action.** PostgreSQL can't add a `NOT NULL` column to a table that has rows, so CocoIndex adds it nullable and gives it the constraint back once every row holds a value. Before, only a row batch tried, with a full-table scan on every batch, and nothing else did: a run with no row change (one after a run that failed or stopped between the DDL and its row writes) never restored the constraint, and `ADD COLUMN IF NOT EXISTS … NOT NULL` landing on a column that was already there nullable reported it `NOT NULL`. Now `_TableHandler._apply_actions` reads the declared `NOT NULL` columns the table holds as nullable from `pg_attribute` on every run and restores them after its DDL commits, so a restart recovers them from the catalog, not from memory. The columns still holding a `NULL` are handed to the run's row handler, which retries after the 1st, 2nd, 4th, 8th… batch instead of scanning on every one; whatever it misses, the next run's table action gets. A column is added `NOT NULL` directly whenever the table lets it (no rows), with the violation, not a racy emptiness check, telling it has rows. The postgres docs page gains a "Schema changes" paragraph that says this.

**Doris: load, delete, then commit.** An upsert of a `DUPLICATE KEY` table deleted the old rows of its keys before it Stream Loaded the new ones, so a load Doris rejected (a row that doesn't fit a column, "too many filtered rows") left those keys gone until a later run. Each chunk now Stream Loads with two-phase commit (loaded, not visible), deletes the old rows, then commits through `_stream_load_2pc`; a delete that fails aborts the load, and the run polls `get_load_state` until the committed transaction is `VISIBLE`, as a one-phase load waits before it answers, warning past `stream_load_timeout` as a one-phase load's `Publish Timeout` does. The FE's 307 to a BE is followed by hand to `be_load_host` when it is set, for the 2PC endpoint as for the load.

**SQL targets, same shape.** Postgres, SQLite, BigQuery and Snowflake each build their table key through one `_table_key(...)` that validates the names, the form the dropped-table check (slice 4) calls from `mount_table_target`. SQLite's vec0 rejects a column name it cannot declare (`_`-prefixed, `k`, `distance`) with a `ValueError` instead of a failed `CREATE`.

- SQLite, BigQuery and Snowflake already keep `NOT NULL` on a re-added column on `main` (`_column_sql` in their `ADD COLUMN`); nothing to port. The Doris "re-raise a failed `DROP TABLE`" DDL fix is already on `main` (#2805's neighbour, `test_doris_target_ddl_swallow.py`).
